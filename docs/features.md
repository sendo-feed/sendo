## Phase 1：MVP

これがないと RSS リーダーとして成り立たない。

| 機能 | 内容 |
|---|---|
| 購読管理 | フィードの追加・削除、フォルダ／カテゴリ。OPML のインポートとエクスポート（Feedly からの移行に必須） |
| 取得（クローラ） | RSS、Atom、JSON Feed に対応。サイトの URL からフィードを自動で見つける。ETag ／ Last-Modified で無駄な取得を避け、取得の頻度はフィードごとに調整する |
| 記事の保存 | 既読・未読、スター（保存）、重複の排除 |
| REST API | 機能はすべて API から使えるようにする（API ファースト） |
| Google Reader API 互換 | Reeder や NetNewsWire がそのまま使える |
| MCP サーバー | 最初からツールとして公開する（[下](#mcp-のイメージ)） |
| 認証 | API トークン（エージェント用）とユーザーアカウント |

**最初のゴール：Feedly の OPML を移して、毎日 Sendo で読む**

## Phase 2：Feedly のプレミアム機能に当たるもの

| 機能 | 内容 |
|---|---|
| 全文の取得 | 要約だけのフィードでも、本文を抜き出して保存する（Readability のような処理）。LLM に渡すにはほぼ必須 |
| 全文検索 | まずは SQLite の FTS5 で十分 |
| フィルタとルール | キーワードや正規表現で、ミュート、自動タグ付け、自動スターを行う |
| 通知 | Webhook、ntfy、Slack など。sendo-reader 向けには Web Push |
| RSS がないサイトのフィード化 | 下の表 |

**RSS がないサイトのフィード化**

| 方法 | 内容 |
|---|---|
| Web ページの変化の監視 | CSS セレクタを指定して、変化を記事にする |
| メールマガジンの変換 | 受信用のアドレスを発行し、届いたメールを記事にする |
| 外部ブリッジとの連携 | RSS-Bridge などとつなぐ |
| X | 公式にログインなしでは読めないので、ブリッジ経由のベストエフォートに留める。深追いしない |

## Phase 3：LLM を使う部分（Sendo ならではの機能）

| 機能 | 内容 |
|---|---|
| 要約 | 記事ごとの要約に加えて、「今日の新着をまとめて」のようなダイジェストを作る |
| 自動分類とタグ付け | LLM や埋め込みベクトルで分類する |
| 関連度スコア | ユーザーの関心（スターや既読の傾向、自然文で書いた関心）に照らして、記事を並べ替えたり絞り込んだりする。鮮度と関連度の両方で並べる |
| クラスタリング | 同じ話題を扱う複数の記事を1件にまとめる |
| 意味検索 | ベクトル検索 |
| LLM の差し替え | OpenAI 互換のエンドポイントにして、Claude、OpenAI、ローカル LLM（Ollama など）を設定で選べるようにする。API キーは各自が持つ |

## MCP のイメージ

**ツール**

| ツール | 用途 |
|---|---|
| `list_feeds` ／ `subscribe` ／ `unsubscribe` | 購読管理 |
| `get_unread` | 未読の取得（期間、フォルダ、件数で絞り込む） |
| `search_articles` | 全文検索と意味検索 |
| `get_article` | 本文の取得（全文抽出済みの内容） |
| `mark_read` ／ `star` | 状態の更新 |
| `digest` | 指定した期間やテーマのダイジェスト |

**リソース**

フィードの一覧や今日の未読を MCP の Resources として公開し、エージェントがコンテキストとして読み込みやすくする。

記事の本文は外部から来る信頼できないデータなので、ツールやリソースで返すときも、エージェントへの指示として読まれないように扱う。書き込み系のツール（`subscribe`、`mark_read` など）の権限の分け方は、技術構成の未決事項 4 で決める。

## 設計の方針

- **LLM はオプション**：LLM 関連の機能はすべてオプションにする。LLM を設定しなくても、普通の RSS サーバーとして完結する。
- **重い処理は非同期**：取得ジョブ、全文抽出、LLM 処理はキューで非同期に流し、API の応答を重くしない。
- **第1版は Cloudflare 前提、移植の余地を残す**：デプロイ先は各自で用意する前提だが、第1版は Cloudflare（Workers・D1・Queues）の上で作る。Cloudflare 固有の部分は緩衝層に閉じ込め、1つのバイナリや Docker で動かす形、SQLite（個人用）と Postgres（複数ユーザー用）の切り替えは、移植するときに足す（[decisions/tech-stack.md](decisions/tech-stack.md)）。

### Cloudflare での実現（案）

| 機能 | 第1版（Cloudflare） | 移植するときの候補 |
|---|---|---|
| 取得・全文抽出・LLM 処理のキュー | Queues | SQLite のジョブ表 |
| 定期的な取得 | Cron Triggers | Node 側のスケジューラ |
| 全文検索 | D1 の FTS5 | SQLite の FTS5 ／ Postgres の全文検索 |
| 意味検索 | Vectorize | sqlite-vec ／ pgvector |
| メールマガジンの受信 | Email Workers（Email Routing） | SMTP の受信サーバー |
| 認証 | API トークン、個人利用は Cloudflare Access も | API トークン ／ OAuth |
