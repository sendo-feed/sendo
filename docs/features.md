## Phase 1：MVP

これがないと RSS リーダーとして成り立たない。

| 機能 | 内容 |
|---|---|
| 購読管理 | フィードの追加・削除、フォルダ／カテゴリ。OPML のインポートとエクスポート（Feedly からの移行に必須） |
| 取得（クローラ） | RSS、Atom、JSON Feed に対応。サイトの URL からフィードを自動で見つける。ETag ／ Last-Modified で無駄な取得を避け、取得の頻度はフィードごとに調整する |

| 認証 | API トークン（エージェント用）とユーザーアカウント |

## Phase 2：Feedly のプレミアム機能に当たるもの

| 機能 | 内容 |
|---|---|
| 全文の取得 | 要約だけのフィードでも、本文を抜き出して保存する（Readability のような処理）。LLM に渡すにはほぼ必須。フィードに入っている本文は、先に配っている。記事のページから抜くのはコンテナ版だけで、取り込んだときに抜く（[記事の本文](decisions/content.md)）。Readability で抜けないサイトのために、フィードごとに抜き方（Readability ／ CSS・XPath のセレクタ）を選べるようにする。セレクタは LLM が直近の記事から推定し、方式ごとの結果（文字数と処理時間）を並べて選べるようにする |
| 全文検索 | まずは SQLite の FTS5 で十分。トークナイザーは trigram にする（既定のトークナイザーでは、分かち書きのない日本語を引けない）。trigram では 3 文字未満の語を引けないので、その引き方は作るときに決める。D1 で trigram が使えるかは確かめる |
| フィルタとルール | キーワードや正規表現で、ミュート、自動タグ付け、自動スターを行う。「PR 記事は除外」「このフィードは 3 時間おきに更新、翻訳しない」のような自然文の指示は、エージェントが MCP 越しにルールと設定に書き換える。sendo の側は構造化したルールだけを持ち、LLM を持たない |
| 通知 | Webhook、ntfy、Slack など。sendo-reader 向けには Web Push |
| RSS がないサイトのフィード化 | 下の表 |

**RSS がないサイトのフィード化**

| 方法 | 内容 |
|---|---|
| Web ページの変化の監視 | CSS セレクタを指定して、変化を記事にする。URL を入れると、LLM が記事らしい部分を推定してセレクタを作り、プレビューを出す。保存したあとの取得では LLM を呼ばない |
| メールマガジンの変換 | 受信用のアドレスを発行し、届いたメールを記事にする。送信者ごとにフィードを自動で作る。トラッキングピクセルとレイアウト用の表を取り除き、リンクは Web 版の URL に直す。メールでしか全文が届かないもの（有料の Substack など）も読める |
| 外部ブリッジとの連携 | RSS-Bridge などとつなぐ |
| X | 公式にログインなしでは読めないので、ブリッジ経由のベストエフォートに留める。深追いしない |

## Phase 3：LLM を使う部分（Sendo ならではの機能）

| 機能 | 内容 |
|---|---|
| 要約 | 記事ごとの要約に加えて、「今日の新着をまとめて」のようなダイジェストを作る |
| 翻訳 | 英語など読む人の言語でない記事の、要約と本文を訳す。訳すのは記事を取り込んだときに記事ごとに 1 回で、訳文を全員で使い回す。記事の行は変えず、訳文は別に持つ。品質を求めるものは Claude Platform（Claude API）で訳す。ふだんは Message Batches API でまとめて送る（料金が半分になる。たいていは 1 時間以内に返るが、最大 24 時間かかり、終わらなかった分は送り直す）。まだ訳文のない記事を読む人が開いたときだけ、その記事をその場で通常の API で訳す。その場で訳した記事は、バッチの結果を捨てる。訳す前に言語を判定し、読む人の言語の記事は LLM に送らない。コード、画像、リンクは訳させず、訳す前に置き換えて、訳したあとで元に戻す（本文の構造を崩さない）。原文も読める |
| 自動分類とタグ付け | LLM や埋め込みベクトルで分類する |
| 関連度スコア | ユーザーの関心（スターや既読の傾向、自然文で書いた関心、下の行動の記録）に照らして、記事を並べ替えたり絞り込んだりする。鮮度と関連度の両方で並べる |
| 行動の記録 | 関連度スコアの材料。開封、実際に読んでいた時間（画面にフォーカスがあり、直近 60 秒以内に操作があった時間だけ）、本文のリンクのクリック、いいね ／ よくないね を記録する。履歴が要るので、集めるのは関連度スコアより先に始める。D1 の書き込みを増やしすぎないよう、クライアントでまとめて送る |
| クラスタリング | 同じ話題を扱う複数の記事を1件にまとめる |
| 意味検索 | キーワード検索（FTS5）とベクトル検索を RRF で混ぜたハイブリッド検索にする。言葉が一致しなくても、意味が近い記事が見つかる。埋め込みは小さい多言語のモデルで作り、次元を減らして軽くする（コンテナ版は Rust で、CPU で作る想定）。類似度のしきい値は、実際の記事で測って決める |
| 似た記事 | 読んでいる記事に近い記事を、意味検索と同じ埋め込みで出す。同じ話題の記事はクラスタリングで 1 件にまとめる |
| LLM の差し替え | OpenAI 互換のエンドポイントにして、Claude、OpenAI、ローカル LLM（Ollama など）を設定で選べるようにする。品質を求める機能（翻訳など）には Claude Platform を使えるように、機能ごとに選べるようにする。API キーは各自が持つ |

## MCP のイメージ

**ツール**

| ツール | 用途 |
|---|---|
| `list_feeds` ／ `subscribe` ／ `unsubscribe` | 購読管理 |
| `get_unread` | 未読の取得（期間、フォルダ、件数で絞り込む） |
| `search_articles` | 全文検索と意味検索 |
| `similar_articles` | 指定した記事に近い記事 |
| `get_article` | 本文の取得（全文抽出済みの内容） |
| `mark_read` ／ `star` | 状態の更新 |
| `digest` | 指定した期間やテーマのダイジェスト |
| `get_rules` ／ `set_rules` | フィードのルールと設定の読み書き（自然文の指示を、エージェントが構造化して書く） |

**リソース**

フィードの一覧や今日の未読を MCP の Resources として公開し、エージェントがコンテキストとして読み込みやすくする。

記事の本文は外部から来る信頼できないデータなので、ツールやリソースで返すときも、エージェントへの指示として読まれないように扱う。書き込み系のツール（`subscribe`、`mark_read` など）の権限の分け方は、技術構成の未決事項 4 で決める。

## 設計の方針

- **LLM はオプション**：LLM 関連の機能はすべてオプションにする。LLM を設定しなくても、普通の RSS サーバーとして完結する。
- **LLM は設定するときに使う**：セレクタの推定や、自然文の指示からルールへの変換のように、LLM は設定を作るときにだけ呼び、そのあとは保存した設定どおりに決まった動きをする。同じ入力からは毎回同じ結果が出て、速く、費用もかからない。
- **重い処理は非同期**：取得ジョブ、全文抽出、LLM 処理はキューで非同期に流し、API の応答を重くしない。
- **2 つの版**：デプロイ先は各自で用意する前提。無料プランで動く Cloudflare 版（Workers・D1・Queues）と、CPU を多く使う機能も載せるコンテナ版（Node ＋ SQLite）を、同じコードから作る。どちらの版に載せるかは、機能を作るときに測って決める（[decisions/tech-stack.md](decisions/tech-stack.md)、[decisions/container.md](decisions/container.md)）。

### 2 つの版での実現（案）

| 機能 | Cloudflare 版 | コンテナ版 |
|---|---|---|
| 取得・全文抽出・LLM 処理のキュー | Queues | SQLite のジョブの表 |
| 定期的な取得 | Cron Triggers | 同じプロセスのタイマー |
| 全文検索 | D1 の FTS5 | SQLite の FTS5 |
| 意味検索 | Vectorize | sqlite-vec |
| メールマガジンの受信 | Email Workers（Email Routing） | SMTP の受信サーバー |
| 認証 | 自前の OpenID Connect（Google など）とセッション、アクセストークン（[decisions/accounts.md](decisions/accounts.md)） | 同じ（実行環境に依存しない） |
