## Phase 1：MVP

これがないと RSS リーダーとして成り立たない。

| 機能 | 内容 |
|---|---|
| 購読管理 | フィードの追加・削除、購読ごとの表示名、フォルダ／カテゴリ。OPML のインポートとエクスポート（Feedly からの移行に必須） |
| 取得（クローラ） | RSS、Atom、JSON Feed に対応。サイトの URL からフィードを自動で見つける。ETag ／ Last-Modified で無駄な取得を避け、取得の頻度はフィードごとに調整する |

## Phase 2：Feedly のプレミアム機能に当たるもの

| 機能 | 内容 |
|---|---|
| 全文の取得 | 要約だけのフィードでも、本文を抜き出して保存する（Readability のような処理）。LLM に渡すにはほぼ必須。フィードに入っている本文は、先に配っている。記事のページからは、取り込んだときに抜く（[記事の本文](decisions/content.md)）。サイト別の設定は持たず、ページ全体の DOM を候補として本文と不要なブロックを判定する。遅延画像を正規化し、本文中の画像ページも上限付きで調べ、同じ写真の拡大版を採る |
| 全文検索 | まずは SQLite の FTS5 で十分。トークナイザーは trigram にする（既定のトークナイザーでは、分かち書きのない日本語を引けない）。trigram では 3 文字未満の語を引けないので、その引き方は作るときに決める |
| フィルタとルール | キーワードや正規表現で、ミュート、自動タグ付け、自動スターを行う。「PR 記事は除外」「このフィードは 3 時間おきに更新、翻訳しない」のような自然文の指示は、エージェントが MCP 越しにルールと設定に書き換える。sendo の側は構造化したルールだけを持ち、LLM を持たない |
| 通知 | Webhook、ntfy、Slack など。sendo-reader 向けには Web Push |
| RSS がないサイトのフィード化 | 下の表 |

**RSS がないサイトのフィード化**

| 方法 | 内容 |
|---|---|
| Web ページの変化の監視 | CSS セレクタを指定して、変化を記事にする。URL を入れると、LLM が記事らしい部分を推定してセレクタを作り、プレビューを出す。保存したあとの取得では LLM を呼ばない |
| メールマガジンの変換 | 受信用のアドレスを発行し、届いたメールを記事にする。送信者ごとにフィードを自動で作る。トラッキングピクセルとレイアウト用の表を取り除き、リンクは Web 版の URL に直す。メールでしか全文が届かないもの（有料の Substack など）も読める |
| 外部ブリッジとの連携 | RSS-Bridge などとつなぐ |
| X | 公式にログインなしでは読めないので、ブリッジ経由のベストエフォートに留める。深追いしない |

## Phase 3：LLM を使う部分（Sendo ならではの機能）

翻訳の前処理として、主言語を LLM なしで判定し、入力元ごとに DB の別表へ保存する。
本文のない記事はタイトル・要約の暫定判定とし、情報不足・不確実な結果は保留する。
方式の根拠と検証結果は[記事の言語判定](decisions/article-language.md)に記載する。翻訳の決まりは[記事の翻訳](decisions/translation.md)が正。

| 機能 | 内容 |
|---|---|
| 要約 | 記事ごとの要約に加えて、「今日の新着をまとめて」のようなダイジェストを作る |
| 翻訳 | 日本語以外の記事の、タイトル、要約、本文を日本語に訳す。訳文は記事ごとに 1 つで、全員で使い回す。記事の行は変えず、訳文は別に持つ。Claude Platform（Claude API）で訳す。取り込んだ記事は Message Batches API でまとめて自動で訳す（料金が半分になる。最大 24 時間かかる）。まだ訳文のない記事は、読む人が求めたときだけ、その場で通常の API で訳す。品質を上げたいときは、求めれば品質優先のモデル（既定は Opus）で訳し直す。費用を抑えるため、自動の翻訳の長い記事は安いモデル（既定は Haiku）で訳す。モデルと思考量は設定で変えられ、訳したときのモデルと思考量は記事の画面に出す。訳す前に言語を判定し、日本語の記事は LLM に送らない。HTML は渡さず、文の断片だけを送る（本文の構造を崩さない）。原文も読める。Discord の投稿は訳さない（[記事の翻訳](decisions/translation.md)） |
| 自動分類とタグ付け | LLM や埋め込みベクトルで分類する |
| 関連度スコア | ユーザーの関心（スターや既読の傾向、自然文で書いた関心、下の行動の記録）に照らして、記事を並べ替えたり絞り込んだりする。鮮度と関連度の両方で並べる |
| 行動の記録 | 関連度スコアの材料。開封、実際に読んでいた時間（画面にフォーカスがあり、直近 60 秒以内に操作があった時間だけ）、本文のリンクのクリック、いいね ／ よくないね を記録する。履歴が要るので、集めるのは関連度スコアより先に始める。書き込みを増やしすぎないよう、クライアントでまとめて送る |
| クラスタリング | 同じ話題を扱う複数の記事を1件にまとめる |
| 意味検索 | キーワード検索（FTS5）とベクトル検索を RRF で混ぜたハイブリッド検索にする。言葉が一致しなくても、意味が近い記事が見つかる。埋め込みは小さい多言語のモデルで作り、次元を減らして軽くする（Rust で、CPU で作る想定）。類似度のしきい値は、実際の記事で測って決める |
| 似た記事 | 読んでいる記事に近い記事を、意味検索と同じ埋め込みで出す。同じ話題の記事はクラスタリングで 1 件にまとめる |
| LLM の差し替え | OpenAI 互換のエンドポイントにして、Claude、OpenAI、ローカル LLM（Ollama など）を設定で選べるようにする。API キーは各自が持つ。翻訳は Batches と structured outputs を使うので、差し替えず Claude API をそのまま使う（[記事の翻訳](decisions/translation.md)） |

## MCP のイメージ

**ツール**

| ツール | 用途 |
|---|---|
| `list_feeds` ／ `subscribe` ／ `unsubscribe` | 購読管理 |
| `rename_feed` | 購読ごとの表示名を設定し、null で配信元の名前に戻す |
| `list_folders` ／ `move_feed` | 空のフォルダも含めて名前と ID を調べ、購読済みのフィードを別のフォルダか未分類へ移す |
| `create_folder` ／ `rename_folder` ／ `delete_folder` | フォルダを作る（同じ名前があればそれを返す）、名前を変える、消す（中のフィードは購読したまま未分類に戻す） |
| `list_articles` | 既読・未読を含む記事一覧。既読状態、スター、フィード、フォルダで絞り込み、公開日時か既読にした日時で期間の指定と並び替えができる |
| `get_unread` | 未読の取得。フィード、フォルダ、件数、公開日時の期間（`since` 以上、`until` 未満）で絞り込む。日時はタイムゾーン付き ISO 8601。ページ送りでは期間も同じ値を渡す |
| `list_activity` | reader で記事を開いた履歴を、期間・操作元・種類で絞って読む |
| `search_articles` | キーワードで記事のタイトル・要約・索引済み本文を検索する。既読状態・期間などで絞り、抜粋を返す |
| `similar_articles` | 指定した記事に近い記事 |
| `get_article` | 本文の取得（全文抽出済みの内容） |
| `mark_read` ／ `star` | 状態の更新 |
| `digest` | 指定した期間やテーマのダイジェスト |
| `get_rules` ／ `set_rules` | フィードのルールと設定の読み書き（自然文の指示を、エージェントが構造化して書く） |

**リソース**

フィードの一覧（`sendo://feeds`）と今日の未読（`sendo://unread/today`）を MCP の Resources として公開している。読むだけの範囲（`read`）で利用でき、エージェントがコンテキストとして読み込める。今日の未読は、日本時間（`Asia/Tokyo`）に公開された未読の記事を新しい順に最大 50 件返す。返された `since`・`until` と `nextCursor` を `get_unread` に渡せば、同じ日の続きを読める。

記事の本文は外部から来る信頼できないデータなので、ツールやリソースで返すときも、エージェントへの指示として読まれないように扱う。書き込み系のツール（`subscribe`、`mark_read` など）には `write` の範囲を求める（[MCP サーバー](decisions/mcp.md)）。

## 設計の方針

- **LLM はオプション**：LLM 関連の機能はすべてオプションにする。LLM を設定しなくても、普通の RSS サーバーとして完結する。
- **LLM は設定するときに使う**：セレクタの推定や、自然文の指示からルールへの変換のように、LLM は設定を作るときにだけ呼び、そのあとは保存した設定どおりに決まった動きをする。同じ入力からは毎回同じ結果が出て、速く、費用もかからない。例外は翻訳で、記事を取り込んだときと読む人が求めたときに呼び、訳文は記事ごとに 1 つにして全員で使い回す。
- **重い処理は非同期**：取得ジョブ、全文抽出、LLM 処理はキューで非同期に流し、API の応答を重くしない。
- **コンテナだけで動かす**：デプロイ先は各自で用意する前提。Sendo はコンテナ（Node ＋ SQLite）だけで動かし、CPU を多く使う機能も含めてすべての機能を載せる（[decisions/tech-stack.md](decisions/tech-stack.md)、[decisions/container.md](decisions/container.md)）。

### 実現のしかた（案）

| 機能 | 実現のしかた |
|---|---|
| 取得・全文抽出・LLM 処理のキュー | SQLite のジョブの表 |
| 定期的な取得 | 同じプロセスのタイマー |
| 全文検索 | SQLite の FTS5 |
| 意味検索 | sqlite-vec |
| メールマガジンの受信 | SMTP の受信サーバー |
