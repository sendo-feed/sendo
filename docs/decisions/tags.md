# 記事のタグ

- 状態：提案中
- 関連：[記事の解析](article-analysis.md)（候補の語と鍵）、[コンテナ版](container.md)（5 の重い読み取り）、[自動のタグ付け](auto-tagging.md)、[差分同期](sync.md)（1、3、4、9、13）、[通知](notifications.md)（3〜5 のベルの持ち方と API の形）、[ワークスペース](workspaces.md)（名前の扱い）、[保存容量と古い記事の片付け](retention.md)（2）、[ユーザーと認証](accounts.md)、[MCP サーバー](mcp.md)（12）

記事に、利用者が選んだタグを付ける。sendo が記事から抜いた語（[記事の解析](article-analysis.md)）を「タグの候補」として出し、利用者が候補から選ぶか、名前を打って作った語だけをタグとして持つ。タグは、記事の埋め込みとの近さで記事に自動で付ける（[自動のタグ付け](auto-tagging.md)）。利用者は手で付け外しもできる。

言葉の呼び方：

- **候補**：記事から抜いた語。記事ごとに持つ（共有のデータ）
- **タグ**：利用者が選んだ語。人ごとに持つ
- **記事のタグ**：タグを記事に付けた結果。人ごとに持つ

## 決定

### 候補の一覧

1. **候補の一覧は、その人の受信箱の、直近 30 日の記事だけで数える。** 受信箱に入った時刻（`user_articles.created_at`）と記事の公開日時（受信箱の行に写した `user_articles.published_at`）のどちらも、DB の時計で 30 日前ちょうど以降の記事について、鍵ごとに記事の数（同じ記事は 1 回）を数え、多い順に 100 件まで、鍵（`key`）、見出し、記事の数を返す。同じ数なら鍵のコードポイントの順。フィードの偏りでは下げない（ただし、下のフィードの定型の語は除く）。ほかの人の受信箱は数えないので、ほかの人の存在は分からない（[ユーザーと認証](accounts.md)）。
   - 公開日時でも区切るので、移行で一度に入った古い記事（「あとで読む」から移した記事など）や、購読したばかりのフィードの古い記事は数えない。フィードに日付がない記事は、公開日時に取り込んだ時刻が入るので外れない（受け入れる）
   - フィードの定型の語：鍵が、同じフィードのこの範囲の解析済みの記事（版によらず解析の行がある記事。入力が空・失敗を含む）の 50% 以上（ちょうどを含む）に、出どころが記事の文字の候補として出ているときは、そのフィードの記事のその候補は数えない（そのフィードのこの範囲の解析済みの記事が 10 件以上あるときだけ）。分子と分母は同じ記事の集まりで数える。共有ボタン、広告、署名、サイト名のような、記事の中身でないページの部品を落とすため。外した行は、見出しの数からも外す。ほかのフィードの記事からは数える。出どころがフィードのカテゴリの候補は、数えるのにも外すのにも当てない（Qiita のタグのフィードのように、どの記事にも同じカテゴリが付く話題を絞ったフィードで、話題の語を消さないため。カテゴリと記事の文字の両方に出る鍵は、出どころがカテゴリになる。[記事の解析](article-analysis.md)の 10）
   - 数えるのは、解析の行と世代が同じ候補の行だけ（[記事の解析](article-analysis.md)の 5）。候補の版を上げている間は、まだ解析し直していない記事の古い版の候補も数える
   - 鍵は、まとめの鍵（[記事の解析](article-analysis.md)の 11。NFKC・小文字・空白をそろえた形）。版は記事の解析で捨ててあるので、`Java 8` の記事は `Java` として数える
   - 見出しには、その鍵の表記のうちいちばん多いもの（同じ数なら表記のコードポイントの順で先のもの）を使う（`Kubernetes` と `KUBERNETES` なら多いほう）
   - 候補を選んでタグを作るときは、見出しを `POST /tags` の `name` に送る。見出しの照合用の名前は候補の鍵と同じになるので、作ったタグで候補が一覧から外れる（2）
   - 集計は、主のスレッドを止めないよう、別のスレッドの書き込まない接続で流す（[コンテナ版](container.md)の 5）。範囲の絞り込みには `user_articles` の `(user_id, published_at, article_id)` の索引を使う。重いのは候補の行の集計なので、`(user_id, created_at)` の索引は足さない
   - 集計の結果（下の残りの記事の数も）は、利用者ごとにプロセスのメモリに置き、集計が終わった時刻から 1 分未満の間は、集計し直さずに使い回す（ちょうど 1 分からは集計し直す）。同じ利用者の集計が流れている間（別のスレッドの順番を待つ間も）に来たリクエストは、その結果を待って使う（1 人が同時に流す集計は 1 本）。1 分たった結果（下の失敗も）は、次にだれかが一覧を求めたときに捨てる。プロセスを起こし直すと、置いた結果は消える
   - 集計が失敗したら、待っていたリクエストにも失敗を返す。その利用者は、失敗した時刻から 1 分未満の間は集計し直さずに失敗を返す（失敗し続ける集計で、1 本の別のスレッドを占め続けないため）
   - 集計では、外したあと（2）の上位 200 件まで持つ。返すたびに、その時点の有効なタグの照合用の名前と却下の鍵で外し直し、100 件まで返す。使い回す間に却下や作ったタグで外れた枠は、多めに持った分で埋める（使い回す間に 100 件より多く外すと、次に集計するまで 100 件より少なくなる。受け入れる）
   - そのため、次のものは最大で 1 分と集計にかかる時間だけ遅れて出る：新しい記事、30 日の範囲から出た記事（範囲は集計した時刻の DB の時計で決まる）、残りの記事の数、集計した時点で外れていた鍵（却下を戻したり、タグを消すか名前を変えたりしても、次に集計するまで出ない）。集計したあとに却下したりタグにしたりした鍵は、置いた結果に残っているので、外す理由がなくなればすぐに、置いた結果の数で出る
   - 30 日の範囲の記事のうち、解析の行に今の候補の版がない記事の数も返す。画面は「集計中（残り n 件）」と出せる
2. **すでにタグにした語と、却下した語は、一覧から外す。** 有効なタグの照合用の名前（4）と同じ鍵、却下の表にある鍵を、集計する文の中で外し、結果を使い回すときも返すたびに外し直す（1）。鍵の作り方を変えても、照合用の名前と却下の鍵は作り直さない（[記事の解析](article-analysis.md)の 11）。変えたあとは、新しい形の鍵で一覧に戻る語が出うる（受け入れる。もう一度却下すればよい）。
3. **却下は人ごとに持ち、いつでも戻せる。** 行はユーザー、まとめの鍵、却下した時刻を持ち、1 人 1,000 語まで。一般的すぎる語（停止語）を落とすのも、却下で行う（停止語の一覧はコードに持たない。[記事の解析](article-analysis.md)の 9）。
   - 却下するときは、受けた鍵をまとめの鍵の作り方で正規化し直してから測る。2〜40 コードポイントで（候補の長さと同じ）、制御文字か対になっていないサロゲートを含めば 400。戻すときは 2〜40 の決まりを当てず（却下の一覧が返した鍵をそのまま受ける）、受けたままの形で 200 コードポイントまでとし、超えるか、制御文字か対になっていないサロゲートを含めば 400。どちらの 400 もエラーコードは `invalid_key`
   - 却下は、上限を同じ文の中で数える `INSERT … ON CONFLICT DO NOTHING`。却下済みの語は、上限より先に見て成功にする。上限ちょうど（1,000 語目）は受け、超えると 409（`tag_rejection_limit_reached`）
   - 戻すときは、受けた鍵と保存した鍵をそのまま照らして行を消す（正規化し直した形でも照らす）。却下の一覧が返した鍵は、鍵の作り方が変わったあとでも戻せる。ない語を戻しても成功にする。戻すと、集計した時点で却下していた語は次に集計するときから、そのときの数で出る（集計したあとに却下した語は、すぐに、置いた結果の数で出る。1）
   - 却下した語の一覧は、新しい順に返す。管理画面（REST API）と MCP のツール（9）で読み書きし、端末に置いて使うものではないので、差分同期には載せない（変更番号を振らない）

### タグと記事のタグ

4. **タグは人ごとに持ち、名前と説明で表す。** 行は ID、ユーザー、名前、照合用の名前、説明、作った時刻、変更番号、消した印を持つ。自動の判定に使うタグのベクトルも、この行に置く（[自動のタグ付け](auto-tagging.md)の 1）。ベクトルを書くときは、変更番号を振らない（同期で配る項目が変わらないため）。
   - 名前と説明は、前後の空白を除いてから測る。名前は 1〜64 コードポイント、説明は 0〜140 コードポイント。名前が空、上限を超える、制御文字か対になっていないサロゲートを含む、のどれかなら 400。上限ちょうどは受ける（[ワークスペース](workspaces.md)の名前と同じ扱い）
   - 照合用の名前は、まとめの鍵と同じ作り方。名前を打って作るタグは、版を付けてもよい（`Python 3.13` と `Python` は別のタグにできる。候補には、例外の一覧の語を除いて版の付いた語は出ない）
   - 有効なタグは 1 人 100 個まで。同じ人で照合用の名前が同じ有効なタグは 1 つにし（部分一意索引）、上限は作る文の中で数える（[通知](notifications.md)の 3 と同じ形。入らなければ読み直し、どの理由にも当たらなければ 1 回だけ流し直す決まりも同じ）
   - 説明は、`Go` のように短く紛らわしい名前の意味を決めるのに使う（「プログラミング言語の Go」）
5. **記事のタグは、タグと記事の組ごとに 1 行持つ。** 行は ID、タグの ID、ユーザー、記事の ID、付け方（`auto` ／ `manual`）、付いているかどうか、変更番号、消した印を持つ。タグと記事の組は一意。印は行の ID で付ける。
   - 見える状態は、自動で付いた ／ 手で付けた ／ 手で外した の 3 つ。どれでもない組は、行がないか、消した印が付いている
   - 自動で付ける・外すのは[自動のタグ付け](auto-tagging.md)の仕事で、消した印のない手で付け外しした行（`manual`）は変えない
   - 有効な記事のタグを作る文と、消した印の行を生き返らせる文は、書くのが誰であっても（手の付け外しの API でも、自動のタグ付けの仕事でも）、タグが本人の有効なタグであることと、記事が本人の受信箱にあることを、同じ文の中で確かめる。確かめずに書くと、受信箱の行やタグが消えてトリガーが動いたあとに、有効な行が残ってしまう
   - 変更番号を振るのは、見える状態が変わったときだけにする
   - タグを消すと、そのタグの記事のタグのうち消した印のない行に、表に付けたトリガーが同じ文の中で、消した印と新しい変更番号を付ける
   - 受信箱の行が消えたら、消えた行のユーザーと記事の ID で絞った記事のタグのうち、消した印のない行に、表に付けたトリガーが同じ文の中で、消した印と新しい変更番号を付ける（手で付け外ししたものも）。記事の行への外部キーで連鎖させない（消した印を 30 日残すため）。同じ記事が受信箱に入り直しても、前の手直しは戻さない
6. **REST API で、候補とタグを扱う。** 入口は `/api/v1` の下で、形はベルにそろえる（[通知](notifications.md)の 5）。タグは `id`、`name`、`description`、`createdAt` を返す。記事のタグは `id`、`tagId`、`articleId`、`kind`（`auto` ／ `manual`）、`on` を返す。
   - `GET /tags`：有効なタグを作った順の `items` と、判定し直しの残りの記事の数 `rejudgeRemaining`（[自動のタグ付け](auto-tagging.md)の 6）を、`{ items, rejudgeRemaining }` で返す
   - `POST /tags`：`{ id?, name, description? }` で作る。候補から選ぶときも、名前を打つときも同じ。`id` を省くとサーバーが決め、オフラインで作るクライアントは小文字の UUID を指定できる。新しく作ったら 201、同じ照合用の名前の有効なタグがあれば、送った `id`・説明・上限によらずそのタグを 200 で返す（どちらも `{ tag }`）。クライアントは応答の `id` を正とする（オフラインで作ったタグが既存のタグにまとめられたら、手元の ID を置き換える）。有効なタグが 100 個あれば 409（`tag_limit_reached`）、指定した `id` がほかの行に使われていれば 409（`tag_id_taken`）。重なったら、400、同じ照合用の名前の有効なタグ（200）、`tag_limit_reached`、`tag_id_taken` の順に、先のものを返す
   - `PATCH /tags/{id}`：名前と説明を変えて `{ tag }` を返す。変えた照合用の名前がほかの有効なタグと同じなら 409（`tag_name_taken`）。同じ文の中で確かめる。本人の有効なタグがなければ 404
   - `DELETE /tags/{id}`：消した印と新しい変更番号を付けて 204。本人が消したタグの再送も 204。本人のタグがなければ 404
   - `GET /tags/candidates`（1）：`{ items: [{ key, label, count }], pending }` で返す。`label` は見出し、`count` は記事の数、`pending` は集計中の残りの記事の数。`GET /tags/rejections`（`{ items: [{ key, rejectedAt }] }`）、`POST /tags/rejections`（`{ key }` で却下し、200 と `{ created }`。却下済みなら `created: false`）、`POST /tags/rejections/restore`（`{ key }` で戻し、200 と `{ restored }`。却下していなければ `restored: false`）（3）。鍵は任意の文字を含みうるので、パスに入れない
   - `PUT /articles/{id}/tags/{tagId}`：`{ on: true | false }` で手で付け外しし、`{ articleTag }` を返す。同じ状態の再送も同じ応答
   - `DELETE /articles/{id}/tags/{tagId}`：手直しを取り消し、自動に戻して 204。変えるのは手で付け外しした（`manual` で消した印のない）行だけで、付け方を `auto` に戻し、消した印と新しい変更番号を付ける。自動のタグ付けが判定し直すまでは、付いていないものとして見える（取り消した記事は判定待ちの表に積まれ、自動のタグ付けが判定し直す。[自動のタグ付け](auto-tagging.md)の 5）。それ以外の行と、行がないときは何も変えずに 204（下の 404 の確かめが先）
   - 手の付け外しと取り消しは、本人の有効なタグであることと、記事が本人の受信箱にあることを、書く文の中で確かめる。どちらかが違えば、記事がないときと同じ 404 にする（ほかの人の受信箱にある記事かどうかを漏らさない）
   - `GET /articles` に `tagId` の絞り込みを足す（自動で付いた・手で付けた記事だけ）。`tagId` に本人の有効なタグがなければ 404。記事の項目には、その人の記事のタグ（手で外したものも）を付ける
7. **タグと記事のタグは、差分同期で配る**（[差分同期](sync.md)の 13）。`includeTags=true` を指定したクライアントに、`tags` と `articleTags` で、有効な行（6 の項目と `deleted: false`）と消した印（`id` と `deleted: true`）を返す。手で外した行も有効な行として配る。番号とページ送り（番号と行の ID の順）はそれぞれの表で独立させる。
   - タグの位置を持たないカーソルでは、最初の同期と同じに扱う（[通知](notifications.md)の 4 と同じ形）。タグは番号 0 から送る。記事のタグは、受信箱の最初の同期と同じ範囲（[差分同期](sync.md)の 4）の記事の分だけを送る。2 回目からの差分は、範囲によらず送る
   - そのため、手元にある古い記事（すでに同期していた端末が、あとからタグを求めた場合など）や、最初の同期の途中で範囲を出た記事の記事のタグは、届かないことがある。クライアントは、`GET /articles` で記事と一緒に受けて補う（6）。タグで絞った一覧は、`GET /articles?tagId` の結果を正とする。手元にない記事の行は、クライアントが持っていてよい
   - 消した印の行は、30 日たったら 1 日 1 回の片付けで消し、回収した番号を記録する。行が物理的に消えたら、表に付けたトリガーが番号の下限を記録する（[差分同期](sync.md)の 1）
8. **記事のタグは、保存容量に含める**（[保存容量と古い記事の片付け](retention.md)の 2）。手の付け外しは、受信箱の行と同じく、容量の上限では断らない（人の操作を、共有の容量で失敗させない）。自動で書く行は、容量の片付けを起こさない範囲で書く（[自動のタグ付け](auto-tagging.md)の 7）。記事を消しても記事のタグは消した印として 30 日残るので、容量による片付けの削除の見積もりには含めない。タグの行と却下の行は、件数の上限があり小さいので、容量に含めない。

### MCP のツール

9. **候補の一覧と却下を、MCP のツールでも扱う**（[MCP サーバー](mcp.md)の 12）。中身と決まりは 1〜3 と同じ。エージェントに「この語はもう出さないで」と頼めば、却下で停止語を足せる。

### 範囲外

- LLM でタグを付けること、候補をそのまま記事のタグにすること
- タグの階層、人どうしでのタグの共有
- タグと記事のタグの MCP のツール（使い道が決まったときに足す）
- 言葉や正規表現のルールで付けるタグ（[機能の一覧](../features.md)の「フィルタとルール」）との関係。ルールを作るときに決める

## 理由

- **候補は語で作り、タグはベクトルで付ける。** 2 つの段は、することが違う。
  - 候補は「名前」を出す段。人が見て選ぶには語が要るが、ベクトルには名前がない。ベクトルから候補を作るには、記事をクラスタリングし、まとまりに名前を付ける段（語の抽出か LLM）が要り、結局は語が要るうえに重い。
  - 候補を出す段には、比べる相手がない。ベクトルの近さは「何に近いか」が決まって初めて使える。タグができると、そのタグが相手になる。
  - 候補に要るのは正確さ。記事に実際に出てくる語なら、件数をそのまま数えられ、しきい値で件数が変わらない。間違った語は人が選ばないだけで済む。タグに要るのは取りこぼしのなさ。タグは自動で付き、人は全部の記事を見られないので、語が出てこない関連する記事まで意味で広げて拾う必要がある。
- **候補の質を、人が選ぶ一段で補う。** 記事から語を抜くだけだと、語の数が多く散らかる。候補は「出すだけ」にすれば、軽い抜き方でも間違いは選ばれないだけで済み、記事に付くのは人が選んだタグだけになる。
- **候補には版の付いた語を出さない（例外の一覧の語を除く）。** 版は記事の解析で捨てる（[記事の解析](article-analysis.md)の 9）。`Java 21` だけを追いたい人は、名前を打てばタグにできる。
- **フィードの偏りで下げない。** はてなブックマークや Lobsters のように、1 つのフィードにいろいろな記事が入るものがある。そこで多く出る語は、その人にとって数えたい語。
- **フィードの定型の語は除く。** 実際の記事では、共有ボタン、広告、署名、サイト名が、候補の上位を占めた（[記事の解析](article-analysis.md)の「計測の結果」）。こうした語は、同じフィードのほとんどの記事に出る。寄せ集めのフィードの話題の語が、同じフィードの半分以上の記事に出ることはまずないので、偏りで下げるのとは違い、数えたい語はほとんど削られない。話題を絞ったフィードの話題の語はカテゴリとして出ることが多いので、カテゴリの候補はこの決まりから外す。それでも本文の語が 50% を超える話題の語は、そのフィードからは数えない（受け入れる。ほかのフィードからは数える）。分母を解析済みの記事にするのは、遡及の途中で割合が下がって部品が漏れないようにするため。30% にすると、話題を絞ったフィードの話題の語（AI 専門のフィードの `AI` など）まで削った。
- **集計は別のスレッドで流し、結果を 1 分使い回す。** 集計は、受信箱の大きい利用者（30 日の範囲の記事 7,234 件、候補の行 21 万 6 千行）で、配備（arm64）で、集計で持つ 200 件の形で数回測って、1 回 中央値 920〜968ms・p95 955〜985ms かかった。libsql は Promise の API でも中では文を同期で動かすので、主のスレッドで流すと、その間ほかの API、差分同期、仕事が止まり、繰り返し呼ばれると詰まる。記事が増えれば集計も重くなる。別のスレッドの接続で流せば、主のスレッドは止まらない（[コンテナ版](container.md)の 5）。ただ CPU は使うので、1 人が同時に流す集計を 1 本にし、1 分使い回して、呼ぶ回数によらず 1 人が集計に使うのを 1 分に 1 回までにする。候補は 30 日の範囲で数えるのでゆっくりしか変わらず、1 分遅れても困らない。タグと却下は返すたびに外し直すので、停止語を続けて却下しても集計し直さず、却下と戻しを交互に呼んで使い回しを避けることもできない。
- **集計の時間に目安を置かない。** 別のスレッドで流すので、集計が重くなっても、遅れるのは候補の一覧の応答（1 人 1 分に 1 回の集計）だけで、ほかの API は止まらない（読み取りが長くなったときの WAL と別のスレッドの埋まり方は、[コンテナ版](container.md)の見直す条件で見る）。候補の一覧はタグを選ぶときにたまに開く画面で、自分で動かす 1 人の使い方なら、数秒かかっても困らない。困るのは、集計が主のスレッドに響いたときと、何人もで共用して別のスレッドの順番待ちが増えたときなので、それを見直す条件にする。
- **直近 30 日で数え、公開日時でも区切る。** いま増えている話題が上に来る。全期間だと、昔よく出た語が居座る。受信箱に入った時刻だけで区切ると、移行で一度に入った「あとで読む」の 2,173 件が、30 日のあいだ一覧を占めた。
- **停止語は却下で扱い、MCP でも直せるようにする。** 一般的すぎる語は、記事の集まりと人によって違う。却下なら、DB の中で、画面からもエージェントからもすぐに直せる。仕組みを停止語と却下の 2 つに分けずに済む。
- **却下を持ち、戻せるようにする。** 却下がないと、選ばなかった語が上位に居座り、一覧が使えなくなる。気が変わることもあるので、戻せるようにする。管理画面と MCP で使い、端末に置いて使うものではないので、同期の仕組みに載せない。
- **記事のタグの行に自分の ID を持たせる。** タグを消すと、そのタグの全部の記事に同じ番号が付き、受信箱の行が消えると、その記事の全部のタグに同じ番号が付く。行の ID で順を決めれば、同じ番号の中でページが切れても取りこぼさない。消した印も、ほかの表と同じ `{ id, deleted }` の形で伝えられる。
- **記事のタグを記事の行と連鎖させない。** 連鎖で消すと、消した印が 30 日を待たずに消え、同期で伝わらないか、片付けのたびにカーソルが古くなる（[差分同期](sync.md)の 3）。受信箱の消した記録と同じく、記事の ID だけを持つ。
- **変更番号は見える状態が変わったときだけ振り、最初の同期は受信箱と同じ範囲に絞る。** 自動の判定し直しのたびに全部の行の番号が変わると、受信箱の全件分が同期で流れる。受信箱の全部に付いた記事のタグを最初の同期で送ると、最初の同期を軽くした意味がなくなる。欠けうる分は、記事を読むときに `GET /articles` で補える。2 回目からの差分の量は、5（見える状態が変わったときだけ番号を振る）と[自動のタグ付け](auto-tagging.md)の 6（ベクトルの変わったタグだけを判定し直す）で抑える。

## 検討した代替案

- **候補もベクトルから作る**（記事をクラスタリングし、まとまりに名前を付ける）：語が出てこない話題のまとまりも見つかるが、名前を付けるのに結局は語の抽出か LLM が要り、重い。件数もクラスタリングの切り方で変わる。
- **候補をそのまま記事のタグにする**：手間はないが、語が多く散らかり、表記の揺れもそのまま残る。
- **LLM で記事ごとにタグを付ける**：品質は高いが、費用がかかり、バッチでは最大 24 時間遅れ、API キーのない人は使えない。
- **何フィードにまたがって出るかで数える**：サイト名や連載名は下がるが、はてなブックマークのようなフィードの語も下がる。
- **記事のタグを最初の同期でも絞らずに送る**：手元の記事のタグが欠けないが、受信箱の全部の分が流れる。
- **主のスレッドで集計し、結果を使い回すだけにする**：スレッドを足さずに済むが、集計する 1 回ごとに主のスレッドが止まり、記事や利用者が増えると止まる時間も伸びる。
- **呼びすぎたら 429 を返す**：止まる時間に上限は付くが、画面を開き直したときや却下のあとの読み直しのような普通の使い方でもエラーになり、使い回せば済む場面を失敗にする。
- **候補の数を前もって数えて保存しておく**（利用者・フィード・鍵ごとの数を、受信箱の行の出入り、解析の世代の入れ替わり、30 日の範囲から出る記事のたびに足し引きする）：一覧は数 ms になるが、配信のたびに受信者の数 × 記事あたり数十行の書き込みと容量が増え、範囲から出た記事の数を引く仕事や、数がずれたときの直し方も要る。定期の仕事でまとめて数える形は、仕事も同じ接続を使うので、止まるのは変わらない。
- **共有の停止語の表を DB に持つ**：全員にまとめて効くが、人ごとの却下と仕組みが 2 つになり、誰が直してよいかも決める必要がある。

## 見直す条件

- 表記の違う同じ意味の語（`JS` と `JavaScript`）が、候補に別々に出て邪魔なとき。語の埋め込みの近さで、まとめの候補を出すことを考える。
- 候補の一覧の集計が、主のスレッドに影響を及ぼしたとき（ほかの API、同期、仕事の応答が遅れるなど）、または 1 つの Sendo を 5 人以上で共用するようになったとき。候補の数を前もって数えて保存しておくか、数える記事の数に上限を置く。
- タグを作っては消すことで、消した印の記事のタグが保存容量を目に見えて押し上げるとき。
- 却下しても一般的な語が次々に出て、却下の手間が大きいとき。初めから入れておく共有の停止語を考える。
- フィードの定型の語の 50% が、部品を残しすぎるか、話題の語を削りすぎるとき。
