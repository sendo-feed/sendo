# 記事の翻訳

- 状態：提案中
- 関連：[記事の言語判定](article-language.md)、[記事の本文](content.md)、[差分同期](sync.md)、[仕事の流し方](jobs.md)、[保存容量と古い記事の片付け](retention.md)、[コンテナ版](container.md)、[Discord チャンネルの購読](discord.md)

日本語以外の記事を、Claude API（Anthropic の Claude Platform）で日本語に訳す。訳す先は日本語だけ。訳文は reader に配り、MCP、Google Reader API、REST の記事一覧では返さない。同じ元記事が届いたら、訳を写して使い回し、同じ原文をなるべく重ねて訳さない。モデルと思考量は段階（通常 ／ 長文 ／ 品質優先）ごとに設定で選び、訳したときの条件を行に残して、モデルと思考量を読む人にも見せる。

## 決定

### 何を訳すか

1. **記事ごとに 1 回だけ、訳すかどうかを決めて、訳文の行を作る。** 行のある記事は、二度と決め直さない（判定の版を上げて判定し直しても）。
   - 決めるのは、記事の言語の判定が、フィードの本文（なければタイトル・要約）とページの本文の両方で済んだとき（ページを抜けなかった記事と URL のない記事は、フィードの本文かタイトル・要約の判定のあと）。または、取り込んでから 1 時間たって、少なくとも 1 つの入力元の判定が済んだとき
   - 主言語は、[記事の言語判定](article-language.md)の結果のうち、状態が `detected` か `provisional` のものを、入力元 `page`、`feed`、`metadata` の順に探して使う
   - 主言語が日本語でなければ `queued`（4 で自動で訳す）。判定はあるが使える結果がなければ（どれも `und`）、`untranslated`（求めたときだけ訳す）。日本語なら `skipped`（配らず、訳さない）
   - 決めるのは、API キーがあり（15）、取り込んでから 1 日以内で、誰かの受信箱にある記事だけ。1 日たっても判定のない記事と、それより前に取り込んだ記事には、行を作らず、訳さない
   - 決める仕事は、その記事の言語の判定を保存したときと、ページを抜けなかったと記録したとき（[記事の本文](content.md)の 14）に、その記事について積む（[仕事の流し方](jobs.md)の 13）。5 分おきの定期実行も、まだ決めていない記事を拾って決める（抜けなかったことを記録できなかった記事は、取り込んでから 1 時間たってから）。同じ記事の仕事が重なっても、行を作る文の中でまだ行がないことを確かめるので、1 回しか作らない。容量が足りず行を作れなかった記事は、取り込んでから 1 日のあいだ、定期実行がまた試す
2. **Discord の投稿は訳さない。** 行を作らず、外へ送らない（[Discord チャンネルの購読](discord.md)）。ほかのフィードは、公開かどうかを見分けずに対象にする。
3. **訳すのは、タイトル、要約、本文。** 本文は、訳すときにページの本文が抜けていればそれ（[記事の本文](content.md)の 10）、なければフィードの本文（同じく 1）。訳し直しで本文を選ぶ決まりは 6。
   - 本文がない記事、本文から送る文（10 の断片）の合計が 60,000 文字（Unicode の文字）を超える記事、訳した本文をサニタイズして 256KB を超える記事は、本文を置かず、タイトルと要約だけを訳す
   - 訳したあとでページの本文が抜けても、訳し直さない

### いつ訳すか

4. **`queued` の記事は、Message Batches API でまとめて訳す。** 5 分おきの定期実行で、次を行う。
   - 送る：`queued` で印のない行を 100 件まで、同じ文で送る印（このバッチの印と時刻）を付けて取り、1 つのバッチにして送る。同じ元記事の訳を写せる部分は送らずに結果を書く文で写し、すべて写せる行は送らない。同じ元記事の行がバッチの中にある行は取らない（16）。`custom_id` は記事の ID。送れたらバッチの ID を書き留める。印を付けてから 1 時間たってもバッチの ID がない行は、印を外して待ちに戻す（バッチを作った直後に落ちると 2 回払うことがあるが、受け入れる）
   - 見にいく：バッチの ID のある印を、古い順に 10 個まで見にいく。見にいけなかったとき（時間切れ、5xx）は印を残し、次の定期実行で見直す。終わっていれば結果を書く
   - 結果を書く文の中で、記事があること、行がそのバッチの印を持ち、まだ訳文がないことを確かめる。合わなければ捨てる。訳文を書いたら印を外す
   - `errored` ／ `expired` ／ `canceled` の記事と、もう見られない（404）バッチの記事は、同じ文で印を確かめて外し、回数を 8 のとおり数える。行が `queued` なら待ちのままにし、3 回目も訳せなかった記事と、拒否（`refusal`）された記事は `untranslated` にする。行が `translating`（その場の翻訳の最中）なら、状態と始めた時刻は変えない
   - 送る印を付けたが、写せるもの（16）もなく、訳すもの（タイトル、要約、本文）もない記事は、送らずに印を外して `untranslated` にする
5. **`queued` か `untranslated` の記事は、読む人が求めたときだけ、その場で訳す。** 開いただけでは訳さない。
   - 求めを受けたら、同じ文で、状態を確かめて `translating` にし、始めた時刻を書く。それから仕事を積み、202 を返す。訳し終えたことは差分同期で届ける（[差分同期](sync.md)の 10）
   - 同じ元記事の訳を写せる部分は送らずに結果を書く文で写し、残りだけを送る。すべて写せたら呼ばない（16）
   - 通常の Messages API にストリーミングで送る。代わりのモデルのあるモデル（9）なら、拒否されたときは、拒否の種類に応じて Anthropic が選ぶ代わりのモデルで訳させる（server-side fallbacks。バッチでは使えない）
   - 呼ぶ前と結果を書く文の中で、行が `translating` で、始めた時刻が仕事を積んだときのものと同じことを確かめる。合わなければ、呼ばずに（書かずに）やめる
   - 訳せたら、同じ文でバッチの印を外して `translated` にする。訳せなければ `untranslated` にする。`untranslated` の記事は、求めればまた訳す
6. **`translated` の記事は、読む人の求めで、1 回だけ品質優先の段階（9）で訳し直す。** 訳し直したかどうかの印を行に持ち、印のある記事は訳し直さない。
   - 求めを受けたら、同じ文で、`translated` で印のないことを確かめて `translating` にし、始めた時刻を書く。もとの訳文は、訳し直した訳文が入るまで残す。呼ぶ前と書くときに 5 と同じく確かめる
   - 訳し直した訳文で全員分を置き換え、印を付けて `translated` に戻す。同じ元記事のほかの記事にも、置き換えられるものに写す（16）。失敗したら、もとの訳文のまま `translated` に戻す（印は付けない）
   - もとの訳文に本文があれば、同じ出どころ（`feed` ／ `page`）の本文を訳し直す。それでも 3 で本文を置かない条件に当たる（本文がない、送る文が 60,000 文字を超える、組み立てた本文が 256KB を超える）ときは失敗にする。仕事の中で、呼ぶ前に分かれば呼ばず、受け取ったあとで分かれば呼び直さない（8）
   - もとの訳文に本文がなければ、3 のとおりに本文を選ぶ。本文を置けなくても失敗にせず、タイトルと要約だけを訳し直す
7. **止まった `translating` は戻す。** 5 分おきの定期実行が、始めてから 1 時間を過ぎた `translating` を、訳文があれば `translated`、なければ `untranslated` に戻す。1 時間は、その場の翻訳の仕事が生きうる長さ（9 の 10 分を 3 回と、借りの期限）より長い。キーがなくても戻す。
8. **待てば通る失敗は回数に数えず、その場の翻訳では、やり直しても通らない失敗をやり直さない。**
   - バッチの回数は、結果が返った記事について数える。`errored` のうち一時的な種類（429、529、5xx の `api_error` ／ `overloaded_error`）と、9 でモデルを外すときの要求の形の誤りは数えない。`expired` ／ `canceled` と、もう見られないバッチ（4 の 404）は数える
   - バッチでは、容量の不足（12）、認証の失敗、利用上限のとき、送らずに待ちのまま次の定期実行に回す
   - その場の翻訳と訳し直しでは、[仕事の流し方](jobs.md)の 5 のとおり合わせて 3 回まで呼び、それでも通らなければ 5、6 の失敗にする
   - ただし、やり直しても通らない失敗は、受けたその回で 5、6 の失敗にする。要求の形の誤り（400）、認証の失敗（401）、権限の不足（403）、モデルの名前の誤り（404）、代わりのモデル（5）でも拒否されたもの、代わりのモデルのないモデルで拒否されたもの、上限で切れた応答と読めない応答（9）、訳し直しで本文を置けないもの（6）。400 は、これとは別に、9 でモデルを外すかの判断にも数える

### どう訳すか

9. **モデルと思考量（`effort`）は、段階ごとに決める。既定は、通常が最新の Sonnet・`medium`、長文が最新の Haiku・`low`、品質優先が最新の Opus・`medium`。**
   - 段階は 3 つ。訳し直し（6）は品質優先の段階。自動の翻訳（4）のうち、送る本文（10 の断片。3 と同じ数え方で、タイトルと要約と、16 で写す本文は数えない。本文を送らない記事は 0 文字）の合計が閾値以上の記事は長文の段階。そのほか（その場の翻訳（5）と、閾値より短い自動の翻訳）は通常の段階。その場の翻訳は、長くても通常の段階にする
   - 環境変数で変えられる。通常は `TRANSLATION_MODEL` ／ `TRANSLATION_EFFORT`、長文は `TRANSLATION_LONG_MODEL` ／ `TRANSLATION_LONG_EFFORT` ／ `TRANSLATION_LONG_THRESHOLD_CHARS`、品質優先は `RETRANSLATION_MODEL` ／ `RETRANSLATION_EFFORT`（[コンテナ版](container.md)の 11）
   - モデルは、系列の名前（`sonnet` ／ `haiku` ／ `opus`）か、モデルの ID で書く。`claude-` で始まる値はモデルの ID で、そのモデルに固定する。それ以外は系列の名前（大文字と小文字は区別しない）で、その系列の最新を選ぶ（下）。思考量は `low` ／ `medium` ／ `high` ／ `xhigh` ／ `max`（大文字と小文字は区別しない）。閾値は 1 から 60,000 までの整数で、既定は 3,000（ちょうど 3,000 文字は長文）。知らない系列の名前、知らない思考量、範囲の外の閾値は、エラーをログに出して、その項目だけ既定で動く。モデルの ID の誤りは、呼んだときの誤り（8）になる
   - 系列の最新は、起動時と 1 日 1 回、Models API で一覧を取り、ID が `claude-sonnet-` ／ `claude-haiku-` ／ `claude-opus-` で始まり、その段階の思考量を受け付ける（一覧の `capabilities` で確かめる）もののうち、作られた日がいちばん新しいものを選ぶ。一覧を取れなければ、前に選んだもの（なければコードの既定）を使う
   - モデルを外す判断はモデルごとに持つ（同じモデルを 2 つの段階で使っても 1 つ）。新しく選んだモデルで、まだ 1 件も訳せていないうちに、そのモデルへの要求の形の誤り（400 の `invalid_request_error`）が続けて 3 件起きたら、プロセスが動いている間はそのモデルを外し、同じ系列の次に新しいもの（その段階の思考量を受け付けるもの）を使う。ログに出す。バッチでは、結果ごとの誤り（`errored`）をその記事のモデルに数え、バッチを作るときの誤りは、そのバッチのモデルが 1 つのときだけ数える
   - 版が変わっても通るよう、要求に使う指定を絞る。`thinking`、サンプリング（`temperature` など）、ツールの強制は指定しない。考える量は段階の思考量を `effort` に渡し、出力の形は structured outputs で決める
   - バッチでは、1 つのバッチの中で記事ごとに段階のモデルと思考量を指定する（長文と通常の記事を同じバッチで送る）。送る印を付けるとき（4）に、送った条件（段階・思考量・プロンプトの版）を、配る条件（18）とは別に行に書き、結果を書く文で 18 の条件に写す（送ってから結果が返るまでに設定やプロンプトが変わっても、送った条件を残す）。送った条件は、送る印と一緒に外す（待ちに戻すときも消す）
   - 拒否のときの代わりのモデル（5 の server-side fallbacks）は、代わりのモデルのあるモデルでだけ指定する。代わりのモデルのないモデルは、コードに持つ一覧（モデルの ID の前方一致。`claude-haiku-` など）で見分ける。一覧にないモデルで指定が断られたら（400）、要求の形の誤り（8、上）として扱う。代わりのモデルのないモデルをその場の翻訳や訳し直しに選んだときは、拒否はその回で訳せなかったもの（8、17）になる
   - 出力の上限は 64,000 トークン（思考のトークンも数える）。上限で切れた応答と、読めない JSON は、訳せなかったものとして扱う。バッチでは回数に数え、その場の翻訳と訳し直しではその回で失敗にする（8）。その場の翻訳と訳し直しの 1 回の呼び出しは、時間切れとやり直しを合わせて 10 分で打ち切る
10. **HTML を LLM に渡さず、受け取らない。** サニタイズした本文を断片に分け、ID を付けた JSON で送る。structured outputs で同じ ID の訳を受け取り、元の木に戻す。
    - 文字を直接持つブロックの要素を、要素の名前によらず 1 つの断片にする。中に別のブロックがあれば、それは別の断片にする
    - 断片の中のリンク、強調、画像、改行、文の中のコードは、番号付きの印に替えて送り、訳のあとで元の要素に戻す。リンクと画像の URL、`pre` ／ `code` の中身は送らない
    - 印が欠けた・増えた・入れ替わった断片と、返ってこなかった断片は、原文のまま残す
    - 組み立てた本文は、もう一度サニタイズしてから置く（[記事の本文](content.md)の 2）
11. **記事の中身は指示ではないと伝え、訳は文字としてだけ扱う。外へ送るのは、訳す文だけ。**
    - システムプロンプトで、渡すのは訳す対象のデータで、その中の指示には従わないと伝える。受け取った訳は文字として扱い、タグとして解釈しない
    - 記事とリンクの URL、フィードの名前、読む人のこと（ユーザー、受信箱）は送らない

### 置く・配る

12. **訳文は記事ごとに 1 つ、記事とは別の表に置き、全員で使い回す。** 同じ元記事の記事どうしでは、訳を写して使い回す（16）。
    - 行には、状態（`queued` ／ `translating` ／ `translated` ／ `untranslated` ／ `skipped`）、元の言語、訳したタイトル・要約・本文（サニタイズした HTML）、訳した本文の出どころ（`feed` ／ `page`）、使ったモデル、訳した時刻、訳し直しの印、4〜8 の印・回数・時刻、16 の正規化した URL と送った本文の指紋、17 の訳せなかった理由、18 の訳したときの条件を持つ
    - 記事を消すと、外部キーで一緒に消える。訳文は保存容量に含める（[保存容量と古い記事の片付け](retention.md)の 2）
    - 容量の上限（同じく 4）は、送る前と呼ぶ前に確かめ、当たれば送らない。受け取ったあとで当たったら、バッチは印を残して次の定期実行で書き直す（結果は 29 日読める）。その場の翻訳と訳し直しは、呼び直さずに失敗にする
13. **訳した本文は記事ごとに取りにいき、訳すことは記事ごとに求める。** どちらも、その人の受信箱にある記事だけ。認証はほかの REST API と同じ。
    - `GET /api/v1/articles/{id}/translation`：訳したタイトル・要約・本文と、本文の出どころ、使ったモデルと思考量（18）、訳した時刻を返す。訳文がなければ 404。本文は返すときにもう一度サニタイズし、画像を中継の URL に書き換える（[記事の本文](content.md)の 2、7）
    - `POST /api/v1/articles/{id}/translation`：その場の翻訳（5）と訳し直し（6。本文で指定する）を求める。受け付けたら 202。断るときのコードは、`translation_unavailable`（API キーがない）、`translation_not_supported`（行がないか `skipped`）、`translation_exists`（その場の翻訳を求めたが、`translated` か `translating`）、`retranslation_not_allowed`（訳し直しを求めたが、`translated` でないか、訳し直したあと）
14. **元の言語、翻訳の状態、訳したタイトル・要約、訳し直しの印、訳した時刻、訳せなかった理由（17）、訳したときのモデルと思考量（18）は、差分同期で配る**（[差分同期](sync.md)の 10）。行のない記事と `skipped` の記事には付けない。読む人の画面は、訳した時刻が変わったら、手元の訳した本文を取り直す。

### 動かす条件

15. **API キーがあるときだけ、行を作り、外へ送る。** キーは環境変数 `ANTHROPIC_API_KEY` で受ける（[コンテナ版](container.md)の 11）。
    - キーがなければ、1 で行を作らない。行がなければ状態も配らないので、読む人の画面は翻訳の表示と操作を出さない。機能の有無を返す API は持たない（[コンテナ版](container.md)の 3）
    - キーを外したあとも、作った行と訳文は残る。残った行への求めは `translation_unavailable` で断り、バッチは送らず、見にいかない。`queued` の記事は、キーを戻すまで待ちのまま
    - キーをログ、応答、エラーの表示に出さない
    - 費用の上限は、アプリでは持たず、Claude Platform の利用上限で決める

### 同じ元記事で使い回す

16. **同じ元記事（正規化した URL が同じ）の記事どうしで、訳を写して使い回し、同じ原文をなるべく重ねて送らない。** 訳文の行は記事ごとのまま（12）で、使い回す訳を、その記事の行に写す。フィードが同じか違うかは問わない。
    - 正規化：URL を WHATWG URL として読み、http ／ https のものだけを対象にする。元のスキームの既定のポートを除いてからスキームを `https` にし、ホストを小文字にし、ユーザー情報とフラグメントを除き、パスの末尾の `/` をすべて除く（パスが `/` だけなら残す）。クエリから計測用のパラメータ（名前が `utm_` で始まるもの（大文字と小文字を区別しない）、`fbclid`、`gclid`）を除き、残りの順は保つ。残りがなければ `?` ごと除く
    - 正規化した URL は、1 で行を作るときに行に書く。URL のない記事、http ／ https でない記事、正規化してパスが `/` だけでクエリのない記事（サイトの最初のページ。壊れたフィードで、すべての項目のリンクがそこを指すことがある）は書かず、使い回さない。この決まりより前に作った行も書かず、使い回さない
    - 写す元は、同じ正規化した URL を持つ `translated` の行。訳し直した行を先に、次に訳した時刻の新しい順に選ぶ
    - タイトル：写す元に訳したタイトルがあれば、原文の表記が違っても写す。写す先の原文にタイトルがなければ写さない
    - 要約：写す元のうち、原文の要約の文字が同じ行の訳した要約を写す
    - 本文：写す元のうち、送る本文の指紋が同じで、訳した本文のある行の訳した本文を写す（「本文なし」の記事を除き、指紋が同じでも訳した本文のない行しかなければ、本文は送る）。指紋は、3 で選んだ本文（サニタイズした HTML）の SHA-256 で、本文を送らない記事（本文がない、60,000 文字を超える）は「本文なし」として、訳した（写した）ときに行に書く（12）。訳し直し（6）では、訳し直しで選んだ本文の指紋に書き換える。指紋のない行（この決まりより前に訳した行）は、本文の写す元にも、訳し直しを広げる先（下）にもしない。訳した本文の出どころは、その記事が 3 で選んだものを書く
    - いつ写すか：送る前（4 のバッチ、5 のその場の翻訳）に、写せるものと送るものを分け、送るものだけを送る。写す分は、結果を書く文（4、5 と同じ条件を確かめる文）の中で、写す元をその文の中で選び直して一緒に書く。送る前には行に書かない。その文のときに写す元がなくなっていたら、訳したタイトル・要約は原文の文字を書き、訳した本文は置かない（10 の、返ってこなかった断片と同じく原文のまま読む。本文を写すと決めて送らなかった記事では、本文の訳がないまま `translated` になることを、まれとして受け入れる）
    - すべて写せる行は送らない。バッチでは、印を付けて取った行のうち、すべて写せる行は、印を外して `translated` にする文の中で写し、空のバッチは作らない。その場の翻訳では呼ばずに、5 の結果を書く文の中で写す。どちらも、その文の中で写す元がなくなっていたら書かない。バッチでは印を外して待ちに戻し、その場の翻訳では写さずに送り直す
    - 写した行の訳した時刻は、書いた時刻にする。使ったモデルは、18 の代表の部分を訳した（写した）ものにする。送って訳したならそのモデル、写したなら写した元の行のモデル。本文（本文がなければタイトル）を訳し直した行から写したら、訳し直しの印も付ける。写した訳文では、1 つの訳文の中で部分ごとにモデルが混ざりうることを受け入れる
    - バッチは待つ：同じ正規化した URL の行がバッチの印を持っている間（結果を書けるまで）は、その記事をバッチで送らない。同じ定期実行でも、同じ正規化した URL の行は 1 つだけを、バッチで訳せなかった回数（8）の少ない順、次に決めた順で取る（訳せずに待ちに戻った行より、待っていた行を先に送る）。どちらも送る行を取る文の中で確かめる。先の行の訳文が書けたら、次の定期実行で写す（残りがあれば送る）。すべて写せる行も、送る行と同じく待つ。その場の翻訳の最中の行（バッチの印がない）は、待つ理由にしない
    - その場の翻訳は待たない（読む人が待っているため）。写せるものを写し、残りを呼ぶ。同じ元記事がバッチの中にあれば、2 回払うことがある
    - 訳し直し（6）：訳し直した行を書いたあと、同じ正規化した URL で、本文の指紋が同じ（どちらも「本文なし」を含む）`translated` で訳し直しの印のない行に、訳し直したタイトルと本文を写し、要約の文字が同じ行には要約も写して、訳した時刻・使ったモデル・18 の条件（思考量、段階、プロンプトの版）・訳し直しの印を、写す元と同じにする。ただし、本文（本文がなければタイトル）を置き換えられない行には写さず、印も付けない。写す先に訳した本文があるのに写す元に訳し直した本文がない（6 で本文を置けなかった）行と、両方に本文がなく、タイトルも写せない（上のタイトルの項）行がそれにあたる。置き換えられない行は、定期実行でも写す先に選ばない。写さなかった行は、読む人が自分で訳し直せる。1 行ずつ、写す元（訳し直しの印のある行）と写す先の条件を、写す文の中で確かめる。訳し直した直後に写し、5 分おきの定期実行も、写し損ねた行（途中で落ちた、容量に当たった、そのとき `translated` でなかった）に写し直す。`translated` でない行（待ち、バッチの中、その場の翻訳の最中）は、あとで結果を書くときに、訳し直した行を先に選んで写す
    - 写した訳も、その行の訳文として保存容量に数える（12）。容量の上限に当たった行には写さない。送って結果を書くバッチの行は 12 のとおり印を残して次の定期実行で書き直し、すべて写せる行は印を外して待ちに戻し、その場の翻訳は 12 のとおり失敗にする。訳し直しを写す先が上限に当たったら、その行には写さず、次の定期実行でまた試す。元の記事が消えても、写した訳は残る

### 訳せなかった理由

17. **訳そうとして訳せずに `untranslated` にした記事は、訳せなかった理由を行に残し、差分同期で配る**（14）。
    - 理由に持つのは、種類（拒否された（`stop_reason` が `refusal`）か、そのほかの失敗か）、拒否の種類（拒否の応答の `stop_details.category`。`cyber` など。なければ空）、どこで起きたか（バッチか、その場の翻訳か）の 3 つ。`stop_details.explanation`（英語の説明文と URL）は残さず、配らない
    - 書くのは、訳そうとして `untranslated` にしたとき。バッチで拒否された（4）、バッチで 3 回目も訳せなかった（4、8）、その場の翻訳の仕事が訳文なしで終えた（5、8、12、15。拒否を含む。代わりのモデルでも拒否されたときは、その応答の拒否の種類。送るものがなかったときも、そのほかの失敗とする）、止まった `translating` を訳文のないまま戻した（7。その場の翻訳での、そのほかの失敗とする）
    - 書かないのは、言語が判定できずに `untranslated` と決めた行（1）と、訳すものがなく送らずに `untranslated` にした行（4）。どちらも、まだ訳す仕事に入っていない。訳し直し（6）が失敗しても書かない（もとの訳文のまま `translated` に戻る）
    - すでに `untranslated` の行に届いたバッチの拒否・回数切れでは、理由を書き換えない（その場の翻訳の理由を残す）
    - 消すのは、`translated` にしたとき（同じ元記事から写したときも。16）。その場の翻訳を受け付けて `translating` にしている間は、もとの理由を残し（配る状態は `translating`）、結果を書くときに書き換える（訳せたら消し、訳せなければ新しい理由）。受け付けを取り消して `untranslated` に戻したときは、もとの理由のまま
    - 理由は `untranslated` のときだけ意味を持つ（ほかの状態では見ない）
    - 理由は行の見積もり（[保存容量と古い記事の片付け](retention.md)の 2 の 1 行の見積もり）の中に含め、容量の上限で `untranslated` への移りを止めない
    - この決まりより前に `untranslated` になった行には、さかのぼって書かない

### 訳したときの条件

18. **訳文を書いたときに、使ったモデル、思考量、段階、プロンプトの版、使ったトークン数、写した元を行に残す。** あとで品質と費用を確かめるため。モデルと思考量は読む人にも見せる。
    - 条件（モデル、思考量、段階、プロンプトの版）は、訳文の代表の部分（本文、本文がなければタイトル、それもなければ要約）を作ったものにする。送って訳したなら、その呼び出しの条件。モデルは応答が返したモデル（拒否で代わりのモデルに替わったときは、代わりのモデル）、思考量と段階は 9 で選んだもの（バッチは送るときに行に書いたもの）。代表の部分を同じ元記事から写したなら（16）、写した元の行の条件
    - プロンプトの版は、システムプロンプトと送る形（10 の断片と印、structured outputs の形）を変えるたびに上げる、コードに持つ番号
    - トークン数は、訳文を書いた呼び出しの応答の入力と出力のトークン数（代わりのモデルに替わったときは、応答が返す合計）と、その呼び出しのモデル（呼び出しのモデル）を組にして残す。代表の部分を写して、ほかの部分だけを送った行では、呼び出しのモデルは代表の部分のモデルと違うことがある。書いた訳文 1 回分で、やり直して失敗した呼び出し、バッチで送り直した分、訳し直す前の訳の分は入らない。送らずにすべて写した行と、訳し直しを広げた行は 0（呼び出しのモデルは空）
    - 写した元：タイトル、要約、本文のそれぞれについて、同じ元記事から写したなら、写した元の記事の ID を残す（送って訳した部分は空）。写した元の記事があとで消えても、ID は残す。訳し直しを広げたとき（16）は、写した部分に、訳し直した記事の ID を書く
    - 訳文を書く文（4、5、6、16）の中で、訳文と一緒に書く
    - 訳せなかったとき（`untranslated` にした、訳し直しが失敗してもとの訳文に戻した）は、書き換えない（もとの訳文の条件が残る）
    - モデルと思考量は、差分同期で配り（14）、`GET /api/v1/articles/{id}/translation` でも返す。読む人の画面は、訳文のある記事にラベルとして出す。段階、プロンプトの版、トークン数、写した元は配らず、返さない
    - 行の見積もり（[保存容量と古い記事の片付け](retention.md)の 2 の 1 行の見積もり）の中に含める
    - この決まりより前に訳した行は、思考量を `low`（前の決まりではいつも `low` で送っていた）とし、段階、プロンプトの版、トークン数、呼び出しのモデル、写した元は空のまま（写した元が空の行は、送って訳したか、分からない）

### 訳し方

19. **訳文は、日本語の読み物として自然に、原文の意味を変えずに書く。** 決まりはシステムプロンプトに書き、変えたらプロンプトの版（18）を上げる。システムプロンプトでは、断片の ID（`title` はタイトル、`summary` は要約、そのほかは本文で文書の順）と、1 回の要求の断片はすべて 1 つの記事のものであることも伝える。
    - 文体は「だ・である」にそろえる（引用した発言も）。1 回の要求の断片は、すべて同じ文体で訳す。同じ元記事から写した部分（16）とは揃わないことがあり、受け入れる
    - 原文にないものを足さない。人名や役職に敬称（「さん」など）を足さない。原文がぼかしていることを言い切らない（解釈を足さない）。説明や注釈を足さない（下の、人名の読みと概念の名前の意味の括弧を除く）
    - 含意、皮肉、慣用句は、字面ではなく意味で訳す。字面どおりに訳すと、事実を取り違えるため（悪用されて結果として費用を払わされていることを、皮肉で "I am funding …" と書いたものを「出資している」と訳すなど）
    - 人名（ラテン文字で書かれたもの）は原文の表記のまま書き、1 回の要求の中で最初に出たところだけ、後ろに括弧でカタカナの読みを付ける（例：Jensen Huang（ジェンスン・フアン））。広く知られた人名（Trump など）も、原文の表記で書いて読みを付ける。最初に出たところは、要求に本文の断片があれば本文の断片の中で文書の順に最初、なければ要約。タイトルには付けない。ラテン文字以外で書かれた人名は、日本語で広く使われる表記で書き、なければカタカナで書く
    - ふつうの単語が特定の概念を指す名前として使われ、訳語にすると一般の意味と区別できなくなる語（フレームワークの項目名、記事が定義した用語など）は、人名と同じ「最初に出たところ」で「原語（意味）」と書き（例：Diligence（責任を持つこと））、2 回目からは原語で書く。意味は短い訳語にし、説明の文にしない。タイトルには付けない。機能名などの技術用語（prompt caching など）には付けない
    - 会社名、製品名、コードの識別子は、広く使われる日本語の表記がなければ原文のまま書く
    - 日本語の文字と印（10）の間に空白を入れない（表示に余計な空白が出る）。英字どうしの間の空白は、原文のまま残す。人名の読みと概念の名前の意味の括弧は、名前だけを包む印の対（入れ子なら、名前だけを包むいちばん外の対）の後ろに置く（例：⟦1⟧Marcus Borg⟦/1⟧（マーカス・ボルグ））。リンクが名前だけを指すように。対が名前より広い句を包むときは、名前の直後（対の中）に置く
    - もともと日本語の断片は変えない（この決まりも当てない）
    - 最初に出たところの判定は要求の単位なので、次のことは受け入れる：本文を写して要約だけを送る行（16）では、要約にも読みと意味が付き、写した本文と二重になる。本文と要約がある要求で、要約にだけ出る名前には付かない。訳した本文が 256KB を超えて本文を置けない記事（3）や、印が崩れて原文のまま残った断片（10）では、付けた読みと意味が残らない
    - この決まりより前に訳した訳文は、訳し直さない（品質優先で訳し直せば、新しい決まりで訳す）。同じ元記事から写すとき（16）は、写す元のプロンプトの版を問わない（古い版の訳も写る）

## 理由

- **Anthropic の API をそのまま使う**：料金が半分になる Message Batches API と、出力の形を決める structured outputs は、OpenAI 互換の形では使えない。
- **自動はバッチ、その場は求めたときだけ**：日本語以外の記事をすべてバッチで訳す費用は、定価の半分×記事の数。開いた記事だけをその場で訳す費用は、定価×開いた数。開くのが半分より多ければバッチのほうが安く、少なくても、開いたときに訳文がもうあって待たずに読めることを選んだ。その場の翻訳を自動にしないのは、バッチを待てば半額で済む記事にまで定価を払わないため。
- **判定のあとすぐ決める**：外国語の記事に早くラベル（`EN · Queued` など）を出し、読む人が待てば訳されると分かるようにする。決めるのは何度動かしても同じ結果で、外へ送らないので、定期実行を待つ理由が薄い（[仕事の流し方](jobs.md)の理由）。
- **1 回だけ決め、日本語と決めたことも残す**：判定のたびに決め直すと、待ちから外す・もう一度入れる規則が要り、判定の版を上げたときに古い記事の費用が跳ねる。決めた印がないと、あとから届いた判定で決め直してしまう。ページの本文の判定まで待てば、ほとんどの記事は本文の言語で決まる。
- **段階で費用を抑える**：自動の翻訳は、読まない記事の長い本文まで訳すので、費用の大半を占める。Haiku 5.5 は Sonnet 5.5 の 20 分の 1 の料金で、実際の記事で比べると、内容は正しく分かる水準だった（皮肉や含意の訳で差が出る）。短い記事は読まれやすく、品質の差が目立つので通常のモデルで訳す。長い記事を Haiku で訳しても、本文は全文を持てる（あとで日本語のセマンティック検索やタグ付けに使う）。読む人が品質を求めた記事は、訳し直しで良くできる。
- **その場の翻訳は長くても通常の段階**：読む人が求めて押したもので、待ってでも読みたい記事なので、品質を落とさない。ただし、その場の翻訳の最中に届いたバッチの結果（長文の段階）や、同じ元記事から写した訳（16）が入ることは受け入れる。
- **思考量を段階ごとに変える**：翻訳は、1 回で答えを返す変換の仕事で、Anthropic の資料では、この種の仕事は思考量による差が小さい（`medium` は `high` と同じ正確さでより安く、`high` から上で測れるほど良くなった例はない。`low` は数ポイント落とす代わりに費用が 3 分の 1〜半分下がる）。思考のトークンも出力として払い、出力の上限に数える。そこで、通常と品質優先は `medium`（Opus 5.5 は `medium` でも前の版の `high` を上回る）、量の多い長文は `low` にする。品質優先は、思考量ではなくモデルで品質を上げる。残した条件（18）で、あとで実際の数字で見直す。
- **設定で変えられる**：予算や記事の傾向は使う人ごとに違う。既定は決めたうえで、段階ごとのモデル・思考量と閾値を変えられるようにする。系列の名前で書けば、sendo を更新しなくても最新の版を使える。
- **訳したときの条件を残す**：モデル、思考量、プロンプトは、あとで変える。どの条件の訳文かが分からないと、品質の差を確かめられず、書いた訳文の費用も分からない。費用は、トークン数と、それを使った呼び出しのモデルの組で出す（代表の部分を写した行では、訳文の代表のモデルと違う）。行に置けば、訳文と一緒に消え、記事ごとの条件を後から引ける。条件は代表の部分（本文）に合わせる。よくある「タイトルと本文を写して要約だけを送る」行で、送った要約の条件を残すと、本文の訳の条件が隠れるため。写した元を部分ごとに残すのは、部分ごとに元が違うことがあり、写した訳か、その記事のために訳したかを見分けるため。
- **モデルと思考量を読む人に見せる**：同じ記事でも、どのモデルで訳したかで品質が違う。読む人が「Haiku low」と分かれば、品質優先で訳し直すかを決められる。段階やトークン数は、読む人の判断には要らないので見せない。
- **最新のモデルを Models API で選ぶ**：モデルの名前は版ごとに固定で、「最新」を指す別名がない。sendo を更新しなくても新しい版を使える。版によって受け付ける指定が変わるので、要求を絞り、受け付けなければ前の版に戻る。1 件の 400 は記事の中身でも起きるので、まだ 1 件も訳せていないモデルで続いたときだけ外す。
- **HTML を渡さない**：HTML を訳させると、タグが崩れたり、記事に仕込まれた要素が訳に混じって返ったりする。断片と印にすれば、構造は sendo が組み立て、LLM の出力は文字にしかならない。
- **Discord を訳さない**：非公開のチャンネルのことがあり、読む人が知らないうちに外へ送らない。ほかのフィードは公開かどうかを見分けられないので、区別しない。
- **訳文を全員で使い回す**：訳文は読む人によらない。購読者が何人いても、1 つの記事の訳文は 1 つで済む。
- **同じ元記事で使い回す**：Hacker News や Lobsters のようなフィードは、同じ元記事を別々に配る。記事はフィードごとの行なので、記事ごとに訳すと、同じ元記事を何度も訳して払う。本文はどちらも同じ URL のページから抜くので、費用の大半を占める本文を何度も払うことになる。
- **URL で見分け、タイトルは表記が違っても写す**：同じ元記事は、同じ訳したタイトルで読めれば足りる。フィードによるタイトルの表記の差（末尾に CVE の番号を足すなど）は、訳したタイトルには出ないことを受け入れ、タイトルを訳す費用を省く。正規化は、表記の揺れ（スキーム、末尾の `/`、計測用のパラメータ）だけをそろえ、中身が変わりうるクエリは残す。
- **要約と本文は、原文が同じときだけ写す**：要約はフィードごとに中身が違い（コメントの数や、元記事へのリンクだけのものがある）、本文はページを抜いた時刻で変わりうる。原文の違う訳を写すと、原文と訳が食い違う。
- **行に写し、別の表を持たない**：訳文は記事ごとの行のまま、差分同期、取りにいく API、容量の数え方、記事を消したときの後始末を今のまま使える。写した分は容量を重ねて使うが、外へ送る費用より安い。写した訳文では部分ごとにモデルが混ざりうるが、同じ原文を重ねて払わないことを選ぶ。
- **写すのは結果を書く文の中だけ**：送る前に写した部分を書くと、まだ訳し終えていない行に訳文の一部が入り、結果を書く文の「まだ訳文がない」の確かめや、止まった `translating` を戻す決まり（7）とぶつかる。写す元も書く文の中で選び直せば、間に訳し直された訳や消えた記事を取り違えない。
- **指紋を行に持ち、ないものは使わない**：送った本文が分からない行を写す元や広げる先にすると、本文のある訳が本文のない訳で上書きされうる。本文の写す元を訳した本文のある行に限るのも同じ理由で、本文を置けなかった行から写すと、送れば置けたかもしれない本文の訳を持てない。そのため、訳した本文が 256KB を超えて置けなかった本文は、同じ元記事が届くたびに送ることになるが、まれとみて受け入れる。
- **バッチは結果を待ち、その場の翻訳は待たない**：バッチはもともと最大 24 時間かかるので、待っても読む人の待ちは大きく変わらず、本文を 2 回払わない。その場の翻訳は読む人が待っているので、2 回払うことがあっても待たせない。
- **サイトの最初のページは使い回さない**：壊れたフィードでは、すべての項目のリンクが最初のページを指し、別々の記事に同じ訳したタイトルが写ってしまう。
- **訳し直しを同じ元記事に広げる**：同じ原文の訳文は同じであるべきで、1 回の払いで、同じ元記事を読むすべての人の訳文を良くする。広げるのは 1 行ずつで、定期実行が写し損ねた行に写し直すので、途中で落ちたり、容量に当たったり、そのとき訳し終えていなかったりした行にも、あとで届く。本文（本文がなければタイトル）を置き換えられない行に写さないのは、6 と同じく、全員分の訳した本文を消したり、訳し直していない（もとの）本文（本文がなければタイトル）に印を付けて二度と訳し直せなくしたりしないため。
- **本文に上限を置く**：その場の翻訳を、仕事の借りの期限（[仕事の流し方](jobs.md)の 1。15 分）の中で終える。60,000 文字の英文は、訳文がおよそ 2 万トークンで、数分で返る。
- **その場の翻訳は応答を待たせない**：長い記事では訳し終えるまで数分かかり、HTTP の応答として待たせられない。終わりは、ほかの変更と同じく差分同期と通知で届く。
- **訳し直しで訳文を減らさない**：訳し直しは品質を上げるために求めるもので、成功すれば印が付き、二度とできない。本文を置けないまま置き換えると、全員分の訳した本文が消え、もう取り戻せない。失敗にすれば、もとの訳文が残る。出どころを揃えるのは、あとから抜けたページの本文が上限を超えていると、何度求めても失敗するため。受け取ったあとで分かる失敗（256KB を超える）は、求めるたびに払うことになるが、同じ出どころから作ったもとの訳した本文は 256KB に収まっていたので、まれとみて受け入れる。
- **状態を同じ文で移し、始めた時刻で確かめる**：バッチの結果、その場の翻訳、訳し直しは、同じ記事に別々の時刻に書く。もとの状態と印、始めた時刻を書く文の中で確かめれば、遅れて返った結果や、戻したあとに終わった古い仕事が新しい訳文を上書きせず、2 人が同時に求めても 1 回しか払わない。払い済みのバッチの結果は、その場の翻訳の最中でも、まだ訳文がなければ書く。訳文のある行には書かないので、訳し直しを上書きしない。
- **実際の記事で確かめた**：Haiku、Sonnet、Opus に思考量を変えて、この決まりを入れたプロンプトで実際の記事を訳させると、印、文体、敬称、印の前後の空白、読みと意味の添えは、どの組み合わせでもほぼ守られた。2 回目から原語で書く決まりと、注釈を足さない決まりは、Haiku（`low`・`medium`）と Sonnet・`low` が一部破った。長文の段階の既定（Haiku・`low`）でこれらが一部守られないことは、費用を優先して受け入れる（9）。
- **だ・である調にそろえる**：断片ごとに訳すので、1 回の要求の中でも断片によって「だ・である」と「です・ます」が揺れ、読みにくい。ニュースや技術記事が多く、簡潔な「だ・である」が合う。
- **足さず、意味で訳す**：実際の記事を Haiku と Sonnet で訳して比べると、原文にない敬称を足す、ぼかしたことを言い切る、皮肉を字面どおりに訳して事実を取り違える、が見つかった。読む人は訳文だけを読むので、原文の意味を変えるものは誤りになる。
- **人名と概念の名前は、原文を残して読みと意味を添える**：人名をカタカナだけにすると、原文で検索できず、読みの揺れも出る。原文だけでは読めない人もいるので、最初の 1 回だけ読みを添える。技術記事では、ふつうの単語が特定の概念の名前として使われる（Anthropic の 4D フレームワークの Diligence など）。訳語だけにすると、読む人は一般の意味で覚えてしまう。原語を先に書けば、名前だと分かる。最初の 1 回に絞り、技術用語全般には付けないのは、訳文が長くなり出力のトークンが増えるためで、誤解が起きやすい語に絞る。タイトルに付けないのは、一覧に出て長くなるため。2 回目から原語で書くのは、意味だけにすると、訳語だけのときと同じく一般の意味で覚えてしまうため。読みと意味の括弧は、原文にないものを足す例外で、原文の括弧と見分けられず、誤ることもあるが、誤解を減らすほうを取る（訳注を作ったときに見直す）。最初に出たところを要求の単位で決めるのは、LLM が見られるのは送った断片だけで、記事の全体（写した部分）を知らないため。
- **前の訳文を訳し直さない**：決まりを変えるたびに訳し直すと、訳した記事の数だけ払い直す。
- **待てば通る失敗を数えない**：混み合いや利用上限のあいだに回数を使い切ると、自動の翻訳が二度と戻らない。
- **やり直しても通らない失敗は、その場の翻訳ですぐ諦める**：要求の形、キー、権限、モデルの名前の誤りは、仕事のやり直し（1 分おき）の間には変わらず、何度呼んでも同じ答えになる。拒否や、上限で切れる応答・読めない応答も、同じ記事ではまた起きやすい（読めない応答は、structured outputs で形を決めているので、ほとんどが切れたときに起きる）。やり直すと、読む人は `translating` のまま数分待たされ、訳せないと分かるのが遅れる。キーやモデルの誤りで `queued` の記事が `untranslated` になると、自動の翻訳からは外れるが、直したあとに読む人がもう一度求めれば訳せる。
- **訳せなかった理由を残して配る**：ログはコンテナを作り直すと消え、読む人には `Untranslated` としか見えない。Claude の安全策に拒否されたのか、一時的な失敗が続いたのかが分からないと、Translate を押す意味があるかを決められない。拒否は同じ記事ではまた起きやすい。どこで起きたかを持つのは、バッチには代わりのモデルがなく、その場の翻訳なら、代わりのモデルのあるモデル（既定の Sonnet）では、代わりのモデルで通ることがあるため（バッチで拒否された記事は、Translate を押す意味がある）。`explanation` を残さないのは、英語の説明文と URL で、読む人の画面に出す文ではなく、置くと容量と配る量が増えるため。拒否の種類があれば、画面の文は作れる。
- **訳し直しの失敗には理由を書かない**：もとの訳文のまま `translated` に戻り、読む人は訳文を読める。`untranslated` の理由として出すものがない。
- **訳す仕事に入っていない `untranslated` には書かず、ほかの理由で上書きしない**：言語が判定できない記事と訳すもののない記事は、まだ訳そうとしておらず、出す理由がない（Translate を押せば、その場の翻訳の結果の理由が付く）。その場の翻訳で拒否された記事に、遅れて返ったバッチの拒否で上書きすると、「バッチで起きた失敗」として Translate を押す意味があるように読めてしまう。
- **受け付けている間は理由を残す**：受け付けたときに消すと、仕事を積めずに取り消したとき、もとの理由が失われる。`translating` の間は状態で見分けられるので、残しても読む人を誤らせない。

## 検討した代替案

- **OpenAI 互換のエンドポイントで、ほかの LLM と差し替える**：Batches と structured outputs が使えない。ほかの機能（要約など）の差し替えは、その機能を作るときに決める。
- **読む人が開いたときに、その場で自動で訳す**：外国語の記事の半分より多く開くなら高くつき、開くたびに待つ。
- **モデルを env だけで決め、既定は sendo の更新で替える**：試してから切り替えられるが、更新しないと古いまま。固定したいときのために、モデルの ID でも書けるようにする。
- **自動の翻訳では、長い記事の本文の先頭だけを訳し、続きは求めたときに訳す**：費用は下がるが、本文の全文を持てず、あとでセマンティック検索やタグ付けに使えない。続きを求める操作と、先頭だけの訳文の扱いが要る。
- **すべての翻訳を Haiku にする**：いちばん安いが、読まれやすい短い記事の品質も落ちる。
- **その場の翻訳にも閾値を当てる**：費用は下がるが、読む人が求めた記事の品質が落ちる。
- **条件をログにだけ出す**：作りは簡単だが、コンテナを作り直すと消え、記事ごとに引けない。
- **HTML のまま訳させる**：プロンプトだけでは、タグの崩れと、記事の要素が混じるのを防げない。
- **訳し直した訳文を、求めた人にだけ見せる**：人ごとのデータになり、同じ記事に何度も費用がかかる。
- **訳し直しで本文を置けなくても、本文なしで置き換える**：作りは簡単だが、訳した本文が消え、印が付くので取り戻せない。
- **訳し直しで本文を置けなければ、タイトルと要約だけを替え、もとの本文を残す**：訳文は減らないが、訳し直しの印が付くので、訳し直していない（もとの）本文を二度と訳し直せない。
- **原文の文字のハッシュだけで引き、URL を見ない**：URL の正規化が要らず、URL のない記事や別の URL の同じ文にも効くが、表記の違うタイトルは別に訳す。
- **正規化した URL とタイトルの文字が同じときだけ、タイトルを写す**：訳したタイトルが原文と食い違わないが、フィードごとに表記が違うことが多く、タイトルは使い回せない。
- **バッチの結果を待たずに、同じ元記事も送る**：作りは簡単だが、先の結果が返る前に決まった記事（ほとんどの場合）では、本文を 2 回払う。
- **訳し直しは、求めた記事だけ**：置き換えの範囲が読む人に分かりやすいが、同じ元記事のほかの記事を良くするには、また払う。
- **使い回す訳を、キーで引ける別の表に置く**：重ねて置かずに済むが、記事が消えたときの後始末と、容量の数え方が増える。
- **訳せなかった理由をログにだけ出す**：作りは簡単だが、コンテナを作り直すと消え、読む人には届かない。
- **人名をカタカナだけで書く**：日本語として読みやすいが、原文で検索できず、読みの揺れで同じ人が別に見える。
- **概念の名前を「訳語（原語）」と書く**：読みやすいが、原語が名前であることが伝わりにくい。
- **技術用語にも原語を併記する**：誤解はさらに減るが、訳文が長くなり、出力のトークンも増える。
- **です・ます調にそろえる**：やわらかいが、ニュースや技術記事、論考では冗長になる。
- **プロンプトの版を上げたら、前の訳文を訳し直す**：訳文の質がそろうが、訳した記事の数だけ払い直す。
- **`explanation` も残して配る**：理由の文をそのまま出せるが、英語で、Anthropic の文が変わりうる。画面の文は拒否の種類から作れる。

## 見直す条件

- Anthropic が「最新」を指す別名を出したとき。新しい版で要求の形が変わり、前の版に戻ることが続くとき。
- 費用が利用上限に届くことが続くとき。フィードごとに翻訳を外す設定を足すか、自動の対象を絞るか、段階の既定（モデル、思考量、閾値）を見直す。
- 残した条件で、長文の段階（Haiku）の訳文の品質の問題が目立つとき。新しい版で、系列の間の料金や品質の差が変わったとき。
- 思考量を上げた段階で、出力の上限（64,000）や 10 分の打ち切りに当たる記事が目立つとき。段階ごとに上限や打ち切りを変えるか、思考量を下げる。
- 印が崩れて原文のまま残る断片が目立つとき。60,000 文字を超えて本文を訳せない記事が目立つとき。本文を置けずに訳し直しが失敗する記事や、同じ元記事の本文を置けずに重ねて送ることが目立つとき。
- 同じ正規化した URL で中身の違うページを返すサイト（末尾の `/` の有無で別のページなど）や、同じ URL を別の記事が指すフィード、写した訳したタイトルが原文と食い違って困ることが目立つとき。
- ページを抜いた時刻で中身が変わり、指紋が合わずに本文を重ねて払う記事が目立つとき。
- 件数や費用の上限をアプリで持つことになったとき。写した分は外へ送らないので、数え方を決め直す。
- 日本語以外への翻訳や、読む人ごとの訳す先が要るとき。
- 読みや意味を添えた人名・概念の名前が、多すぎて読みにくい、または足りずに誤解が起きることが目立つとき。訳注（読む人が選んだ語に注釈を付ける）を作ったときは、どちらで補うかを決め直す。長文の段階（Haiku・low）で、この決まり（特に最初に出たところの判定）が守られないことが目立つとき。
- 拒否の種類（`stop_details.category`）の形が変わったとき。「そのほかの失敗」が粗すぎて、読む人が Translate を押すかを決められないことが目立つとき。
