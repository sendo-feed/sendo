# 記事の本文

- 状態：提案中
- 関連：[画像の中継とサムネイル](images.md)、[差分同期](sync.md)、[古い記事の片付け](retention.md)、[仕事の流し方](jobs.md)、[テックスタック](tech-stack.md)（Rust）、[コンテナ版](container.md)（版で有無が分かれる機能）、[MCP サーバー](mcp.md)、[Google Reader API 互換](greader.md)

今は、記事を 500 文字までのプレーンテキストの要約でしか持っていない。フィードに本文の HTML が入っていても捨てているので、reader で記事を読み切れない。ここでは、本文をどこから採り、どこに置き、どう配るかを決める。

本文の出どころは 2 つある。**A：フィードに入っている本文**と、**B：記事のページを取りにいって抜いた本文**。A を先に作り、そのあとで B を作る。B は CPU を多く使うので、コンテナ版だけで動かす。コンテナ版には容量と CPU に余裕があるので、B は取り込んだときに抜き、DB に置く。

## 決定

### 本文を採る（A）

1. **フィードに入っている本文を、記事を取り込むときに保存する。** 採るのは、RSS の `content:encoded`（なければ `description`）、Atom の `content`（なければ `summary`）、JSON Feed の `content_html`。
   - 保存するのは、要約に収まらなかった本文（文字が要約の長さを超える）か、画像・リンク・コード・表などを含む本文だけ。要約と同じ中身なら、保存しない
   - 記事のページは取りにいかない（それは B）
   - すでにある記事には、さかのぼって付けない
2. **保存する前にサニタイズし、返すときにもう一度サニタイズする。**
   - 通すのは、決めたタグと属性だけ（段落、見出し、リスト、引用、コード、表、強調、リンク、画像、改行）。`script`、`style`、フォーム、`class` ／ `style` ／ `id`、イベントの属性、`data:` と `javascript:` の URL は落とす
   - 埋め込み（`iframe`）と動画・音声は通さず、その URL へのリンクに替える
   - リンクと画像の URL は、記事の URL を基準に絶対の URL にし、http ／ https（リンクは `mailto:` も）だけを通す。リンクには `rel="noopener noreferrer nofollow"` を付ける
   - サニタイズしたあとで 256KB を超える本文は、保存しない（その記事は、本文なしになる）
   - 返すときのサニタイズは、今の決まりをもう一度当てるためのもの。決まりを厳しくしたら、保存してある本文にも効く

### 本文を置く

3. **フィードの本文は、オブジェクトの置き場（Cloudflare では R2）に置く。D1 には置かない。** ページから抜いた本文（B）は、コンテナ版の DB に置く（13）
   - 置き場は、緩衝層（`src/platform/`）のインターフェース越しに使う（置く、読む、消すだけ）
   - 置くのは、サニタイズした HTML。記事 1 件につき 1 つ
   - 記事の行には、フィードの本文の置き場の名前を持たせる（本文がなければ null）。記事の本体の一部で、取り込んだあとは変えない（[差分同期](sync.md)の 7）。API には、名前ではなく、本文があるかどうかだけを出す
4. **置き場と D1 の食い違いは、名前の書き留めで片付ける。** 置き場の名前は、置くたびに乱数で決め、同じ名前を二度使わない。
   - 書き留めは、D1 の表に、名前ごとに 1 行で持つ。「この名前の本文は、どの記事の行にも入っていないかもしれない」という印
   - 取り込むとき：名前を書き留めてから本文を置き、そのあとで記事の行を入れる。行に入った名前の書き留めは、入れたあとで消す。行に入らなかった名前（その記事がもうあった、途中で落ちた）は、書き留めに残る
   - 消すとき：記事の行を消すだけにする。行が消えると、表に付けたトリガーが、削除と同じ文の中で、その行の名前を書き留める。消す側のコードは、置き場に触らない
   - 1 日 1 回の片付けが、1 時間より前の書き留めを見る。どの記事の行にも入っていない名前は、本文を消してから書き留めを消す。行に入っている名前は、書き留めだけを消す
   - 1 回の取得で本文を置くのは、新しい記事 30 件まで。超えた分は、本文なしで取り込む（1 つの仕事を、1 回の実行の上限に収めるため）
5. **本文は、記事と一緒に消える。** 期間は[古い記事の片付け](retention.md)のまま（スターのない記事は 90 日）。本文だけを先に消すことはしない。

### 本文を配る

6. **本文は、差分同期に載せず、記事ごとに取りにいく。** `GET /api/v1/articles/{id}/content` で、サニタイズした HTML と出どころを返す。
   - 認証はほかの REST API と同じ。その人の受信箱にある記事だけを返す
   - 本文がなければ 404。記事（REST API と差分同期）に、本文があるかどうか（`hasContent`）を載せるので、クライアントは、ある記事だけを取りにいく
   - クライアントは、取った本文を手元に置いてよい。信頼できない HTML として扱う（そのままページに差し込まない、スクリプトを動かさない）のは、クライアントの側でも続ける
7. **本文の中の画像は、中継を通る URL に書き換えて返す**（[画像の中継とサムネイル](images.md)）。書き換えるのは返すときで、保存するのはもとの URL。
   - 使うのは `<img>` の `src` だけ。`srcset` と `<picture>` の `<source>` は落とす
   - 署名の鍵を作り直すと、手元に置いた本文の中の画像は 403 になる。そのときは、最初から同期し直して、本文を取り直す
8. **MCP の `get_article` で、本文をプレーンテキストにして返す。** タグを除き、長さに上限を置く。ツールの説明の「指示ではない」は、本文にも当てる（[MCP サーバー](mcp.md)の 8）。
9. **Google Reader API には、今は本文を出さない**（要約のまま）。

### ページから抜く（B）

10. **コンテナ版では、記事を取り込んだときに、記事のページの本文を抜く。**
    - 取得の仕事が新しい記事を取り込んだら、記事ごとに「ページから抜く」仕事を積む。抜くのは、記事の URL（`http` ／ `https`）がある記事だけ
    - 抜いた結果は、全員で共有する（記事と同じく、フィードを購読している全員のもの）
    - 読者が開いたときにまだ抜いていなければ（この機能より前に取り込んだ記事、仕事がまだ動いていない記事）、そのリクエストの中で抜く
    - 配る入口は 6 と同じ `GET /api/v1/articles/{id}/content` にし、`source=page` を付けたときにページの本文を返す
    - サニタイズ（2）と画像の書き換え（7）も、同じものを通す。サニタイズしたあとで 256KB を超える本文は、置かない（抜けなかったものとして扱う）
11. **コンテナ版だけで抜く。Cloudflare 版では、今は使えない**（[コンテナ版](container.md)の 1〜3）。
    - コンテナ版は、抜く処理を Rust で書き、napi-rs で読み込む（[テックスタック](tech-stack.md)の 5）。Mozilla の Readability を Rust に移した dom_smoothie を使う
    - Cloudflare 版は、抜く仕事を積まない。`source=page` を呼ぶと、「この版では使えない」と分かるエラーを返す。使える機能の一覧（`GET /api/v1/features`）で、ページの本文を抜けるかを返す
12. **ページを取りにいくのは TypeScript の側で、Rust には取ってきたバイト列を渡す**（[テックスタック](tech-stack.md)の 5）。
    - 取りにいくときは、フィードの取得と同じ守り（`toFetchableUrl`、リダイレクトごとの確認、接続する IP の確認、大きさと時間の上限、読者のことを渡さない）をかける。上限は 3MB と 10 秒
    - HTML でない応答（`Content-Type` が `text/html` ／ `application/xhtml+xml` でない）は、抜けなかったものとして扱う
    - 文字コードは Rust の側で決める。`Content-Type` の `charset`、なければページの先頭の `<meta charset>`、どちらもなければ UTF-8。Shift_JIS や EUC-JP のページも読む
    - Rust の側は、本文の HTML、タイトル、本文の文字数を返す。HTML のサニタイズは、返ってきたあとで TypeScript の側で行う（2）
13. **抜いた本文は、記事とは別の表に、記事ごとに 1 行で持ち、サニタイズした HTML もその行に入れる。** 置き場（R2 ／ ファイル）には置かない。記事の行には持たせない（記事の本体は、取り込んだあとは変えない）。
    - 行には、抜けたかどうか、本文の HTML（抜けたときだけ）、抜いた時刻を持つ
    - 抜く仕事と、開いたときの抜き取りが重なったら、先に行を書いたほうを残す。行を書く文の中で、まだ抜けた行がないことを確かめる
14. **抜けなかったときは、そう記録する。** 抜く仕事は、ページの側の問題（取れない、HTML でない、本文が見つからない、大きすぎる）ではやり直さない。開いたときの抜き取りは、1 日たってから取りにいき直す。
    - 抜けなかった理由は、ログにだけ出す。API は理由を出さず、404 に `page_content_unavailable` のコードを付けて返す（記事がないときの `not_found` と分ける）
    - クライアントは、抜けなかったら、フィードの本文（A）か要約を見せ続ける
15. **抜いた本文は、記事と一緒に消える**（5 と同じ）。行は、記事の行が消えると連鎖で消える。
16. **MCP と Google Reader API には、今はページの本文を出さない。** MCP の `get_article` は、今までどおりフィードの本文を返す。

## 理由

- **A を先に**：外への取得が増えず、全文を載せているフィードは、すぐに読み切れるようになる。置き場、サニタイズ、配る入口は B でもそのまま使うので、先に固めておく。要約だけのフィード（ニュースサイトに多い）は、B を待つ。
- **置き場を D1 と分ける**：D1 は無料プランで 500MB まで。今の記事（1.5〜2.6KB）だけで、30 分おき・160 フィードなら 180MB を使う。本文は 1 件で数 KB〜数十 KB になるので、D1 に置くと容量が先に尽きる。R2 は無料で 10GB まであり、通信量に課金されない。記事の一覧や未読の数を読むときに、本文を読まずに済む。
- **緩衝層越しに使う**：置き場に求めるのは「置く、読む、消す」だけ。Cloudflare 以外（VM やコンテナ）に移すときは、ローカルのファイルか S3 互換の置き場に替えられる。
- **2 回サニタイズする**：保存の前に通すのは、大きさを抑え、危ないものを置かないため。返すときに通すのは、決まりの穴をあとで直したときに、保存してある本文にも効かせるため。画像の URL の書き換えでどのみち 1 回は走査するので、手間は増えない。
- **サニタイズを sendo の側で行う**：REST API、MCP、あとで足す入口のどれから出ても、同じ決まりを通る。クライアントごとに作ると、どれかが漏れる。reader の CSP は変えない。
- **本文を先に置き、行を先に消す**：置き場と D1 を、1 つの文でまとめて書けない。「本文があると言っているのに、ない」が残る順序を避ける。置くときは本文が先、消すときは行が先なら、残るのは「行のない本文」だけになり、それは書き留めから片付けられる。
- **消すときに、本文を先に消さない**：消す記事を確かめてから行を消すまでの間に、スターが付いたり、購読を始めた人の受信箱に入ったりすると、行を消す文はその記事を飛ばす（[古い記事の片付け](retention.md)）。本文を先に消していると、残った行の本文だけがなくなり、戻らない。
- **名前を書き留める**：取得のジョブのやり直しは、フィードを取り直すだけで、前に置いた本文を覚えていない。書き留めがあれば、片付けが、置き場を全部見て回らずに、残った本文だけを消せる。書き込みは、本文のある記事 1 件につき、取り込むときと消すときに数行ずつ増える。
- **消すときの書き留めをトリガーで行う**：変更番号の下限や、受信箱の消した記録と同じ（[差分同期](sync.md)）。削除と同じ文の中で起き、記事を消す処理がいくつあっても（取得のジョブ、1 日 1 回の片付け、フィードが消えたときの連鎖）、書き留めを忘れない。
- **名前を乱数にして、二度使わない**：名前をフィードと記事のキーから決めると、やり直しで同じ名前に上書きできるが、片付けとぶつかる。片付けが「この名前は、どの行にも入っていない」と確かめたあとで、取得のやり直しが同じ名前に置いて行を入れると、片付けがその本文を消してしまう。乱数なら、書き留めにある名前をあとから行に入れるのは、それを書いた実行だけで、その実行は 1 時間たつ前に終わっている。
- **フィードの本文の名前を、記事の行に持つ**：置き場を読まずに、本文があるかをクライアントに知らせられる。取り込むときに決まるので、「記事は取り込んだあとは変えない」が崩れない。B の結果はあとから付くので、記事の行には持たせない。
- **差分同期に載せない**：最初の同期と、起動したときの 1 回の速さを保つ。読まない記事の本文まで運ばない。
- **保存するのはもとの画像の URL**：署名した URL を保存すると、鍵を作り直したときに、保存してある本文をすべて書き直すことになる。
- **Google Reader API に出さない**：アプリは 1 回に数百件の記事を取る。記事ごとに置き場を読むと、1 回の実行の上限に当たる。中継の画像は認証が要るので、アプリの `<img>` からは読めず、もとの URL のまま返すことになる（配信元に読者の IP が渡る）。
- **256KB と 30 件**：どちらも、測る前の控えめな値。実装のときに、実際のフィードで測って見直す。
- **コンテナ版では、取り込んだときに抜く**：読者が開いたときに待たずに済む。あとで、オフラインで読む、全文で検索する、LLM に渡す、にもそのまま使える。取得は新しい記事 1 件につき 1 回増える（30 分おき・160 フィードで月 2 万回ほど）が、コンテナ版には 1 回の実行の上限も、無料の枠もない。仕事に積んで、取得の仕事とは別に動かすので、フィードの取得は遅くならない。
- **開いたときにも抜く**：この機能を入れる前に取り込んだ記事や、仕事が動く前に開いた記事も読めるようにする。抜く処理は取り込むときと同じものを使う。
- **コンテナ版だけで抜く**：Mozilla の Readability のテスト用のページ集（実際のサイトを写した 130 ページ、最大 1.6MB）で、1 ページを抜くのにかかる時間を測った（2026-11-16、手元の Linux）。
  - Rust（dom_smoothie 0.19）：中央値 2.8ms、9 割が 8.1ms 以内、最大 36ms。抜けなかったページはなかった
  - JS（Readability.js 0.6 と linkedom、Node）：中央値 15.8ms、9 割が 54ms 以内、最大 306ms
  - Cloudflare 版で JS のまま抜くと、中央値でもドキュメントの CPU の上限（1 回 10ms）を超え、大きなページでは実測の上限（キューの受け手で約 1.2 秒）にも近づく。Rust にしても、Wasm にしたときの速さと大きさは、まだ測っていない
  - コンテナ版を足したのは、こういう処理を上限に縛られずに動かすため（[コンテナ版](container.md)）。まずコンテナ版で作り、Cloudflare 版に載せるかは、Wasm で測ってから決める
- **dom_smoothie**：Readability を Rust に移したもので、保守が続いている（ダウンロード 100 万回、2026 年 10 月にも版が出ている）。テストのページ集では、すべてのページで本文を抜けた。Readability と同じ考え方で抜くので、ほかのリーダーと結果が近い。
- **取りにいくのは TypeScript の側**：SSRF の守り（`toFetchableUrl` と接続する IP の確認）を、フィードの取得と同じ 1 か所に保つ（[テックスタック](tech-stack.md)の 5）。
- **文字コードを Rust の側で決める**：日本のサイトには、まだ Shift_JIS や EUC-JP のページがある。Rust の encoding_rs は、ブラウザと同じ決まり（WHATWG）で読める。
- **サニタイズを TypeScript の側で行う**：A と同じ決まりを、同じコードで通す。Rust の側には、HTML の安全を任せない。
- **結果を別の表に持つ**：記事の行は取り込んだあとは変えない（[差分同期](sync.md)の 7）。抜いた結果はあとから付くので、記事とは別に持つ。抜けなかった記録も同じ行に持てば、何度も取りにいかずに済む。
- **本文の HTML を DB の行に入れる**：A で置き場を分けたのは、D1 の容量（無料で 500MB）が先に尽きるため。コンテナ版の SQLite は自分のディスクにあり、その上限がない。行に入れれば、置き場との食い違いが起きないので、名前の書き留め、トリガー、片付けが要らない。記事の行が消えれば、連鎖で一緒に消える。量は、1 件 10〜20KB として、月 2 万件で 200〜400MB、90 日で 1GB ほどになる。
- **抜く仕事はやり直さず、開いたときは 1 日たってから**：取れなかったのが一時的な障害なら、読者が開いたときに抜ける。何度開いても、そのたびに相手のサイトを取りにいくことはしない。
- **MCP にまだ出さない**：エージェントが、記事を開くたびにページを取りにいかせられるようになる。どこまで許すか（読むだけの範囲で取りにいかせてよいか）は、MCP で使うときに決める。

## 検討した代替案

- **本文を D1 に置く（記事とは別の表）**：設定が増えないが、容量が先に尽きる。本文だけ先に消す、圧縮する、の作り込みが要る。
- **Cloudflare 版でも、すべての記事のページを、取り込むときに抜く**：取得・CPU・容量が記事の数だけかかり、無料の枠に収まらない。
- **コンテナ版でも、開いたときにだけ抜く**：取得とディスクは減るが、初めて開いた人が数秒待つ。コンテナ版には余裕があるので、待たせないほうをとる。
- **抜いた本文を、A と同じ置き場（ファイル）に置く**：A と作りがそろうが、名前の書き留めとトリガーと片付けが要る。コンテナ版では、DB に入れるほうが早くて単純。
- **Cloudflare 版でも、JS（Readability.js）で抜く**：両方の版で使えるが、CPU の上限を超える（上の測った値）。
- **Cloudflare 版でも、Rust を Wasm にして抜く**：同じ crate を使えるかもしれないが、Wasm での速さとバンドルの大きさを測っていない。測ってから決める（[仕事の流し方](jobs.md)の「見直す条件」）。
- **抜く処理を TypeScript で書き、コンテナ版でだけ動かす**：Rust が要らないが、遅い（中央値で 5 倍ほど）。重い処理は Rust で書く（[テックスタック](tech-stack.md)の 5）。
- **ページを取りにいくのも Rust で行う**：つなぎ目は減るが、SSRF の守りが 2 か所になる。
- **行のない本文を、置き場を見て回って探す**：書き留めが要らないが、置き場の一覧を毎日読むことになり、本文が増えるほど重くなる。
- **記事の行を先に入れ、本文を置いてから「ある」の印を付ける**：行のない本文は残らないが、記事を取り込んだあとで変えることになり、印が付く前に同期したクライアントは、本文がないと思ったままになる。
- **サニタイズせずに保存し、返すときだけサニタイズする**：もとの HTML が残るので、決まりを緩めたときにも効くが、信頼できない HTML をそのまま置くことになり、大きさも抑えられない。
- **サニタイズをクライアントに任せる**：sendo は軽くなるが、入口ごとに作ることになる。
- **本文を差分同期に載せる**：オフラインですべて読めるが、同期が重くなる。
- **画像の URL を書き換えずに返す**：reader の CSP（`img-src 'self' data:`）で出せない。配信元に読者の IP が渡る。

## 見直す条件

- Cloudflare 版でもページの本文を抜きたくなったとき。同じ crate を Wasm にして、workerd で速さと大きさを測る（11）。
- 抜いた本文が、フィードの本文より短い・崩れているなどで困るとき。どちらを返すか、抜き方の設定を変えるかを決め直す。
- DB の大きさが気になってきたとき（抜いた本文を圧縮する、置き場に移す、抜くフィードを選べるようにする）。
- 取り込むときの取得が、相手のサイトに負担をかけていると分かったとき（同じサイトへの間隔を空ける、抜くフィードを選べるようにする）。
- MCP でページの本文を使いたくなったとき（16）。
- 記事のページの `og:image` をサムネイルに使いたくなったとき（[画像の中継とサムネイル](images.md)）。
- 全文検索（Phase 2）や LLM の処理（Phase 3）を作るとき。本文を D1 の索引に入れるか、先に抜く範囲を広げるかを決める。
- Google Reader API のアプリで本文を読みたくなったとき。
- 置き場の使用量や、1 回の実行の上限が、測ってみて見込みと違ったとき（256KB、30 件、R2 の無料の枠）。
- Cloudflare 以外で動かすとき（置き場の実装を足す）。
