# 画像の中継とサムネイル

- 状態：提案中
- 関連：[差分同期](sync.md)、[ユーザーと認証](accounts.md)、[古い記事の片付け](retention.md)、[テックスタック](tech-stack.md)、sendo-reader の[ローカルファースト](https://github.com/sendo-feed/sendo-reader/blob/main/docs/decisions/local-first.md)（ページの守り）

sendo-reader の CSP は、画像を同じオリジンと `data:` に限る（`img-src 'self' data:`）。Sendo はサムネイル、フィードのアイコン、記事の本文に含まれる画像を中継し、sendo-reader が同じオリジンから表示できるようにする。

## 決定

### 画像の中継

1. **`GET /api/v1/images?url=<もとの URL>&sig=<署名>` で、画像を中継する。**
   - 元の画像 URL は 4,096 文字まで。認証は、ほかの REST API と同じ（セッションのクッキーか、アクセストークン）。`<img src>` にそのまま入れられる
   - 中継できないときは、エラーを返すだけにする。認証がなければ 401、署名が合わなければ 403、配信元から取れない ／ 画像でない ／ 大きすぎるときは 502
2. **中継するのは、sendo が署名した URL だけ。**
   - 署名は、もとの URL の HMAC-SHA-256（先頭の 128 ビットを base64url にした 22 文字）。sendo が API の応答に画像の URL を載せるときに付ける
   - 署名に、ユーザーと期限は入れない。認証は別に求めるので、署名が確かめるのは「sendo が配信するために署名した URL か」だけ
   - 鍵は 32 バイトの乱数。初めて使うときに sendo が作り、DB に置く（なければ入れる、を 1 つの文で行う）。デプロイする人が入れる設定は増やさない
   - 鍵を作り直すと、配った URL はすべて 403 になる。そのときは、クライアントに最初から同期し直してもらう
3. **中継先は、フィードの取得と同じ決まりで制限する。**
   - http ／ https だけ。取得の前に `toFetchableUrl` を通す（内部の宛先、URL の中の認証情報、既定ポートと 80・443・8080・8443 以外のポートを拒む）
   - リダイレクトは自分でたどり（5 回まで）、行き先ごとに同じ確認をかける
   - 時間切れは、本文を読み終えるまでで 15 秒。大きさは 10MB まで（`Content-Length` が超えていれば読まずにやめ、なくても読んだ量でやめる）
4. **配信元には、読者のことを渡さない。** リクエストは sendo が新しく組み立て、ブラウザから来たヘッダーを写さない。
   - 送るのは `User-Agent`（Sendo のもの）と `Accept`（画像）だけ
   - クッキー、`Authorization`、`Referer`、ブラウザの `User-Agent` と `Accept-Language`、`X-Forwarded-For` などの IP の載るヘッダーは送らない
5. **返すのは、中身を確かめた画像だけ。**
   - 形式は、配信元の `Content-Type` を信じず、先頭のバイトで確かめる。通すのは JPEG、PNG、GIF、WebP、AVIF、ICO。`Content-Type` は、確かめた形式から sendo が付ける
   - **SVG は通さない。** 同じオリジンで直接開かれると、スクリプトが動くため
   - 配信元の応答のヘッダーは写さない（`Set-Cookie` など）。sendo が付けるのは、`Content-Type`、`Content-Length`、`Cache-Control`、`X-Content-Type-Options: nosniff`、`Content-Security-Policy: default-src 'none'; sandbox`、`Cross-Origin-Resource-Policy: same-origin`
6. **キャッシュは、ブラウザと reader の Service Worker に任せる。sendo の側にはキャッシュを置かず、画像の縮小も行わない。**
   - 画像の応答には `Cache-Control: private, max-age=2592000`（30 日）を付ける。エラーの応答は `no-store`
   - URL が同じなら中身も同じとみなす。reader の Service Worker は、30 日より長く持ってよい

### サムネイルとフィードのアイコン

7. **記事にサムネイルの URL を持たせる。** フィードを解析するときに、次の順で最初に見つかったものを採る。なければ null。
   1. `media:thumbnail`
   2. 画像の `media:content`
   3. 画像の添付（RSS の `enclosure`、Atom の `rel="enclosure"` のリンク、JSON Feed の `attachments`）
   4. `itunes:image`、JSON Feed の `image`
   5. 本文の HTML の最初の `<img>`（幅か高さが 1〜2 と書かれた計測用の画像は飛ばす）

   - 記事のページは取りにいかない（`og:image` は使わない）
   - http ／ https の URL だけを保存する。長すぎる URL（2,000 文字を超える）は捨てる
   - サムネイルは記事の本体の一部で、取り込んだあとは変えない（[差分同期](sync.md)の 7）
8. **フィードにアイコンの URL を持たせる。** フィードの取得のジョブのついでに、30 日に 1 回探す。
   - 探す順：フィード自身のアイコン（JSON Feed の `icon` ／ `favicon`、Atom の `icon`）、サイトのページの `<link rel="icon">` ／ `apple-touch-icon`、サイトの `/favicon.ico`
   - 候補は実際に取得し、5 の決まりで画像と確かめられたものだけを保存する。見つからなければ null
   - RSS の `<image>` と Atom の `logo` は使わない（横長のロゴが多い）
   - 探すのに失敗しても、フィードの取得は失敗にしない
   - アイコンが変わったら、名前やサイトの URL が変わったときと同じように、トリガーで購読の変更番号を進める
9. **API では、中継を通る URL にして返す。**
   - 記事の `thumbnailUrl` とフィードの `iconUrl` に載せる。値は `/api/v1/images?url=…&sig=…` の形のパス（オリジンは付けない）か null
   - REST API の記事とフィード、差分同期（`GET /api/v1/sync`）の記事とフィードに載せる。クライアントは URL を組み立てず、受け取ったものをそのまま使う
   - Google Reader API と MCP には載せない
10. **サムネイルは記事を取り込むときに決める。** 取り込み済みの記事にはさかのぼって付けない。アイコンはフィードを取得する際に、8 の間隔で探す。

## 理由

- **sendo が中継する**：CSP を広げると、画像の URL で手元のデータを外へ送れるようになり、配信元にも読者の IP と開いた時刻が伝わる。中継なら、reader からは同じオリジンの画像に見える。
- **署名した URL だけ**：ログインしていれば任意の URL を中継できると、ページに入った他人の JS が、中継の URL に手元のデータを載せて外へ送れる（CSP で塞いだ穴が、中継で開く）。sendo が見た URL だけに限れば、塞いだままにできる。
  - 記事やフィードの ID から引く形（下の代替案）と比べて、DB を読まずに確かめられる。本文の中の画像にも同じ入口を使える
  - フィードを書く人は、好きな URL を sendo に取りにいかせられる。これはフィードの取得と同じ立場で、`toFetchableUrl` で同じように守る
- **署名にユーザーと期限を入れない**：記事は手元に長く置かれ、オフラインでも使う。期限を付けると、置いてある URL が切れる。画像は共有のデータで、認証は別に求めるので、署名がほかの人に渡っても、その人が自分のセッションで同じ画像を見られるだけ。
- **鍵を DB に置く**：デプロイする人が画像中継用の鍵を個別に用意せずに済む。鍵が漏れても、起きるのは「ログインした人が、任意の URL を中継できる」まで。
- **新しく組み立てたリクエスト**：Node の `fetch`（undici）は、外への取得に、受けたリクエストのヘッダーを自分からは足さない（足すのは `accept-encoding` などの決まったものだけ）。ブラウザから来たヘッダーを写さなければ、読者の IP は配信元に渡らない。本番で、ヘッダーを映す外のサーバーに向けて確かめる。
- **先頭のバイトで確かめる**：配信元は `Content-Type` を偽れる。HTML や SVG が画像として同じオリジンから返ると、直接開いたときにスクリプトが動く。形式を確かめたうえで、`nosniff` と `sandbox` も重ねる。
- **SVG を通さない**：`sandbox` を付ければ返せるが、守りがヘッダー 1 つになる。写真やアイコンは、ほぼほかの形式で足りる。
- **sendo の側にキャッシュを置かない、作り直さない**：
  - 同じ画像を何度も取りにいくのは、同じ端末の同じ人。ブラウザと Service Worker のキャッシュで足りる（2 人で使うので、人をまたいだキャッシュの効果は小さい）
  - 手間は、画像 1 枚につき、端末ごとに 30 日に 1 回の中継。外への取得 1 回と、DB の読み取り数行（セッションの確認）で、書き込みは増えない。本文はそのまま流すので、CPU はほとんど使わない
  - 小さく作り直すには、画像 1 枚で CPU を数十〜数百 ms 使う（Rust で書けばスレッドプールで動かせる）。作ったものを置くディスクと片付けも要る
  - ディスクに置けば配信元への取得は 1 回で済むが、置き場と片付けが要る
- **サムネイルをフィードの中から採る**：記事のページを取りにいくと、記事 1 件ごとに外への取得と解析が増える。サムネイルの選定は、フィードの解析だけで行える。
- **アイコンを確かめてから保存する**：`/favicon.ico` のないサイトは多い。確かめずに配ると、reader が開くたびに、失敗する中継が走る。確かめるのは、フィードごとに 30 日に 1 回で、取得が数回と書き込みが 1 行。
- **中継の URL をそのまま配る**：reader が URL を組み立てないので、あとで形を変えられる。オリジンを付けないのは、sendo が reader のオリジンを知らなくても済むように。
- **さかのぼらない**：記事は取り込んだあとは変えない。さかのぼって付けると、同期で届けるために受信箱の行の変更番号も進めることになり、記事 1 件・1 人あたり数行の書き込みが要る。
- **同期の量**：サムネイルのある記事 1 件につき、0.2KB ほど増える（もとの URL を URL エンコードしたもの、署名 22 文字、パスと項目の名前。圧縮前）。サムネイルを除く記事 1 件を 1〜2KB とすると、サムネイルのある記事で 1〜2 割、全体で 1 割前後増える見積もり。フィードは 1 件につき同じく 0.2KB ほどで、数が少ないので効かない。DB の容量は、記事 1 件あたり 0.1KB ほど増える。

## 検討した代替案

- **reader の CSP を `img-src https:` に広げる**：sendo は何もしなくてよいが、背景に書いた 2 つの穴が開く。
- **記事やフィードの ID から引く（`/api/v1/articles/{id}/thumbnail`、`/api/v1/feeds/{id}/icon`）**：鍵が要らず、「その人の受信箱の記事か、購読しているフィードか」で確かめられる。同期の量もほとんど増えない。ただし、画像 1 枚ごとに DB を読む。本文の中の画像は、記事ごとに画像の一覧を別に持たないと引けない。アイコンは、中身が変わっても URL が変わらず、古いキャッシュが残る。
- **署名にユーザーを入れる**：署名がほかの人に渡っても使えなくなるが、同じ画像の URL が人ごとに変わる。守れるものは増えない（認証は別に求めている）。
- **鍵を必須の秘密（環境変数）にする**：DB に秘密を置かずに済むが、デプロイの手順が増える。
- **SVG を `sandbox` 付きで返す**：SVG のアイコンも出せるが、理由に書いたとおり見送った。
- **取り込むときに画像も取っておく（ディスクに置く）**：配信元に、読者が開いた時刻も伝わらなくなり、配信元が消しても出せる。読まれない画像まで取ることになり、置き場所と片付けが要る。
- **Rust で、サムネイルを小さく作り直す**：通信量は減るが、理由に書いた CPU と置き場の手間がかかる。
- **アイコンを、外のサービス（Google の favicon の API など）から取る**：探す処理は要らないが、購読しているサイトの一覧を外のサービスに渡すことになる。
- **すでにある記事にも、次の取得でさかのぼって付ける**：フィードに載っている記事にはすぐ付くが、理由に書いた書き込みがかかる。

## 見直す条件

次の 4 つは、今の規模（2 人で使う、1 つのコンテナ）に合わせて選んだ。それぞれ、次のときに決め直す。

- **署名した URL（2）→ 記事やフィードの ID から引く形**
  - 同期の量を実際に測って、画像の URL の分が重いと分かったとき（最初の同期が遅い、手元の容量を使いすぎる）
  - 本文の中の画像を署名なしで扱う形に決めたとき（署名を使い続ける理由がなくなる）
  - 鍵を作り直す場面が実際に起き、配った URL がまとめて切れるのが困ると分かったとき
- **鍵を DB に置く（2）→ デプロイする人が入れる秘密**
  - 公開サーバーとして運営する話が出たとき、または知らない人どうしが 1 つのサーバーを使うようになったとき（[ユーザーと認証](accounts.md)の見直す条件と同じ）
  - DB の書き出しやバックアップを、秘密を扱えない場所に置くようになったとき
  - 署名で守るものが増えたとき（署名が合えば認証なしで返す、など。今は、鍵が漏れても「ログインした人が任意の URL を中継できる」まで）
- **小さく作り直さない、sendo の側にキャッシュを置かない（6）→ 作り直す ／ 置く**
  - 一覧の画像が重いと分かったとき（モバイルの回線での表示の速さ、通信量）。先に reader の側（遅らせて読む、回線によって出さない）で和らげ、それで足りなければ sendo で作り直す
  - 使う人が増えて、同じ画像を人をまたいで何度も取りにいくようになったとき、または配信元から取得を断られる（回数の制限）ようになったとき
- **SVG を通さない（5）→ `sandbox` を付けて通す**
  - アイコンの付かないフィードが目立ち、その理由が SVG のアイコンしかないことだと分かったとき
  - 本文の中の SVG の図を出したくなったとき

ほかに、次のときにも見直す。

- 本文の中の `<img>` は、本文を返すときに同じ中継の URL に書き換える（[記事の本文](content.md)の 7）。本文の中の画像の数が増えて、中継の回数が見込みと違ったとき。
- フィードから採れるサムネイルでは足りず、抽出するページの `og:image` も使いたくなったとき。取り込み後に付けてよいかを含めて見直す（[差分同期](sync.md)の 7）。
- 本番で確かめて、配信元に読者の IP が渡っていたとき。
