# Google Reader API 互換

- 状態：提案中
- 関連：[ユーザーと認証](accounts.md)、[差分同期](sync.md)、[機能一覧](../features.md)（Phase 1 の「Google Reader API 互換」）

Reeder や NetNewsWire などのリーダーアプリから、Sendo をそのまま読めるようにする。Google Reader API は公式の仕様が残っていないので、FreshRSS や Miniflux などが実装して、リーダーアプリが使っている形に合わせる。

## 決定

1. **入口は `/accounts/ClientLogin` と `/reader/api/0/...` にし、REST API（`/api/v1`）とは分ける。** リーダーアプリには、Sendo の URL（`https://<sendo>`）をそのまま設定してもらう。
2. **ログインのパスワードは、アクセストークン（アプリ用パスワード）にする**（[ユーザーと認証](accounts.md)の 6、7）。
   - `ClientLogin` は、`Email`（ユーザーのメール）と `Passwd`（そのユーザーのアクセストークン）を受け、両方が合えば `SID`、`LSID`、`Auth` に同じトークンを入れて返す。メールが違えば、トークンが正しくても受けない
   - そのあとは `Authorization: GoogleLogin auth=<トークン>` で認証する（`Bearer` も受ける）
   - 書き込みに付ける `T`（`/reader/api/0/token` で配る）は、配るが確かめない。認証はヘッダーで行い、ブラウザが自動で付けるものではないので、CSRF の対策は要らない
3. **記事の ID（アイテムの ID）は、記事（共有）に持たせる整数にする。** 値は、記事を取り込んだときに振る、1 以上 2^53 未満の乱数にする。
   - 返すときは、長い形（`tag:google.com,2005:reader/item/` ＋ 16 桁の 16 進）と、`stream/items/ids` の短い形（10 進）を使う。受けるときは、長い形、16 桁の 16 進、10 進のどれも受ける
   - 一意にし、重なったら振り直す
4. **ストリームの ID は、次のとおりにする。**

   | ストリーム | ID |
   |---|---|
   | 購読しているすべての記事 | `user/-/state/com.google/reading-list` |
   | 既読 ／ スター | `user/-/state/com.google/read` ／ `user/-/state/com.google/starred` |
   | フォルダ | `user/-/label/<フォルダの名前>` |
   | フィード | `feed/<フィードの ID>`（REST API と同じ ID） |

   `user/<ユーザーの ID>/...` の形で来ても、`user/-/...` と同じに扱う。

5. **状態を変える操作は、REST API と同じ処理に任せる。**
   - `edit-tag`：既読（`read`）とスター（`starred`）の付け外し。`kept-unread` を付けたら未読にする
   - `mark-all-as-read`：`ts`（マイクロ秒）より前に受信箱に入った記事だけを既読にする。`ts` がなければ、受けた時刻を境界にする
   - 購読（`subscription/quickadd`、`subscription/edit`）、フォルダ（`rename-tag`、`disable-tag`）も、REST API と同じ処理を通す
   - 購読の名前の付け直し（`subscription/edit` の `t`）は、人ごとの名前を持つまで受けるだけで何もしない
6. **記事の本文は、要約（プレーンテキスト）を HTML にエスケープして返す。** Google Reader API の `summary.content` や `content.content` は HTML として表示されるので、エスケープしないと、フィードの中身がリーダーアプリの画面でマークアップとして解釈される。全文の取得（Phase 2）ができたら、サニタイズした HTML を返す。
7. **続き（`c`）は、意味を持たせない文字列にする。** 中身は、記事の一覧と同じく「最後に返した記事の位置」（公開日時と記事の ID）。

## 理由

- **入口を分ける**：リーダーアプリは、決まったパス（`/accounts/ClientLogin`、`/reader/api/0`）を前提にしている。REST API の形（JSON、エラーの形、OpenAPI）とは決まりが違うので、混ぜない。
- **パスワードにアクセストークン**：Reeder や NetNewsWire はユーザー名とパスワードでしかログインできない。アプリごとに発行して取り消せるトークンなら、アプリが漏らしてもそのトークンを取り消せば済む（Miniflux、FreshRSS と同じ形）。メールも確かめるのは、ほかの人のトークンを誤って入れたときに、別の人としてログインさせないため。
- **T を確かめない**：T は、もとはクッキーで認証するときの CSRF の対策。ヘッダーで認証するなら、ほかのサイトから勝手に送らせることはできない。確かめないほうが、T の期限切れでリーダーアプリがつまずかない。
- **アイテムの ID を整数にする**：リーダーアプリは、アイテムの ID を 64 ビットの整数として扱う（NetNewsWire は 10 進を読み、16 進に直して送り返す）。Sendo の記事の ID は UUID なので、別に整数を持つ。
- **乱数にする**：記事は全員で共有するので、順に振ると、ID の間の飛びから、ほかの人が購読しているフィードの記事の数が分かる（[ユーザーと認証](accounts.md)の 5「共有を利用者から見せない」）。2^53 未満にするのは、D1 から JavaScript の数で受け取っても、丸められないようにするため。記事が 100 万件になっても、どれか 2 つが重なる見込みは 1 万分の 1 より小さく、重なっても一意制約で振り直せる。
- **フィードの ID を REST API と同じにする**：URL を ID にする形（もとの Google Reader）もあるが、URL は正規化や移転で変わる。リーダーアプリは `subscription/list` の `id` をそのまま送り返すだけなので、REST API と同じ ID でよい。
- **REST API と同じ処理に任せる**：既読やスター、購読の変更を 2 か所で書くと、変更番号（[差分同期](sync.md)）の振り忘れや、並行したときの扱いがずれる。

## 検討した代替案

- **アイテムの ID を、記事の UUID の先頭 64 ビットから作る**：列は要らないように見えるが、ID から記事を引くのに結局その値の索引が要る。符号の扱い（先頭のビットが立つと負になる）も、リーダーアプリごとに違う。
- **アイテムの ID を順に振る**：振り方は簡単（変更番号と同じ形）だが、ほかの人の記事の数が分かる。
- **受信箱の行ごとに ID を振る**：人ごとに違う ID になり、共有が見えにくくなるが、取り込むたびに人数分の ID を振ることになる。記事ごとの乱数で、共有は十分見えない。
- **T を確かめる**：もとの Google Reader に忠実だが、ヘッダーで認証する限り守りは増えず、T の期限切れの扱いが要る。
- **パスワードに、Google Reader API 専用の別の秘密を発行する**：アクセストークンと分けると、取り消しの画面が 2 つになる。

## 見直す条件

- よく使われるリーダーアプリが、ここの形で動かないと分かったとき（ID の形、T の扱いなど）。
- 全文の取得（Phase 2）ができたとき（6 の本文を、サニタイズした HTML に替える）。
- 購読の名前を人ごとに付け直せるようにしたとき（5 の `t` を受ける）。
