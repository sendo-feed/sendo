# あとで読むページ

- 状態：提案中
- 関連：[差分同期](sync.md)、[ユーザーと認証](accounts.md)、[保存容量と古い記事の片付け](retention.md)

購読していないページや投稿を URL 単位で保存し、同じ Sendo アカウントの端末間で同期する。

## 決定

1. **URL だけで保存する。** HTTP(S) を受け付け、ユーザー名・パスワードを含む URL は受け付けない。標準の URL API で正規化した URL を保存し、クエリとフラグメントは残す。URL は正規化後も 2,048 文字までとする。タイトルは任意のプレーンテキストで 300 文字まで。最初の版では外部取得を行わないので、Sendo から本文を取れない投稿も元のリンクを保存できる。
2. **ユーザーと URL の組で、保存したページを一意にする。** ID は正規化した URL の SHA-256 を小文字の 16 進数で表した値。読み書きは必ず認証したユーザーで絞る。同じ URL を保存し直したときは現在の保存情報を返し、解除後に保存した場合は新しい保存日時を付ける。
3. **フォルダや受信箱とは独立して保存する。** Saved のページはその URL を保存したという記録で、購読記事のスターと独立して扱う。reader の既存の Saved では両方を表示し、同じ URL に重なったら 1 件にまとめ、それぞれの保存状態は保つ。購読解除や記事の片付けで保存したページは消さない。
4. **REST API で登録・一覧・解除し、既存の差分同期にも載せる。** `PUT /api/v1/saved` で URL を登録し、`GET /api/v1/saved` は保存日時の新しい順にページ送りできる。`DELETE /api/v1/saved/{id}` は同じ要求を再送できる。`includeSaved=true` を送ったクライアントに、初回同期では有効な保存を、差分では保存と解除を返す。保存用の位置を持たない既存カーソルでは保存の位置だけを最初から読む。指定しないクライアントには保存用の位置を発行しない。
5. **保存容量を人ごとに抑える。** 有効な保存は 2,000 件、解除の記録を含む行は 4,000 件まで。上限は登録する SQL と同じ文で確かめる。解除した行には ID・ユーザー・変更番号・解除日時を残し、URL とタイトルは消す。30 日を過ぎた解除の記録を日次で片付けるときは、回収の下限を削除と同じ文の中で記録する。それより古い同期カーソルには既存の `invalid_cursor` を返す。保存はメタデータだけを別枠で持ち、フィード記事用の容量で片付けない。

## 理由

- 内容が取れないときも、リンクを保存できれば目的を果たせる。本文の保存と配信を追加する場合は、既存の記事取得と保存容量の決まりに沿って扱いを決める。
- URL から ID を決めると、複数の端末やオフラインでの送信が重なっても同じ保存に合流できる。
- 解除の記録を残すと、別の端末でも解除を反映できる。URL とタイトルを消しておけば、解除の伝達に元の情報を残す必要がない。
- 保存の数と各項目の長さを抑えることで、フィードの保管とは独立して容量を見積もれる。
