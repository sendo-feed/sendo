# ワークスペース

- 状態：提案中
- 関連：[ユーザーと認証](accounts.md)、[差分同期](sync.md)、[あとで読むページ](saved.md)、[MCP サーバー](mcp.md)

## 決定

1. **ワークスペースはアカウントごとに持つ。** 購読は最大1つに所属し、`workspaceId` が null なら未割り当て。フォルダは従来どおり使い、同じフォルダ内でも購読ごとに所属を選べる。移動で購読・記事の ID、フォルダ、既読・スターは変わらない。過去の記事も現在の有効な購読の所属に従う。Reader の「すべて表示」には未割り当てと購読のない項目も含める。Reader は表示の選択を手元に持ち、アクセス権限はアカウント単位とする。
2. **既存・新規アカウントに `default` を作る。** マイグレーションで購読が0件のアカウントも含めて1つずつ作り、有効な既存購読をそこに入れる。所属を付けた有効な購読だけ変更番号を振り直し、移行前に同期した端末へ所属を届ける。新規アカウントではユーザーを挿入する文のトリガーで空の `default` を作る。名前変更も削除も通常のワークスペースと同じで、後のログインやトークン発行で作り直さない。
3. **有効な購読が0件なら削除できる。** 最後の1件も削除できる。削除の文で購読が0件のことを確かめ、購読を所属させる文で移動先が同じ利用者の有効なワークスペースであることを確かめる。先に所属が付けば削除は 409 `workspace_not_empty`、先に削除された場合は所属の指定を 400 `workspace_not_found` で返す。購読解除済みの行は件数に含めない。削除は変更番号を振って印を付け、フォルダと同様に同期用に保持する。
4. **REST API で管理する。** 入口はすべて `/api/v1` の下。ワークスペースは `id`、`name`、`createdAt` を返す。名前は前後の空白を除いた1〜200文字で、有効なワークスペース内でアカウントごとに一意とする。

   | 操作 | リクエストと結果 |
   |---|---|
   | `GET /workspaces` | 有効なワークスペースを名前順で `{ items }` に返す |
   | `POST /workspaces` | `{ name, id? }` で作る。ID を省略するとサーバーで採番する。オフライン作成ではクライアント指定の小文字 UUID を使え、同じ有効な ID の再送は現在の項目を200で返す。新規は201で `{ workspace }` を返す |
   | `PATCH /workspaces/{id}` | `{ name }` で名前を変え、`{ workspace }` を返す |
   | `DELETE /workspaces/{id}` | 空のワークスペースを削除して204を返す。同じ利用者が削除済みの ID を再送したときも204 |
   | `POST /feeds` ／ `PATCH /feeds/{id}` | 購読の入力に `workspaceId` を受ける。追加時の省略と明示的な null は未割り当て。変更時の省略は現在の所属を保ち、null は所属を外す。変更で所属を指定するときは対象の購読の `subscriptionId` も渡す。購読し直した別の行への変更は404。対象の購読 ID と所属先を、指定された変更を書き込む文の中で確かめる |

   - 同じ名前との衝突は 409 `workspace_exists`。作成で削除済みまたは使用できない ID を指定すると 409 `workspace_id_taken`。変更・削除で本人の項目が見つからなければ404。所属先のエラーは別アカウントの ID にも同じ結果を返す。
   - `GET /feeds` と購読の追加・変更の応答に `workspaceId` と `subscriptionId` を載せる。購読し直すと `subscriptionId` は変わる。Discord の購読も、作成後は同じ変更 API で移動できる。
5. **差分同期は `includeWorkspaces=true` を指定したクライアントに届ける。** `workspaces` 配列に有効な項目（`deleted: false`）と削除の印（`id, deleted: true`）を返し、有効な購読に `workspaceId` と `subscriptionId` を付ける。変更番号とページ送りはワークスペースの表で独立させる。ワークスペースの位置を持たないカーソルでは、ワークスペースと購読を番号0から送り、購読に所属を補う。ワークスペースは削除の印も送る。購読は通常の差分と同じ規則で送る。現在も有効な購読があるフィードには、古い購読の削除の印を送らない。ほかの表はカーソルの続きから送る。指定を外したリクエストの応答ではワークスペースの位置を持たない。ページ順に依存せず、Reader は所属情報が揃うまで選択外の記事を出さない。Reader は同期応答で対応が確認できた Sendo に所属指定付きの書き込みを送る。
6. **一括既読は、押したときの購読 ID と同期済みの境界を送る。** `POST /api/v1/articles/mark-read` で従来の範囲指定に加え、記事の位置が完了した `cursor` と `subscriptionIds` の組を受ける。他の範囲指定や `until` との併用は400。Reader は押したときに選択範囲へ入っていた有効な購読の ID を操作に記録する。送信時にその ID が指す同じ利用者の有効な購読だけを対象にするので、購読の移動で別の購読が加わらず、解除後に購読し直したものにも及ばない。現在のワークスペース名・所属はこの照合に使わない。従来と同じく `read_seq` と記事 ID で同期済みの境界を守る。1 回の上限は90件で、超える場合は同じカーソルで分けて送れる。公開日時や記事位置でさらに絞る操作は従来の個別記事 ID 指定を使う。
7. **所属指定のない購読。** REST API、Discord、MCP、OPML で、所属指定なしの新規購読は未割り当て。初期の `default` を名前で探すことはない。すでに購読している場合は既存の所属を維持し、所属を変える場合は購読の変更 API を使う。OPML の既存のフォルダの取り込みは従来どおり。書き出しは従来どおり Discord 以外の全購読とフォルダを対象にする。

## 理由

- **購読に所属を持たせる**と、フィードの取得と記事の受信箱を共有したまま、フォルダとは別に表示する範囲を選べる。
- **所属指定なしを未割り当てにする**と、古いクライアントや OPML から追加したフィードが、画面共有中に選んでいるワークスペースに突然現れない。
- **操作時の購読 ID を送る**と、オフラインの間に選択や所属が変わっても、別の購読へ操作が広がらない。

## 検討した代替案

- **フォルダごとに所属させる**と、同じフォルダのフィードを用途ごとに分けるたびに、従来のフォルダ整理も変えることになる。
- **一括既読でワークスペース ID を送る**と、送信までに移動してきた購読も既読になる。

## 見直す条件

- 同じ購読を複数のワークスペースに入れたいとき。
- MCP でもワークスペースを指定して読み書きしたいとき。
