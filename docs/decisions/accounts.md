# ユーザーと認証

- 状態：提案中
- 関連：[テックスタック](tech-stack.md)、[インセプションデッキ](../inception-deck.md)、[技術構成](../tech-deck.md)

## 決定

1. **ユーザーの表を最初から持つ。ユーザーが決めるパスワードは持たない。**
2. **ログインは外部の認証に任せる。** Sendo 自身が OpenID Connect（認可コードフロー、PKCE 付き）で Google にログインを頼む。GitHub などの提供元は、あとから同じ形で足せるようにする。
3. **ユーザーになれるのは、許可したメールアドレスの人だけ。** 許可するメールは設定（環境変数）に書く。提供元が確認済みとしたメールだけを使い、初めてログインしたときにユーザーを作る。
4. **1 人のユーザーが、複数の提供元のログインを持てる。** 提供元の ID（issuer と subject）は、ユーザーとは別の表に置く。ログインしたときは次の順で見分ける。
   1. その提供元の ID がすでに結び付いていれば、そのユーザー
   2. なければ、提供元が確認済みとしたメールが一致するユーザーに結び付ける
   3. それもなければ、許可したメールならユーザーを作る

   一度結び付いたあとは提供元の ID で見分けるので、提供元の側でメールが変わっても同じユーザーのまま。メールの確認をきちんとしている提供元だけを使う（GitHub なら確認済みの主メールだけ）。
5. **データは人ごとに分ける。** 購読・フォルダ・既読・スターは人ごとに持つ。
   - フィードと記事は、裏では全員で共有し、取得は 1 回だけにする。誰も購読していないフィードは取得しない
   - **共有は、取得を最適化するための内部の作りで、利用者からは見えないようにする。** 人ごとの設定（フィードの名前の付け直し、Phase 2 のフィルタなど）は、共有のフィードではなくその人の購読に持つ。購読している人数など、ほかの人の存在が分かる情報は API で返さない
6. **入口ごとの認証**

   | 入口 | 認証 |
   |---|---|
   | ブラウザ（sendo-reader） | OpenID Connect でログインし、セッションのクッキー（HttpOnly・Secure・SameSite=Lax）を使う。セッションは DB に置き、取り消せる |
   | エージェントやスクリプト（REST API） | ユーザーが発行するアクセストークン（`Authorization: Bearer`） |
   | リーダーアプリ（Reeder、NetNewsWire など） | アクセストークンを「アプリ用パスワード」として、パスワード欄に入れる（Google Reader API の決まりで、パスワード欄しかないため） |
   | AI エージェント（リモート MCP） | MCP の OAuth で認可する。ログインはここの OpenID Connect を使う。細かい形は [MCP サーバー](mcp.md)で決める |

7. **アクセストークン（アプリ用パスワード）の扱い**
   - ログインしたユーザーが、用途の名前を付けて発行する。一覧で見られ、いつでも取り消せる
   - 中身は 32 バイト以上の乱数。DB には SHA-256 のハッシュだけを置き、発行したときに一度だけ見せる（ユーザーが決める文字列ではないので、遅いハッシュは要らない）
   - 今の、環境変数 1 つのトークン（`API_TOKEN`）はやめる
   - 用途（リーダーアプリ用 ／ MCP 用）を持たせる。MCP 用は範囲（`read` ／ `write`）を持ち、`/mcp` でしか使えない（[MCP サーバー](mcp.md)の 2）

## 理由

- **パスワードを持たない**：パスワードを持たなければ、漏えいしたときの被害と、パスワードの再設定などの作り込みを避けられる。
- **自前の OpenID Connect**：Cloudflare Access に任せると作る量は少ないが、移植するときに作り直しになる（[テックスタック](tech-stack.md)の「移植の余地を残す」に反する）。リモート MCP の OAuth も、自前のログインの上に作れる。
- **アプリ用パスワード**：Reeder や NetNewsWire は、Google Reader API の決まりでユーザー名とパスワードでしかログインできない。ユーザーが決めるパスワードの代わりに、アプリごとに発行して取り消せる秘密を使う（Miniflux や FreshRSS と同じ形）。
- **確認済みのメールで結び付ける**：Google でも GitHub でも、同じ人は同じユーザーとして扱いたい。ユーザーになれるかどうかをすでに許可したメールで決めている（確認済みのメールをその人とみなしている）ので、メールで結び付けても新しい危険は増えない。結び付けたあとは提供元の ID で見分けるので、メールの変更にも強い。
- **許可したメールだけ**：セルフホストで、各自が自分のデプロイ先を持つ前提。知らない人が Google アカウントでログインしても入れないようにする。ホスティングサービスの運営は「やらないこと」に入っている。
- **人ごとに分ける**：家族や小さなチームで 1 つのサーバーを使える。本番にデプロイした人はまだいないので、今ならデータの移行を気にせずに表を作り変えられる。
- **フィードと記事は裏で共有する**：同じフィードを人数分取得せずに済む。Phase 2 の全文抽出や Phase 3 の LLM の処理（要約、分類など）も記事ごとに 1 回で済むので、利点は機能が増えるほど大きくなる。
- **共有を利用者から見せない**：利用者が意識しなくてよいようにし、ほかの人のプライバシーも守る。1 か所だけ、ほかの人がすでに購読しているフィードは、購読したときに最近の記事がすぐ並ぶ（誰も購読していなければ取得を待つ）。珍しいフィードでこの差を観察すれば、誰かが読んでいると推測できるが、許可したメールだけの小さな集まりでは問題にならないと判断した。

## 検討した代替案

- **Cloudflare Access に任せる**：作る量は少ないが、Cloudflare 以外に移すときに作り直しになる。Access を Sendo の前段に置いて守りを重ねるのは、各自の判断でできる。
- **ユーザー名とパスワード**：リーダーアプリとの相性はよいが、パスワードの保存、再設定、総当たり対策を作り込む必要がある。
- **ユーザーの表を持たない（1 人用）**：いちばん軽いが、2 人目を入れるときや MCP の認可を作るときに、データの移行が要る。
- **データを全員で共有する**：今の表をそのまま使えるが、あとで人ごとに分けるときにデータの移行が要る。
- **フィードと記事も人ごとに持つ**：作りはいちばん単純になる（受信箱に配る処理や、最近の記事の補充が要らない）が、取得・全文抽出・LLM の処理が人数分かかる。
- **提供元の ID をユーザーの表に 1 組だけ持つ**：表は 1 つで済むが、Google の人が GitHub でログインすると別人になる（同じメールなら一意制約にぶつかってログインできない）。
- **結び付けは、ログイン中に「提供元を追加する」操作だけにする**：メールで自動的に結び付けるより慎重だが、許可の判定がすでにメールなので守りとしての差は小さく、手間だけが増える。
- **誰でも登録できる**：公開サーバーとして運営するなら要るが、登録の制限や不正対策が要り、「ホスティングサービスの運営はやらない」に反する。

## 見直す条件

- 公開サーバーとして運営する話が出たとき（登録の制限、不正対策）。
- パスキーなど、外部の提供元を使わないログインが求められたとき。
