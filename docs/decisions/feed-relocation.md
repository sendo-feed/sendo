# フィードの移転先候補

- 状態：提案中
- 関連：[仕事の流し方](jobs.md)、[差分同期](sync.md)

## 決定

1. **元のフィードが 404 を返すか、フィードとして解析できない応答を返したら、HTML の `<link rel="alternate">` から移転先候補を探す。** 相対 URL の基準はリダイレクトをたどったあとのページにする。元の URL や失敗した応答の URL に戻る候補は除く。
2. **取得して読めた最初の候補を 1 件だけ記録する。** 候補の URL とリダイレクト先に取得の制限を適用する。404 の本文は先頭 512 KiB まで読み、HTML のリンクはデコード後の先頭 524,288 UTF-16 コード単位まで調べる。候補の確認は 3 件まで、通信の待ち時間は合計 5 秒まで、候補の本文は 1 件 512 KiB までにする。
3. **候補は共有のフィードに持ち、購読の REST API と差分同期で `relocationCandidate` を返す。** 候補がなければ null。あれば確認したフィードの URL、タイトル、サイト URL を返す。読者は元のフィードと見比べて選ぶ。候補の変化は、取得結果と同じ更新の中で購読の変更番号に反映する。
   - 元のフィードの取得に成功したら候補を消す。404 や解析失敗で候補を調べ直したときは、その結果に更新する。通信エラーやレート制限などで候補を調べる応答が得られなければ、直近の候補を使う。
   - 候補は一時的な失敗中でも返す。元のフィードが長期に失敗した場合は、候補と `stalled` の状態が並ぶ。候補の有無で、元のフィードの取得間隔は変えない。
4. **選んだ URL は、既存の購読 API で追加する。** 元の購読と記事の既読・スターは元のフィードに結び付けたままにする。元の購読を外すかどうかは、読者が決める。

## 理由

- 404 のページや、フィードの URL が返す案内ページに、移転したフィードへのリンクが残ることがある。候補を先に確認しておけば、利用者が壊れたリンクを一つずつ試す手間が減る。
- ドメインの再利用でも、読める別のフィードが見つかる。タイトルとサイト URL を併せて示し、関連があるかは読者が判断できるようにする。
- 新しい購読にすると、元の記事の既読・スターを、同じ記事か確かめられない新着へ移す必要がない。

## 検討した代替案

- **最初に読めたフィードへ自動で付け替える。** ドメインが別のサイトに使われていれば、無関係な購読に変わる。
- **元の購読を差し替え、既読やスターを新着に引き継ぐ。** 配信元が移転の際に記事 ID や URL を変えると、どの記事が同じかを安定して判定できない。

## 見直す条件

- 配信元の正当な移転を確かめられる情報が増えたとき。購読の差し替えや既読・スターの引き継ぎを見直す。
- 実際のフィード集で候補が見つからない、または候補の確認にかかる費用が大きいとき。調べる範囲と頻度を見直す。
