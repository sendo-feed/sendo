# 記事の解析

- 状態：提案中
- 関連：[テックスタック](tech-stack.md)（5 の Rust）、[記事の本文](content.md)（1、10、14）、[記事の言語判定](article-language.md)（2、4、5 の前処理と背景の仕事の形）、[記事のキーワード検索](article-search.md)（3 の容量の扱い）、[仕事の流し方](jobs.md)（1、2、4、5、12、13）、[保存容量と古い記事の片付け](retention.md)（2〜4）、[コンテナ版](container.md)（1、2）、[記事のタグ](tags.md)（候補の一覧）、[自動のタグ付け](auto-tagging.md)（埋め込みの使い方）

記事ごとに、候補の語と埋め込みベクトルを作り、全員で使い回す。これを「解析」と呼ぶ。候補の語は、タグの候補の一覧に使う。埋め込みは、タグを記事に自動で付ける判定に使う。候補の一覧は[記事のタグ](tags.md)で、自動の判定は[自動のタグ付け](auto-tagging.md)で決める。意味検索・似た記事・クラスタリング（[機能の一覧](../features.md)の Phase 3）にこの埋め込みを使うかは、それらを作るときに決める。

## 決定

### 解析の仕事

1. **解析は、ページの本文を抜き終えてから、記事ごとに 1 回だけ行い、全員で使い回す。** 処理は Rust で書き、外への取得と DB には触らない（[テックスタック](tech-stack.md)の 5）。読み込めなければ起動しない（[コンテナ版](container.md)の 2）。
   - 新しい記事は、待たずに続けて解析する。ページの本文を抜いた・抜けなかったを記録したら（取り込んだあとの仕事でも、読者が開いたときでも。[記事の本文](content.md)の 10、14）、その記事の解析の仕事をすぐに積む（連鎖）。ページから抜かない記事（`http` ／ `https` の URL のない記事、Discord の投稿）は、取り込んだときに積む。積めなくても、積む側の処理は失敗にしない
   - 解析したあとに本文が変わっても（開いたときの抜き取りが 1 日後に成功したなど）、作り直さない
2. **拾い直しと遡及は、定期実行が受け持ち、遡及の仕事は同時に 1 本だけにする。** 解析を待つ記事は、今の版の解析がなく、次のどれかに当たる記事：本文を抜いた・抜けなかった記録がある、ページから抜かない、取り込んでから 1 時間たった（記録がなければ、そのときある本文で解析する）。
   - 拾い直し：10 分の区切りで、取り込んでから 1 日以内の記事のうち、解析を待つ記事を拾う（積めなかった・落ちた新しい記事）。記事の取り込みの時刻の索引で引く
   - 遡及：解析を待つ記事を、取り込みの時刻と ID の新しい順に解析する。進み具合は 1 行の位置（取り込みの時刻と ID、その遡及が対象にする候補と埋め込みの版）に持つ。版を上げたときと、1 日 1 回の片付けのときに、位置を先頭に戻す。この機能を入れる前の記事、版を上げたときの古い記事、拾い直しの 1 日を過ぎた記事（容量やコンテナの停止で解析できなかったもの）は、ここで拾われる。解析済みの記事は飛ばすだけなので、1 日 1 回全部をたどっても軽い
   - 遡及の仕事はジョブの表に 1 つだけ置く（未着手 1 つ・着手済み 1 つの一意の枠。着手済みがあれば未着手を取り出さない）。1 つの仕事で 100 件まで解析し（飛ばした記事は数えず、たどるのは 1,000 件まで）、区切りを待たずに次の仕事に引き継ぐ。位置を書く文で、位置が読んだときのままであることを確かめる（先頭に戻したのを、古い仕事が上書きしない）。定期実行は、遡及が終わっておらず、遡及の仕事がないときだけ積む
   - 埋め込みの版を上げたあと、その版で初めて遡及が最後までたどり終えたら、その埋め込みの版と終わった時刻を記録する（位置の行が持つ対象の版が前の版から変わっていたときだけ。1 日 1 回の遡及の終わりでは書き換えない）。[自動のタグ付け](auto-tagging.md)が、解析し直した記事の手直しを取り込むのに使う
3. **1 件の失敗で、ほかの記事を止めない。** 記事ごとに例外を受けて先へ進む。記事があることは、書く文の中で確かめる（[記事の言語判定](article-language.md)の 4 と同じ）。Rust が失敗した記事は「失敗」として記録し、同じ版では解析し直さない。本文の置き場が読めない記事は、本文なしで（タイトル、要約、カテゴリだけで）解析する。
4. **保存容量に入らないときは、解析しない。** 推論の前に使用量を読み、上限を超えていれば計算しない。書く文でも容量を確かめ、入らなければ続きを積まず、次の定期実行でやり直す（[記事の言語判定](article-language.md)の 5 と同じ）。作り直せる解析のために、容量による片付け（90% で始まる。[保存容量と古い記事の片付け](retention.md)の 3）を起こさないよう、書いたあとの使用量で次のように止める。
   - 連鎖の解析（新しい記事）：90% 以上になるなら書かない（片付けは 90% 以上で始まる）。後回しにした記事は、拾い直しか遡及が拾う
   - 拾い直しと遡及：80% を超えるなら後回しにする（[記事のキーワード検索](article-search.md)の 3 と同じ）。遡及は、後回しにした記事があれば位置を進めずに止まり、次の定期実行でその記事から続ける（古い版の記事を残したまま、遡及が終わったことにしない）
5. **解析の結果は、記事ごとの解析の行に持ち、候補と埋め込みで版・状態を分ける。** 行は記事の ID、フィードの ID、要約のハッシュ（8）、候補の版・状態・世代、埋め込みの版・状態、ベクトルを持つ。状態は、済み ／ 入力が空 ／ 失敗。候補の抜き方（機能語の一覧や版の例外の一覧など）だけを直したときに、埋め込みまで作り直さないように分ける。仕事は古いほうだけを作り直し、行の更新はそれぞれの版を別々に比べて、古いほうの列だけを書く。
   - 候補の行は、解析のたびに新しくする世代の番号を持ち、1 つの文でまとめて入れる（記事、世代、まとめの鍵が一意）。そのあとで解析の行に、候補の版と世代を書く。これを済んだ印にする。解析の行は、同じ版を上書きしない
   - 候補を読む側は、解析の行と世代が同じ候補の行だけを使う。印を書く前に落ちた解析や、重なって負けた解析の候補の行は、どこからも読まれない。1 日 1 回の片付けが、世代が合わず、作ってから 1 日たった行を消す（実行中の解析の行は消さない）
   - 埋め込みの入力（7）が空の記事は、埋め込みを「入力が空」とする。候補の語は、埋め込みが空・失敗でも、カテゴリや語があれば作る
6. **埋め込みのモデルは、model2vec の potion-multilingual-128M（256 次元の静的な埋め込み）を int8 に縮めたものにする。** 配備中と同じ arm64 で、multilingual-e5-small・e5-base と比べて選んだ（「計測の結果」）。int8 に縮めても当たり方は変わらず、モデルは約 130MB になる。Rust で動かし（model2vec-rs）、モデルはイメージに入れて実行時に取りにいかない。
   - model2vec-rs は `default-features = false` で使い、外への取得の機能（`hf-hub`）を入れない。正規表現は、tokenizers の `fancy-regex`（純 Rust）だけを入れる。tokenizers は正規表現の実装がないとビルドできないので、model2vec-rs と同じ版（0.21）の tokenizers を直接の依存に足し、`fancy-regex` だけを指定して機能をそろえる。model2vec-rs の `onig` と `fancy-regex` の機能は、C の oniguruma か C++ の部品（`esaxx_fast`）も入れるので使わない
   - モデルの用意：元のファイル（`tokenizer.json`、`model.safetensors`、`config.json`。safetensors と JSON だけで、pickle の形式は取らない）を Hugging Face から取る。版はコミットのハッシュで固定し、3 つのファイルの SHA-256、変換したファイルの SHA-256 と一緒にリポジトリに置く。どれかが合わなければ止める
   - 変換：埋め込みの表を行ごとに int8 に縮め、行ごとの倍率を `weights` の表に入れたファイルにする。元のファイルに `weights` か `mapping` の表があれば、変換を止める（行ごとの倍率がずれるため）。変換はリポジトリの中の道具（`scripts/` の Node の道具）で行い、Dockerfile のビルドの段でも、手元（`pnpm dev`、Rust を使うテスト）でも、CI でも同じ道具で用意する。CI は、固定した版をキーにキャッシュする
   - 起動時は、変換したファイルを縮め直さずにそのまま使う（float32 の表を読んでから縮めると、読み込み中に 1.6GiB を超えるため）。ファイルは緩衝層が読み、バイト列を Rust に渡す
   - モデルのライセンスは MIT（トークナイザーの元の bge-m3 も MIT）。固定した版のモデルカード（`README.md`。ライセンスを書いている）を、イメージに一緒に入れる
   - 配備（arm64）で、モデルを読み込んだ sendo は、落ち着いたあと約 870MiB、遡及の最中の最大で約 1.2GiB を使う（「計測の結果」）。動かすサーバーのメモリは 2GB 以上にする（[コンテナ版](container.md)の 2）
   - 遡及の最中も、API の応答と取得はほとんど遅れない（約 1 万件の遡及が約 80 秒で終わり、その間の API の応答は数 ms、遅れた取得はなかった。「計測の結果」）
7. **埋め込みの入力は、タイトル、要約、本文を、モデルの上限のトークン数で切ったもの。** 本文は 8 と同じ選び方と前処理（要約を使わない決まりも同じ）。6 のモデルでは、先頭 2,000 コードポイントで切ってから、512 トークンで切る（model2vec の `max_length` を 512 にする。計測と同じ）。ベクトルは正規化した float32 のリトルエンディアンで、次元を決めた BLOB に持ち、API と同期には出さない。

### 候補の語

8. **候補の出どころは、フィードのカテゴリと、記事の文字の 2 つにする。**
   - フィードのカテゴリ：RSS の `category`、Atom の `category`（`label`、なければ `term`）、JSON Feed の `tags`。取得の仕事が、記事を入れたあと、ページを抜く仕事と解析の仕事を積む前に、記事とは別の表に記事ごとに 10 個まで保存する（記事の行は変えない）。制御文字と対になっていないサロゲートを落とし、前後の空白を除いて、9 の長さと数字だけの決まりに合うものだけを残す（`2024` は残らない。`未分類` のような一般的すぎる語は、人ごとの却下で落とす）。記事を入れたあと、カテゴリを入れる前に落ちたときは、その記事のカテゴリは欠ける（受け入れる）。この機能を入れる前の記事には、さかのぼって付けない（[記事の本文](content.md)の 1 と同じ）
   - 記事の文字：タイトル、要約、本文（抜いた本文があればそれ、なければフィードの本文）を、NFKC で正規化したプレーンテキストにする。要約が、同じフィードのほかの記事の要約とまったく同じなら、その要約は使わない（移行のときに付けた定型文や「続きを読む」のような、記事の中身でない文）。比べるのは、要約を NFKC で正規化し、空白をそろえた文のハッシュ。解析の行にフィードの ID と要約のハッシュを、状態（済み ／ 入力が空 ／ 失敗）によらず持ち、要約が空ならハッシュは NULL にする（比べない）。`(フィードの ID, 要約のハッシュ)` の索引で、同じフィードのほかの記事の解析の行（版によらない）に同じハッシュがあるかを引く。次のときは要約を使い、解析し直さない（受け入れる）：同じ要約の記事のうち最初に解析した 1 件、同時に解析した同じ要約の記事、相手の記事が片付けで消えたあとに入った記事。本文からは、コードブロック（`pre`）と、URL の形をした文字列を除く。リンクの文字（はてなのキーワードリンクなど）と、文中のコード（`code`、`kbd`、`samp`）は残す。本文は先頭 20,000 コードポイントまでで、切り目にかかった最後の語は捨てる。形態素解析はしない
9. **記事の文字からは、英数字の語とカタカナの語を拾う。**
   - 英数字の語：英数字の並びに、中の `.` `-` `_`、末尾の `+` `#`（`C++`、`C#`）、英字の前の `.`（`.NET`）を含めたもの。英字を 1 つ以上含み、大文字か数字を含む語だけを拾う（`Rust`、`iPhone`、`k8s`、`arm64`）。英字が小文字だけの語は拾わない。最初の文字が英小文字で、ドットでつながった語は、本文に紛れたコードなので拾わない（`document.addEventListener`、`navigator.userAgent`）。大文字か数字で始まる語（`Node.js`、`ASP.NET`）と、ドットで始まる語（`.NET`）は拾う
   - 判定の順番：版を捨てる（次の項目）→ 大文字か数字を含むか → ドットでつながった語か → 機能語か。`iOS18.1` は版を捨てて `iOS` を拾い、`python3.13` は版を捨てると小文字だけの `python` になるので拾わない
   - 版は捨てる。拾う語のすぐあとに、空白 1 つかハイフンを挟んで版（`8` のような整数、`3.13` のようなドット付き、`v20` のような `v` 付き）が続けば、版を捨てて語だけを拾う（`Java 8`、`Java-8`、`Python 3.13`、`Node v20` は `Java`、`Python`、`Node`）。語に直結したドット付きの版も捨てる（`Python3.13` は `Python`）。語に直結した整数は、名前の一部であることが多いので残す（`EC2`、`S3`、`Web3`、`Java8`）。例外の一覧（`Web 2.0`、`Industry 4.0` など、離れた版が名前の一部の語）は、版を捨てない。版だけの語は拾わない
   - 拾う語が空白 1 つで 2〜3 個続けば、その並びを 1 つの候補にし、中の語は別には拾わない（`Claude Code`、`Visual Studio Code`）。4 個以上続く並び（英語のタイトルの単語ごとの大文字など）は、語ごとに拾う。機能語（冠詞、前置詞、代名詞、接続詞、助動詞、指示語などの閉じた語類。`The`、`This`、`In`、`of`、`However`、`We`、`It`、`When` など。コードに持つ小さな一覧）は落とす。照らすのは表記そのままで、一覧の語の小文字の形と先頭だけ大文字の形だけ（全部大文字の `IT`、`CAN` は落とさない）。並びの端の機能語を落としてから語の数を数える（`In Rust` は `Rust`、`The Visual Studio Code` は `Visual Studio Code`）。単独の語と、4 個以上の並びを分けたあとの語にも当てる（文頭の `The` だけなら拾わない）
   - カタカナの語：カタカナと長音の並び。`・` で区切る
   - 候補は、表記（NFKC のあと）とまとめの鍵（11）のどちらも 2〜40 コードポイントのものだけを残す。数字だけの候補は拾わない。一般的すぎる語（`アクセス`、`サイズ` など）の停止語の一覧はコードに持たず、人ごとの却下で落とす（[記事のタグ](tags.md)の 3）
10. **候補は記事ごとに 50 個までにする。** まとめの鍵（11）で重なりを除いて数え、同じ鍵の表記が複数あれば先に出たものを残す。フィードのカテゴリと記事の文字の両方に同じ鍵があれば、出どころはカテゴリにする。超えたら、フィードのカテゴリ、記事の中で出た回数の多い順、先に出た順で選ぶ。行は記事の ID、世代、まとめの鍵、表記、出どころ、作った時刻を持つ。
11. **表記の揺れは、まとめの鍵でまとめられるようにする。** 表記は残す。
    - まとめの鍵：NFKC で正規化し、小文字にし、前後の空白を除き、空白を 1 つにそろえる（`Kubernetes` と `KUBERNETES`、全角の `ＡＷＳ` と `AWS` は同じ鍵）
    - 鍵の作り方を変えるときは、候補の版を上げる。解析し直しの間は、古い作り方と新しい作り方の鍵が混ざり、同じ語の数が割れる（受け入れる）。鍵を保存して使う側（タグの照合用の名前など）は作り直さない

### 容量

12. **解析、候補の語、フィードのカテゴリは、保存容量に含め**（[保存容量と古い記事の片付け](retention.md)の 2）、容量による片付けの見積もりにも含める。記事が消えると連鎖で消える。

## 理由

- **解析は、ページの本文を抜いてから 1 回だけにする。** 取り込んだときにフィードの本文で作り、抜いたあとに作り直すと、計算が 2 回になる。埋め込みが変わると、それを使う自動のタグも付いたり外れたりして、読む人には理由が分からない。ページから抜く仕事は取り込んですぐ積まれ、多くはすぐ終わる。抜く仕事が滞っても、1 時間で待つのをやめるので、記事が取り残されない。
- **新しい記事は連鎖で、区切りを待たずに解析する。** 新しい記事は、すぐにタグの判定に使われる。区切りを待つと、本文を抜いてから最大 10 分、タグが付かない。
- **記事ごとに 1 回作り、全員で使い回す。** 記事は共有なので、計算は記事の数に比例し、人の数には比例しない。
- **解析は自動で、新しい記事から遡る。** 解析は共有のデータなので、誰かが依頼しても計算するのは全員分。依頼の口を作ると、API と状態が増える。版を上げたときの作り直しと同じ道で、入れる前の記事も埋められる。新しい記事から進めるので、いま読まれる記事が先に使えるようになる。
- **遡及の仕事は 1 本だけにし、位置で進める。** 遡及が何本も並ぶと、同じ記事を重ねて推論して書き込み、同時に動く仕事の枠（[仕事の流し方](jobs.md)の 2）を埋めて取得を遅らせる（1 件の重さは「計測の結果」）。位置で進めれば、全記事を毎回探し直さずに済む。1 日 1 回先頭に戻せば、拾い直しの 1 日を過ぎて取り残された記事も拾える。
- **model2vec にする。** 計測では、1 件の時間が e5-small（int8）の約 250 分の 1 で、当たり方は 600 件・8 タグで全体に上回った（AUC の平均 0.911 対 0.890、固定のしきい値での F1 0.582 対 0.457。「計測の結果」）。純 Rust で動き、ONNX Runtime の C++ のライブラリが要らない。e5-small が上回ったのは「Claude」「生成 AI」「ゲーム」で、文脈を見るぶん固有の話題や広い概念に強い。potion は縮める前はメモリ（Python 込みで約 1.8GB）とモデル（507MB）が重いが、int8 に縮めればモデルは約 130MB になり、当たり方は変わらない。Rust で読み込むと、メモリの大半はトークナイザー（約 560MiB）で、モデルを縮めても減らない。解析は常に動くので（[コンテナ版](container.md)の 1）、動かすサーバーにはメモリ 2GB 以上を求める（[コンテナ版](container.md)の 2）。
- **版を分け、世代の番号で候補をそろえる。** 候補の抜き方を直すたびに埋め込みまで作り直すと、全記事の推論をやり直すことになる。読む側が世代で候補をそろえれば、途中で落ちても、重なっても、読まれる候補はいつも 1 回の解析の分だけになる。
- **容量の片付けを、解析で起こさない。** 解析は作り直せる派生データなので、そのために記事が片付けられてはいけない。満杯で運用すると使用量は片付けの 80〜90% の間を行き来するので、新しい記事の解析まで 80% で止めると、多くの記事が解析されない。新しい記事は片付けの始まる 90% の手前まで、急がない遡及と拾い直しは 80% までにする。
- **フィードのカテゴリは、ただで手に入る質の高い候補。** Zenn・Qiita・はてなブログなど、多くのフィードが記事ごとに付けている。
- **形態素解析をしない。** 辞書で数十 MB 重くなる。技術の話題の語は、英数字とカタカナの並びでおおむね拾える。英数字は、大文字か数字を含む語だけを拾うと、英語の本文の普通の語（小文字）を落とせる。
- **コードブロックと URL だけを除く。** コードブロックの API の名前やドメインは、記事をまたいで出て候補に居座る。リンクの文字と文中のコードは文の一部で、製品名やコマンド名が入ることが多いので残す。
- **停止語の一覧をコードに持たず、却下で落とす。** 一般的すぎる語は、記事の集まりによって変わる。コードに持つと、直すたびに版を上げて全記事を解析し直すことになる。機能語は閉じた語類で、記事の集まりによって変わらないので、コードに持ってよい。人ごとの却下なら、画面と MCP からすぐに直せる。記事あたりの候補を 50 個にするのは、却下される語が枠を食っても、残したい語が落ちないようにするため（計測では、記事あたりの候補は中央値 13 個、上位 1 割で 30 個に届いた）。
- **同じフィードで同じ要約を使わない。** 移行した「あとで読む」の 2,173 件は、すべて同じ定型文の要約を持っていた。そのまま入れると、候補にその文の語が並び、埋め込みも同じ方向に寄る。要約の文そのものは画面で伝える役があるので、記事の行は変えず、解析の入力からだけ外す。
- **小文字で始まり、ドットでつながった語を拾わない。** 計測では、本文に紛れたスクリプトの語（`document.addEventListener` など）が、同じ 169 件の記事にそろって出た。
- **候補の長さを、表記と鍵の両方で 40 コードポイントまでにする。** タグの名前や却下の鍵の上限に収まり、候補をそのまま選べる。
- **版は捨てる。** 候補の一覧は話題の名前を出すためのもの。`Python 3.13` のような候補は選ばれず、版ごとに数が割れるだけになる。版ごとのタグが欲しい人は、名前を打てば作れる。語に直結した整数は、`EC2`、`S3`、`Web3`、`PS5` のように名前の一部であることが多いので残す。

## 検討した代替案

- **multilingual-e5-small を使う**：広い概念のタグには少し強いが、1 件 0.5 秒かかり、当たり方は全体でやや劣った。類似度が高い値に固まり、全体で 1 つのしきい値では分けにくい。ONNX Runtime の C++ のライブラリも要る。
- **停止語の一覧をコードに持つ、または共有の停止語の表を DB に持つ**：コードに持つと直すたびに全記事を解析し直す。共有の表は、人ごとの却下と仕組みが 2 つになる。
- **移行のデータの要約を DB で書き換える**：解析の入力からは消えるが、画面で「公開日時は不明」を伝える役がなくなり、記事の本体を取り込んだあとで変えることになる（[差分同期](sync.md)の 7）。
- **取り込んだときにフィードの本文で解析し、ページの本文を抜いたら作り直す**（[記事の言語判定](article-language.md)の 5 に近い形）：早く使えるが、計算が 2 回になり、使う側の結果が入れ替わる。
- **入れる前の記事の解析を、reader から依頼する**：上の理由で、依頼の形が合わない。
- **遡及も定期実行の区切りごとに拾う**：作りは簡単だが、区切りごとに仕事が増えて重なる。全記事を毎回探し直すことになる。
- **候補の語を形態素解析で抜く**：漢字の複合語も拾えるが、辞書で重くなる。
- **本文から、文中のコードとリンクも除く**（[記事の言語判定](article-language.md)の 2 と同じ）：雑音は減るが、文の一部の製品名やコマンド名、キーワードリンクの語を落とす。
- **版を残し、鍵でまとめる**（`Java 8` を親の鍵 `Java` にまとめ、画面では「Java（Java 8、Java 21 ほか）」と出す）：版ごとの表記を見せられるが、まとめる条件（親の語が単独でも出ているか）、見出しの選び方、候補を選んだときの名前の決まりが要り、重い。版の付いた候補は選ばれないので、得るものが少ない。
- **語に直結した整数も捨てる**：`Java8` も `Java` になるが、`EC2` が `EC`、`S3` が `S` になり、名前を壊す。

## 見直す条件

- 記事が増えるなどして、遡及・連鎖の解析での取得や API の遅れが目に見えて大きくなったとき（「計測の結果」の配備での値と比べる）。解析を動かす時間帯や数を絞る。
- メモリ 1GB のサーバーで動かしたいという声が出たとき。トークナイザーの語彙を日本語・英語などに絞る（区切り方が変わるので、当たり方を測り直す）、トークナイザーを軽く作り直す、などを考える。
- 広い概念のタグ（「生成 AI」など）の当たり方が足りないとき。e5-small のような文脈を見るモデルを、もう一度比べる。
- 候補に漢字の複合語が出ないことで、欲しい語が拾えないとき。形態素解析を考える。
- 候補に、英語のタイトルの言い回しなど、意味のない並びが多く出るとき。並びの切り方と機能語の一覧を見直す。
