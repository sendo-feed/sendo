## 決定

1. **言語は TypeScript、フレームワークは Hono** にする。ただし、CPU を多く使う処理は Rust で書く（5）。
2. **Sendo は、コンテナ（Node ＋ SQLite）だけで動かす。** Cloudflare（Workers・D1・Queues）では動かさない。動かし方と配り方は[コンテナ版](container.md)に書く。
3. **実行環境の入出力は、緩衝層（`src/platform/`）の内側に閉じ込める。** インターフェース（`Platform`）を `src/platform/` に、Node での実装と入口を `src/platform/node/` に置く。
   - 対象は、DB、ジョブキュー、定期実行、ファイルの置き場、外への取得、Rust のネイティブのモジュール、設定
   - アプリ（`api/`、`jobs/`、`fetcher/` など）は `Platform` 越しに使い、テストでは差し替える
4. **開発ツールは pnpm・Biome・Vitest** にする。テストは Node で動かす。Rust は cargo・rustfmt・clippy で検査し、`pnpm check` から呼んで CI でも通す。
5. **CPU を多く使う処理は、Rust で書き、napi-rs で Node のプロセスに読み込む。**
   - 対象は、記事のページからの全文抽出、言語判定、画像の処理、埋め込みの計算やクラスタリングなど。速いほどよいので、新しく作る重い処理は、まず Rust で書くことを考える
   - API、同期、認証、DB の読み書き、仕事の流し方は TypeScript のままにする
   - Rust のコードは `crates/` に置き、Cargo のワークスペースにする。処理の本体の crate と、Node から呼ぶための結び（napi-rs）の crate を分ける
   - ネイティブのモジュールを読み込むのは `src/platform/node/` だけにする。アプリは `Platform` 越しに使う
   - 重い処理は napi-rs の非同期の仕事（`AsyncTask`）として libuv のスレッドプールで動かし、イベントループを止めない
   - Rust の側は、外への取得と DB に触らない。取得（`toFetchableUrl` と接続先の IP の確認）と書き込みは TypeScript の側で行う。Rust には取ってきたバイト列を渡し、結果を返してもらう
   - 処理の本体の crate は `#![forbid(unsafe_code)]` にする。panic はエラーにして JS に返し、プロセスを落とさない
6. **ほかの言語で書かれた既存のサーバーも、機能に見合えば使う**（たとえば関連検索の RustXNG）。sendo のプロセスには入れず、別のコンテナとして並べて HTTP で呼ぶ（[コンテナ版](container.md)の 7）。どの機能で何を使うかは、その機能の決定ファイルに書く。

### 緩衝層で隠すもの

| 役割 | 実装 |
|---|---|
| DB | SQLite のファイル ＋ libsql ＋ Drizzle。Postgres は今は支えない |
| ジョブキュー | SQLite のジョブの表に積み、同じプロセスで回す（[仕事の流し方](jobs.md)） |
| 定期実行 | 同じプロセスのタイマー |
| ファイルの置き場 | ボリュームの上のファイル |
| 外への取得 | 接続する IP アドレスも確かめる `fetch` |
| 意味検索（Phase 3） | sqlite-vec |
| 重い処理 | Rust（napi-rs）の実装を渡す（5） |
| 設定・秘密情報 | 環境変数 |

### 守る規約

ここの規約は、アプリ本体（`src/`）に適用する。手元の Node で動かす道具（`scripts/` の管理用のコマンド、`*.config.ts` などの設定ファイル）は対象外とし、`node:*` を使ってよい。

- アプリは Web 標準の API（`fetch`、`Request`、`Response`、Web Crypto、Streams）を使い、`node:*` のモジュールには頼らない。`node:*` を使ってよいのは、緩衝層の実装（`src/platform/node/`）だけにする。この規約は Biome の `noNodejsModules` で、`src/` を機械的に検査する。
- 定期実行とジョブキューの入口は薄くし、中身は普通の関数（例：`runScheduled(platform, time)`）にする。テストから同じ関数を呼べるようにするため。
- `crates/` の Rust は、外への取得と DB に触らない（5）。取得の守り（SSRF）と冪等な書き込みを、TypeScript の側の 1 か所に保つため。
- 書き込みは、対話的なトランザクションにも batch にも頼らず、何度実行しても同じ結果になる（冪等な）形で組み立てる。途中で失敗しても、やり直せば正しい状態になるようにする（例：一意制約と「あれば飛ばす」で重複を防ぐ、記録は処理の最後に書く）。複数の書き込みを必ずまとめて反映する必要が出たら、そのときに libsql のトランザクションを緩衝層の DB に足す。
- 件数などの集計は、別の列に持たずにその都度数える。持つ場合は、いつでも数え直せるようにする（途中で失敗したときにずれないように）。
- スキーマとマイグレーションは SQLite の方言で書き、1 組だけ持つ。

## 理由

- **コンテナだけにする：**
  - Sendo がほかの RSS リーダーと違う価値を出すのは、記事のページからの全文抽出、言語判定、これから作る LLM や埋め込みの機能など、CPU を多く使う処理。Cloudflare の無料プランでは、CPU（1 回 10ms、実測でも 1〜2 秒で止まる）、1 回の実行のクエリ数（50）、外への取得（50 回）、D1 の容量（500MB）と書き込み（1 日 10 万行）に収まらず、これらを載せられなかった（[コンテナ版](container.md)の「理由」）
  - 載せられる範囲だけの Cloudflare 版は、普通の RSS リーダーと変わらず、Sendo を使う理由にならない。2 人で話し合い、そう結論した
  - 2 つの版を保つ手間（緩衝層の 2 つの実装、workerd と Node の 2 組のテスト、封筒や `QUERY_BUDGET` などの上限に合わせた作り、デプロイの 2 つの手順）が、機能を作る速さを削っていた
- **緩衝層を残す：** 版を切り替えるためではなく、実行環境の入出力を 1 か所に集めるために残す。アプリをテストで差し替えやすくし、外への取得の守り（SSRF）やネイティブのモジュールの読み込みを、ほかの場所から迂回できないようにする。
- **アプリは Web 標準の API を使う：** Hono、Drizzle、Web 標準の API で書いたアプリは、ファイルやソケットに直接触らない。入出力が緩衝層に集まっていれば、テストで本物のファイルやネットワークを使わずに済み、守りの確かめも 1 か所で済む。
- **reader との共有：** sendo-reader も TypeScript なので、OpenAPI から生成した型をそのまま共有できる。MCP の TypeScript SDK も成熟している。
- **重い処理を Rust で書く：**
  - 重い処理を速く動かすと、応答が早くなり、同じ機械で多くの処理を回せる。Rust なら、JS より速く、メモリも少なく済む見込みが高い
  - 開発者が Rust を好み、書き続けられる。いくつかの言語を使い分けることは、手間として受け入れる
  - 埋め込みの計算（ONNX Runtime）や画像の処理など、ネイティブのライブラリをそのまま使える
  - 本体は TypeScript のままなので、reader と型を共有することは崩れない
- **napi-rs で同じプロセスに読み込む：**
  - 呼ぶたびの通信の往復がなく、本文をバイト列のまま渡せる。いちばん速い
  - 1 つのコンテナ・1 つのプロセスで動かす形（[コンテナ版](container.md)の 7）を崩さない
  - スレッドプールで動かせば、重い処理の間も API の応答が止まらない
- **Rust の側で取得と DB に触らない：** SSRF の守りと冪等な書き込みは TypeScript の側にある。Rust の側にもう 1 組作ると、片方だけが直って食い違う。
- **冪等な書き込みを続ける：** 仕事は失敗するとやり直し、プロセスは途中で止まることがある。何度動かしても同じ結果になる書き込みなら、やり直しにも二重の実行にも壊れない。今のコードはこの形で揃っていて、トランザクションを使える環境になっても書き直す理由がない。
- **既存のサーバーを別のコンテナにする：** RustXNG のような AGPL のサーバーは、別のプロセスとしてネットワーク越しに使えば、sendo のライセンスに影響しにくい。上流の更新も、sendo とは別に取り込める。

## 検討した代替案

- **Cloudflare 版とコンテナ版の 2 つを、同じコードから作り続ける**：サーバーを持たない人も無料で使える。ただ、Cloudflare 版に載るのは普通の RSS リーダーの範囲だけで、Sendo を選ぶ理由にならない。2 つの版を保つ手間も大きい（理由を参照）。
- **Cloudflare だけにし、Workers Paid（月 5 ドル）を前提にする**：CPU の上限は 1 回 30 秒（最大 5 分）に広がるが、なくならない。重い機能ごとに上限に合わせた工夫を続けることになり、使う人みんなに月 5 ドルを求める。ネイティブのライブラリ（ONNX Runtime など）も使えない。
- **Go の単一バイナリ ＋ SQLite**：VPS や Docker にはとても載せやすいが、reader と言語が分かれ、MCP の SDK や OpenAPI の型の共有を手放す。今の TypeScript のコードも書き直しになる。
- **書き込みをトランザクションや batch でまとめる**：途中まで書いた状態が残らない。ただ、今のコードは冪等な書き込みで揃っていて、ジョブのやり直しとも相性がよい。必要になった箇所から足す。
- **サーバー全体を Rust で書く**：いちばん速い。しかし、MCP の TypeScript SDK、zod から作る OpenAPI、reader との型の共有を手放し、API・同期・認証を書き直すことになる。
- **重い処理を、Rust のサイドカー（localhost の HTTP）にする**：言語の境目ははっきりする。ただ、呼ぶたびに通信が往復し、本文を送り直す。プロセスが増え、1 つのコンテナ・1 つのプロセスで動かす形（[コンテナ版](container.md)の 7）も崩れる。
- **Rust を Wasm にして、Node で動かす**：CPU の種類ごとのビルドが要らない。ただ、スレッドが使いにくく、ネイティブのライブラリ（ONNX Runtime など）を使えない。
- **Bun**：起動が速く、テストランナーも速い。ただ、napi-rs のモジュールと libsql の互換に不安が残る。パッケージマネージャーとしては速いが、pnpm で揃えた守り（公開から 14 日待つ、インストール時のスクリプトの許可制、宣言していない依存を使えない厳しさ）を優先した。
- **Vite+（Oxlint・Oxfmt）**：Biome から替える案。速く ESLint 互換のルールが多いが、lint と整形が1つで済み、整形が成熟した Biome を選んだ。

## 見直す条件

- Postgres を支える必要が出たとき（[コンテナ版](container.md)の「見直す条件」）。
- Rust のツールチェーンと、CPU の種類ごとのネイティブのモジュールのビルドが、CI とコントリビューターの負担に見合わなくなったとき。
- JS と Rust の間でデータを写す手間が、速くなった分を食うと分かったとき。境目の引き方（何を渡し、何を返すか）を考え直す。
- サーバーを持たない人にも使ってもらう必要が出たとき。コンテナを動かせるホスティング（無料の枠があるもの）を勧めるか、軽い版を作るかを考える。
