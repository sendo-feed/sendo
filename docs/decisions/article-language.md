# 記事の言語判定

- 状態：合意済み
- 関連：[記事の本文](content.md)、[コンテナ版](container.md)、[テックスタック](tech-stack.md)、[記事の翻訳](translation.md)

## 決定

1. **記事の主言語を、LLM を使わず Lingua 1.8.0 の通常モードで判定する。** 候補は全 75 言語とし、日英だけには絞らない。Rust に実装し、判定器をプロセス内で共有する。napi-rs の `AsyncTask` で動かし、外部への通信と DB の操作はしない。アプリは `Platform.languageDetection` 越しに利用する。
2. **HTML の自然文だけを判定する。** `script`・`style`・`svg`・`math` と `pre`・`code`・`kbd`・`samp` を除き、URL と余分な空白を落とす。2,000 文字以下なら全文、それより長ければ先頭・中央・末尾から各 666 文字を取り、改行でつなぐ。文字数は UTF-8 のバイト数ではなく Unicode の文字で数える。
3. **短文と不確実な結果は保留する。** 判定入力の文字（Unicode Alphabetic）が 40 字未満なら `insufficient`。それ以上でも最上位の生スコアが 0.8 未満、または次点との差が 0.2 未満なら `uncertain`。どちらも言語は `und` とする。この閾値は初期の保守的な条件であり、スコアを正解確率として扱わない。
4. **結果は記事とは別の `article_languages` に、記事 ID × 入力元で保存する。** 入力元はフィード本文 `feed`、抽出したページ本文 `page`、タイトルと要約 `metadata`。言語は `ja`・`en` などの ISO 639-1（不明は `und`）、状態、生スコア、次点との差、判定した入力の SHA-256、判定器名、前処理・閾値を含む単調増加の `pipeline_revision` を持つ。
   - 本文の条件を通った結果は `detected`。本文がなくタイトルと要約で条件を通った結果は `provisional` とし、本文の判定とは区別する。
   - フィード本文がある記事は `feed`、ない記事は `metadata` を判定する。ページ本文を得たら `page` を別に判定し、先の結果を上書きしない。読者の翻訳先言語や翻訳の要否は共有の判定結果に入れない。
   - 記事を取り込んだあとは本文の入力元も不変とする。方式を変えたら版を上げ、新しい版だけが古い版を置き換える。同じ版の保存は何度行っても更新せず、遅れて完了した古い仕事でも新しい結果に戻さない。
   - 記事の存在を INSERT と同じ文で確かめる。記事を消すと外部キーで結果も消す。人ごとの変更番号や差分同期には載せない。
5. **判定と保存は、取得や本文の配信を止めない背景の仕事にする。** 起動時と 10 分ごとの定期実行で、未処理または古い版の入力元を拾う。1 つの仕事で 10 件までを処理し、進捗があれば次の仕事に引き継ぐ。保存前に落ちても、次回は未処理のまま残る。情報不足・不確実も処理済みとして残し、同じ入力を繰り返し判定しない。
   - 容量の上限を保存と同じ文で確かめる。保存できなければ連続して仕事を積まず、次の定期実行でやり直す。派生行と索引の見積もり（1 行 512 バイト）を容量集計と記事の削除見積もりに含める。
6. **主言語を翻訳の判断材料として保存し、混在言語の判定は翻訳の条件に使わない。** 主言語が日本語でも外国語の引用は含まれ得る。混在候補は人名やクレジットも拾うため、記事全体の翻訳が必要という意味にはしない。翻訳の実行と、判定結果を読者に返すことは、この機能の範囲外とし、[記事の翻訳](translation.md)で扱う。

## 理由と検証結果

### 評価の条件（2026-11-17）

購読中の 72 フィードから最近の 800 記事を読み取り専用で抽出した。フィード本文 175 件、ページ本文 238 件で、同じ記事の入力元の重複を含め 413 本文。フィードごとに最近 12 記事までを選び、英語を増やすため Martin Fowler の記事を追加した。

本文の先頭・中央・末尾の抜粋をエージェントが確認して、日本語 59 記事・英語 30 記事（28 フィード）の参照ラベルを付けた。89 件はすべてページ本文。人間や独立した複数人による評価ではなく、英語 30 件は Fowler の 1 フィードに偏る。以下の一致数を、全言語の一般的な正解率や未知の配信元の保証には使わない。

whatlang 0.18.0 と Lingua 1.8.0 を Rust 1.99.0 の release ビルドで比較した。候補言語は各ライブラリの全言語。`RAYON_NUM_THREADS=1` とし、方式を並行には動かさず、初回の後に順序をずらして 5 巡した各記事の中央値を集計した。p95 はその値の nearest-rank（`ceil(n × 0.95)` 番目）。時間は検出部分だけで、HTML の前処理・DB・通信・napi は含まない。

### 判定器の比較

macOS arm64、先頭・中央・末尾の合計約 3,000 字（区切りを含め最大 3,002 字）での結果。

| 判定器 | 参照ラベルとの一致 | 中央値 | p95 | プロセス最大 RSS |
|---|---:|---:|---:|---:|
| whatlang | 80 / 89 | 0.023ms | 0.178ms | 19.8MiB |
| Lingua low accuracy | 75 / 89 | 3.171ms | 23.149ms | 190.7MiB |
| **Lingua 通常** | **89 / 89** | **0.487ms** | **12.313ms** | **183.2MiB** |

RSS は 2,839 ケースを読み込む検証プロセス全体の最大値で、ライブラリ単体の増分ではない。両ライブラリと全言語を含む検証実行ファイルは約 280MiB。今回 low accuracy が通常モードより遅かったことも、一般的な性能の順序を保証しない。

whatlang は技術用語や顔文字の混じる日本語に誤りがあり、誤判定 9 件のうち 1 件はスコア 1 かつ `is_reliable=true` だった。Lingua low の誤判定 14 件も、すべて最高スコア 1・次点との差 1。速さや高スコアだけで選ばず、今回の本文で一致した通常モードを選ぶ。

### 入力長と Linux コンテナ

同じ 89 記事で入力の取り方を変え、3 巡した。Lingua 通常は次の全方式で 89 / 89 件が一致した。

| 入力 | 中央値 | p95 |
|---|---:|---:|
| 約 1,000 字の 3 地点抜粋 | 0.235ms | 6.548ms |
| **約 2,000 字の 3 地点抜粋** | **0.411ms** | **8.655ms** |
| 約 3,000 字の 3 地点抜粋 | 0.490ms | 11.946ms |
| 先頭 3,000 字 | 0.481ms | 11.895ms |
| 全文（最大 55,535 字） | 0.511ms | 43.098ms |

2,000 字程度なら文脈を残しつつ、長い全文の処理時間を抑えられた。これは 3 地点を連結した主言語の判定で、各地点が同じ言語だと確認した結果ではない。

通信を無効にした Linux arm64 コンテナ（1 CPU、メモリ上限 1GiB）でも、約 2,000 字の主言語は 89 / 89 件が一致し、中央値 **0.549ms**、p95 **11.295ms**、最大 RSS **184.1MiB** だった。別途、配備中と同じアプリのイメージの隔離コンテナで、作成したテスト文章 52 件を実行し、中央値 0.210ms、p95 4.476ms、最大 RSS 178.4MiB、初回の 1 件目は 429ms だった。入力が違うため、2 つの環境の速さは直接比較しない。

Mac と Linux の 141 ケースでは、主言語・仮の保留条件の通過・検出した言語集合が一致した。共有した判定器を 4 スレッドから呼ぶ実行も終了した。ただし、この時点では Rust 単体であり、アプリに組み込んだときのメモリ増分、API の応答性、napi の検証ではない。初回の読み込み時間はばらつくので、warm 時の数値を起動直後の保証値にはしない。

### 前処理・保留・混在

日英と仏独西中韓の説明文、短文、コード、技術用語、引用、言語が切り替わる文章を作って比較した（最初の 42 件に追加して計 52 件）。作成文は実記事の精度評価とは区別する。

- 生の JavaScript や SQL は英語と高スコアで判定され、日本語の説明よりコードが多いと英語になった。`pre`・`code` 等を除いた場合は、コードのみが空になり、残った日英の説明文を正しく判定できた。
- `Rust`・`Go`・`AI` などの短い入力には別言語を返す。決定 3 の条件で短文 14 件と、タグから除外した純コード 3 件を保留し、評価記事 89 件はすべて通過した。生コードや言語混在までこの条件で防げるわけではない。
- 日英が混ざる文章を、日本語だけとスコア 1 で判定する例があった。高スコアは言語混在がないことを保証しない。

| 混在の調べ方 | 混在作成文の検出 | 単一言語作成文の誤検出 | 実記事 89 件の混在候補 | 実記事の中央値 / p95 |
|---|---:|---:|---:|---:|
| 全体の主言語だけ | 0 / 10 | 0 / 37 | 0 | 0.549 / 11.295ms |
| 3 地点を別々に判定 | 2 / 10 | 0 / 37 | 0 | 1.069 / 24.519ms |
| 段落・文を最大 6 個判定 | 8 / 10 | 0 / 37 | 7 | 0.737 / 26.967ms |
| Lingua 組み込み混在 API | 9 / 10 | 1 / 37 | 34 | 11.432 / 121.809ms |

上表はローカル Linux の結果。段落・文は各 400 字までで、決定 3 の条件を通ったものを候補に加えた。組み込み API は区間に文字が 40 字以上あるものを加えた。単一言語の 37 件からは、意図的に前処理を省いた生コード 5 件を除いた。

段落・文方式が見逃した 2 件は 40 字未満の短い外国語引用。実記事の候補 7 件には引用・参考文献・画像クレジット・英語版への案内・人名の列挙が含まれた。組み込み API は英語の説明文の一部をフランス語にする誤検出もあった。候補数は実記事の混在判定の正解率ではない。組み込み API は[上流でも実験段階](https://github.com/pemistahl/lingua-rs#107-detection-of-multiple-languages-in-mixed-language-texts)であり、初期の翻訳条件には使わない。

### 保存の試作

ローカル SQLite に、800 記事の ID と、入力元別の 1,213 記録（metadata 800・feed 175・page 238）を保存した。試作は比較のため本文のある記事にも metadata を作ったが、製品は本文がない場合だけ metadata を作る。

状態は `detected` 388、`provisional` 747、`insufficient` 74、`uncertain` 4。本文由来の 413 記録中 388 記録が仮の条件を通り、25 記録は保留になった。これは条件の通過数であり、388 記録すべての正解を確認したという意味ではない。

- 同じ保存を繰り返しても更新 0 件。137 件で中断した状態から再開しても重複しなかった。
- 記事を削除すると対応する 3 記録が連動して消え、削除済みの記事に再保存しても復活しなかった。
- 版 2 の保存後に版 1 の実行が完了しても、版 2 は上書きされなかった。
- 各文を autocommit で動かし、複数文のトランザクションには頼っていない。
- 記事 ID だけの仮の表と索引を含め 360KiB。製品のスキーマや索引の実使用量の保証には使わない。

### 根拠の保持と限界

購読本文・購読先・記事 ID・認証情報・配備先固有の値は公開リポジトリには入れない。実記事はローカルで処理し、実サーバーの隔離コンテナには作成文と実行ファイルだけを渡した。本番 DB やサービスの設定は変更していない。

検証ハーネスは `whatlang=0.18.0`・`lingua=1.8.0` を固定した独立の Cargo プロジェクトで、入力 JSON を読み、候補の生スコア・次点との差・各回の時間を JSON に出した。参照ラベル・原データ・出力・コードの SHA-256 はローカルの検証資料に保存した。この記事の表は保存済み JSON の集計で、実装のテスト結果や本番での成功率に読み替えない。

英語の配信元を増やした実記事評価、日英以外の実記事評価、閾値の校正、混在文や固有名詞の扱いは残っている。今回の根拠で採用するのは、主言語を先に調べて保存し、後の翻訳の判断材料にするところまで。

## 検討した代替案

- **whatlang**：速く軽いが、今回の日本語の技術記事で誤りが残った。通常の Lingua が資源の上限に合わなくなったら、対象の本文で測り直す。
- **Lingua low accuracy**：今回の一致数・時間の両方で通常モードを下回った。
- **タイトルやフィードの申告言語だけ**：本文とは言語が違う場合がある。本文のない場合の暫定結果に限定する。
- **LLM で言語を判定**：翻訳が不要な記事を外部へ送る前に判定したいので使わない。
- **日英だけに絞る**：ほかの言語も日英のどちらかに押し込むため採らない。

## 見直す条件

- 実記事の追加評価で、翻訳の誤起動や必要な翻訳の見逃しが目立ったとき。
- 起動・メモリ・並行ジョブ・API の応答を測り、資源の負担が問題になったとき。
- 判定器や前処理を変えるとき。評価をやり直し、`pipeline_revision` を上げる。
- 混在文の部分翻訳を作るとき。
