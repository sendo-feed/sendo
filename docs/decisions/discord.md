# Discord チャンネルの購読

- 状態：提案中
- 関連：[ユーザーと認証](accounts.md)、[仕事の流し方](jobs.md)、[差分同期](sync.md)、[記事の本文](content.md)、[画像の中継とサムネイル](images.md)

## 決定

1. **ブラウザの Integrations から Discord を接続する。** デプロイごとに Discord アプリと Bot を用意する。すでに Sendo にログインしている人が OAuth の `identify` で Discord アカウントを確認する。2 つのアカウントの結び付きだけを保存する。Bot の追加はサーバーを管理できる人が行う。
2. **1 チャンネルを 1 フィードとして購読する。** チャンネル URL を受け、接続した本人と Bot の両方が閲覧・履歴読み取りをできる場合だけ受け付ける。通常のテキストチャンネルとアナウンスチャンネルを対象にする。年齢制限付きのチャンネルは対象から外す。
3. **Discord の REST API を使い、購読したときに直近の投稿を最大 20 件取り込み、そのあとは新着を取得する。** 既存の定期ジョブで動かし、配布が済んだメッセージ ID を記録する。1 投稿を 1 記事として、テキスト、埋め込みの文字の部分、投稿者、投稿時刻、元投稿へのリンクを持つ。添付ファイル、埋め込みの画像・サムネイル・動画、元投稿の編集の反映は扱わない。
4. **Discord のフィードと記事は接続ごとに持つ。** 同じチャンネルの購読でも、別のユーザーに投稿を配らない。接続、連携解除、チャンネルの新規購読は Sendo のブラウザセッションで行う。Discord の購読は OPML に含めない。
5. **取得のたびにアクセスを確かめる。** Discord で閲覧権限を失ったことを検出した場合、購読を解除し、保存した記事をスター付きも含めて削除する。Sendo 側で個別に購読を解除した場合や、Discord との接続を解除した場合も同じ。クライアントには既存の差分同期で削除を伝える。
6. **テキストか埋め込みの文字がある投稿には、すべて本文を置く。** 本文は、フィードの本文と同じに置いて配る（[記事の本文](content.md)の 2〜7）。要約と同じ中身でも置く（[記事の本文](content.md)の 1 の例外）。ページを取りにいかず、ページから本文を抜く処理（同じく 11、12、17〜21）も当てない。
   - 本文は、テキストのあとに、埋め込みごとに作者の名前、タイトル（URL があればそのリンク）、説明、フィールドの名前と値、フッターの文字を並べる
   - Discord の Markdown とメッセージの書式（メンション、チャンネル、絵文字、時刻）は解釈せず、文字のまま出す。改行は保ち、http ／ https の URL はリンクにする
   - タイトルはテキストの 1 行目、要約はテキスト。空白だけのテキストは、テキストのないものとして扱う
   - テキストのない投稿は、タイトルか説明のある最初の埋め込みから、タイトル（なければ説明の 1 行目）を記事のタイトルにし、説明を要約にする。そういう埋め込みもなければ、タイトルは「Discord の投稿」、要約はなし
   - 本文は取り込んだときに決める。取り込み済みの投稿と、あとから付いた埋め込み（リンクのプレビューなど）には、さかのぼって付けない
   - 置いた本文を、全文（`source=page`。[記事の本文](content.md)の 10）としても返す。応答の `source` は `page`。サニタイズと画像の書き換え（同じく 2、7）は、フィードの本文と同じに返すときにも通す
   - 抜いた本文の表（同じく 13）には写さず、返すときに置き場から読む。抜けなかった記録も付けない（同じく 14 の記録と、1 日たってからの取り直しは当てない）
   - 置き場に本文がない投稿（テキストも埋め込みの文字もなく、本文を置いていない投稿を含む）は、全文も 404（`page_content_unavailable`）。置き場を読むのに失敗したときは 5xx を返す（404 にせず、抜けなかった記録も付けない）
7. **フィードのアイコンは、Discord のサーバーのアイコンにする。** 権限を確かめるために取得のたびに読むサーバーの情報（5）から、Discord の CDN の URL を組み立てる。アイコンを探す取得も、確かめる取得もしない（[画像の中継とサムネイル](images.md)の 8 の探し方と間隔は当てない。画像かどうかは、配るときに中継が確かめる）。サーバーにアイコンがなければ null。配り方は、ほかのフィードのアイコンと同じ（同じく 9）。

## 理由

- Bot の設置とチャンネルの権限を Discord 側で管理できる。公開 RSS と扱いを分けることで、ある人の権限で取得した投稿が別の人の購読に入るのを防げる。
- 新着を定期取得する形なら、常時接続する仕組みを置かず、フィードの取得と同じジョブの仕組みで扱える。
- 購読したときに直近の投稿を取り込むと、公開フィードと同じく、最初から投稿のペースで取得の間隔が決まる（[仕事の流し方](jobs.md)の 7）。購読より後の投稿だけを対象にすると、最初の取得は必ず 0 件になり、間隔が上限の 1 日になる。購読できるのは本人が履歴を読めるチャンネルだけなので（2）、本人が読める範囲は広がらない。20 件あれば、間隔を決めるのに足り、受信箱を古い投稿で埋めない。
- 通知の Bot や Webhook は、中身を埋め込みだけで送ることが多い。埋め込みを捨てると、記事にタイトルも本文も残らない。
- Discord の投稿は認証が要るので、記事のページから本文を抜けない（[記事の本文](content.md)の B）。要約は一覧や同期に使う文字で、改行とリンクを保った形で読めるのは本文だけなので、テキストだけの投稿にも本文を置く。
- 置いた本文は、Sendo が取り込む範囲（3 のテキストと埋め込みの文字）の全部で、Sendo がそれ以上を得る手段はない。全文としても返せば、クライアントは、ほかのフィードで全文が取れたときと同じ道で扱え、Discord の投稿かどうかを見分けずに済む。中身が同じなので、抜いた本文の表に写して二重に持たない。
- 添付ファイルの URL には、Discord が期限付きの署名を付けるので、保存した URL があとで切れる。埋め込みの画像も、添付ファイルを指すことがある。文字の部分だけなら、保存したものが切れない。
- Discord の Markdown やメッセージの書式を変換すると、Discord の書き方の変化に追いつく必要があり、メンションなどは名前を引く取得も要る。文字のままでも、通知の Bot の投稿は読める。
- サーバーの情報は、権限を確かめるために取得のたびに読んでいるので、アイコンのための取得が増えない。チャンネルの URL のページは Discord のアプリなので、サイトのページから探すと、サーバーのアイコンではなく Discord のアイコンになる。

## 検討した代替案

- **埋め込みの文字を要約にだけ入れる**：本文を置かずに済むが、ページから本文を抜けないので、記事を開いても改行とリンクを保った形で読めない。
- **埋め込みの画像も本文に入れる**：見た目は Discord に近づくが、添付ファイルを指す画像は、上の理由で URL が切れる。外の画像だけを選んで入れる区別は、まだ要らない。
- **全文は返さず、クライアントが Discord の投稿を見分けて全文を頼まない**：`source=page` をいつもページから抜いた本文の意味に保てるが、クライアントは、フィードの URL の形などに頼るか、記事やフィードに Discord の投稿かを表す印を足して見分けることになり、どのクライアントにも同じ手当てが要る。
- **全文は返さず、クライアントがフィードの本文を出しているときは「全文が取れない」を知らせない**：印が要らないが、本文が途中までしか入っていない公開フィードでも、元の記事で続きを読める手掛かりが消える。
- **置いた本文を、抜いた本文の表にも写す**：全文はいつもその表から読めばよくなるが、同じ本文を置き場と DB に二重に持ち、写す処理と、写したあとの食い違いが増える。

## 見直す条件

- 画像や添付ファイルだけの投稿が多く、記事として読めないことが目立ったとき。
- Markdown の記号やメンションの ID が、文字のままでは読みにくいと分かったとき。
- 置く本文の範囲を変えるとき（画像や添付ファイルを入れるなど）。全文として返すものも、同じく変わる。
