# コンテナ版

- 状態：提案中
- 関連：[テックスタック](tech-stack.md)（2 つの版、緩衝層）、[仕事の流し方](jobs.md)（Cloudflare 版の仕事の運び方と、実測した上限）、[デプロイ](deploy.md)（Cloudflare 版のデプロイ）、[コストの見積もり](../cost.md)

Sendo は、Cloudflare 版とコンテナ版の 2 つの版を、同じリポジトリの同じコードから作る（[テックスタック](tech-stack.md)の 2）。

これまでは Cloudflare だけを対象にしてきた。しかし、これから作る機能（記事のページからの全文抽出、画像の縮小、埋め込みの計算など）を考えると、Workers の CPU 時間には収まらなくなってきた。そこで、CPU を多く使う処理も動かせるコンテナ版を足す。無料で動く Cloudflare 版も残し、両方を使えるようにする。

ここでは、どちらの版にどの機能を載せるか、コンテナ版をどう動かし、どう配るかを決める。

## 決定

### 載せる機能

1. **コンテナ版には、すべての機能を載せる。Cloudflare 版には、無料プランで動く範囲の機能だけを載せる。**
   - 今ある機能（Phase 1）は、どちらの版にも載せる
   - 新しい機能は作るときに、どちらの版に載せるかを決め、その機能の決定ファイルに書く。決めるときは、Cloudflare 版で 1 つの仕事が無料プランの上限（CPU、`QUERY_BUDGET`、外への取得 50 回）に収まるかを測る
   - CPU を多く使う見込みのものは、記事のページからの全文抽出（[記事の本文](content.md)の 10）、画像の縮小（[画像の中継とサムネイル](images.md)）、埋め込みの計算やクラスタリング（Phase 3）
2. **版によって有無が分かれる機能は、緩衝層（`Platform`）がその機能を持つかどうかで切り替える。**
   - コンテナ版の緩衝層だけが、その機能の実装を渡す。Cloudflare 版では、その項目がない（`undefined`）
   - アプリは `Platform` の中身を見て振る舞いを変え、版の名前では分岐しない
3. **版にない機能は、使えないことが分かる形で伝える。**
   - REST API：版にない機能も OpenAPI には載せ、呼ばれたら「この版では使えない」と分かるエラーを返す。使える機能の一覧を返す API も用意し、sendo-reader はそれを見て画面を出し分ける
   - MCP：版にないツールは、ツールの一覧に出さない
   - Google Reader API：今の範囲には、版で分かれるものがない

### 動かし方

4. **コンテナ版は Node で動かす。** 入口と緩衝層の実装は `src/platform/node/` に置き、HTTP は `@hono/node-server` で受ける。CPU を多く使う処理は Rust で書き、napi-rs のネイティブのモジュールとして同じプロセスに読み込む（[テックスタック](tech-stack.md)の 5）。
5. **DB は SQLite のファイルにし、ドライバは libsql を使う。**
   - スキーマとマイグレーションは、2 つの版で 1 組だけ持つ。片方の版でしか使わない表も、同じスキーマに入れる
   - マイグレーションは、コンテナを起動したあと、リクエストを受ける前に当てる
   - Postgres は、今は支えない
6. **仕事は SQLite のジョブの表に積み、同じプロセスの中で取り出して動かす。** 定期実行も、同じプロセスのタイマーで動かす（Cloudflare 版と同じく、10 分おきと日本時間 3:00 の片付け）。
   - どちらの版でも動く仕事は、今までどおり Cloudflare 版の上限（`QUERY_BUDGET` など）に収める。コンテナ版だけの仕事は、その上限に縛られない
   - 失敗した仕事は、Cloudflare 版と同じく、少し間を置いて 3 回までやり直す
7. **sendo は、1 つのコンテナ・1 つのプロセスで動かす。** データ（SQLite のファイルと記事の本文）は、1 つのボリューム（`/data`）にまとめる。記事の本文は、そのボリュームにファイルとして置く。
   - 既存のサーバー（関連検索の RustXNG など）を使う機能は、そのサーバーを別のコンテナとして `compose.yaml` に並べる（[テックスタック](tech-stack.md)の 6）。その機能を使わない人は、入れなくてよい
8. **外への取得では、接続する IP アドレスも確かめる。**
   - 名前解決の結果が内部用・予約済みの範囲なら、接続しない。リダイレクトの行き先にも同じ確認をかける
   - この確認ができるまで、コンテナ版は出さない
9. **コンテナは HTTP だけを受ける。** TLS は、デプロイする人が手前に置くリバースプロキシ（Caddy など）に任せる。

### 配り方

10. **上流のリポジトリの CI がイメージを作り、GHCR（`ghcr.io/sendo-feed/sendo`）に置く。使う人は fork しない。**
    - 使う人は、手元に `compose.yaml` と `.env` だけを置き、イメージを取ってきて動かす。上流の更新は `docker compose pull` で取り込む
    - `main` に変更が入るたびに、`main` のタグを付けて出す。版を切るようになったら、版のタグ（`1.2.3`、`1.2`）と `latest` も付ける
    - amd64 と arm64 の両方で作る。Rust のネイティブのモジュールも、それぞれの CPU 向けにビルドしてイメージに入れる
    - リポジトリを公開するまでは、イメージも非公開にする
11. **設定は環境変数で渡し、名前は Cloudflare 版と同じにする**（`PUBLIC_URL`、`READER_URL`、`ALLOWED_EMAILS`、`FETCH_INTERVAL_MINUTES` など）。秘密も、`.env` から環境変数として渡す。
12. **テストは、どちらの版でも動く処理を今までどおり workerd で動かす。コンテナ版の緩衝層と、コンテナ版だけの機能は Node で動かす。Rust の処理は cargo test で確かめ、Node から呼べることは Node のテストで確かめる。** CI ではすべてを通す。

## 理由

### なぜコンテナ版が要るのか

これから作る機能が、Workers の CPU 時間に収まらなくなってきたから。

- 無料プランの CPU 時間は、ドキュメントでは 1 回 10ms。実測でも、キューの受け手は約 1.2 秒で止まる。`ctx.exports` で呼んだ仕事は同じ isolate で CPU を分け合い、合計 1.5 秒ほどでまとめて止まる（[仕事の流し方](jobs.md)）
- 今の重い処理はフィードの解析で、1 本 5〜31ms で収まっている。しかし、記事のページ（数百 KB）から本文を抜く処理は、それよりずっと重くなる見込み。画像の縮小は、1 枚で数十〜数百 ms かかる（[画像の中継とサムネイル](images.md)）。埋め込みの計算やクラスタリングは、記事の数に比例して重くなる
- これまで、上限に収めるための工夫（封筒、`QUERY_BUDGET`、`ctx.exports` で別の実行に分けること）を重ねてきた。重い機能ごとに同じ工夫を続けると、機能の作りが上限の都合で決まってしまう
- Workers Paid（月 5 ドル）にしても、CPU 時間の上限は 1 回 30 秒（最大 5 分まで延ばせる）に広がるだけで、なくなりはしない。それに、使う人みんなに月 5 ドルを求めることになる
- コンテナには、CPU 時間、1 回の実行で使えるクエリの数、外への取得の回数のどれにも上限がない。手元の PC、自宅のサーバー、VPS のどこでも動く

### なぜ 2 つの版を両方持つのか

- サーバーを持たない人でも無料で使える Cloudflare 版は、OSS として残しておきたい（[仕事の流し方](jobs.md)の代替案「Workers Paid を前提にする」と同じ理由）。RSS リーダーとしての機能は、Cloudflare 版だけで揃う
- 重い機能が要る人は、コンテナ版を使えばよい。LLM の機能は、もともとオプションにしている（[機能一覧](../features.md)の「設計の方針」）
- 同じコードから作るので、2 つの版を保つ手間は、緩衝層の実装とそのテストに限られる

### 決定ごとの理由

- **緩衝層で機能の有無を切り替える：**
  - 版の名前で分岐すると、版の事情が `src/` のあちこちに漏れる
  - 重い処理を Rust（napi-rs のネイティブのモジュール）で書いても、緩衝層の中に閉じ込められる
- **版にない機能も API に残し、エラーを返す：**
  - sendo-reader は `spec/openapi.json` から型を作る。版ごとに API の形を変えると、型を 2 つ持つことになる
  - MCP では、使えないツールを見せると、エージェントがそれを呼んで失敗する。だから一覧から外す
- **Node を使う：**
  - LTS の期間が長く、開発の道具（`.node-version`）でもすでに使っている
  - undici の接続の処理を差し替えれば、外への取得で接続先の IP を確かめられる（8）
- **libsql を使う：**
  - アプリの `Database` は、SQLite の非同期のドライバに共通の型にしてある。libsql はファイルの SQLite を非同期で扱えるので、その型にそのまま合う
  - better-sqlite3 は同期のドライバなので、この型に合わない
  - FTS5 とトリガーも使える
- **スキーマを 1 組にする：** マイグレーションを 2 組持たずに済む。2 つの版の間で、データも移せる（D1 から書き出した SQLite を、コンテナ版で読める）。
- **ジョブの表とタイマーで動かす：** 外のキューやスケジューラ（Redis など）を足さずに、1 つのコンテナで完結する。仕事を表に積むので、再起動しても消えない。
- **1 つのプロセスで動かす：** SQLite のファイルは、1 つのプロセスから書くのが安全。個人で使う規模なら、1 つで足りる。Rust の重い処理も同じプロセスのスレッドプールで動くので、プロセスを分けずに済む。既存のサーバーを別のコンテナにしても、それらは sendo の SQLite に触らない。
- **接続する IP も確かめる：**
  - 今の確認（`toFetchableUrl`）は、ホスト名の文字列しか見ていない
  - Workers からはそもそも内部のネットワークに届かないので、それで足りていた
  - コンテナからは内部のネットワークやクラウドのメタデータ（`169.254.169.254`）に届く。内部のアドレスに解決されるドメインや、DNS リバインディングで突破されてしまう
- **fork しない：**
  - Cloudflare 版で fork するのは、Workers Builds の GitHub App が、リポジトリを持つアカウントにしか入らないから（[デプロイ](deploy.md)）
  - 上流でイメージを作って配れば、使う人は自分のリポジトリを持たなくてよい
  - 人ごとの設定は `.env` にあって git に載らないので、自分の URL が公開の fork に載る心配もない
- **設定の名前を揃える：** 版を移るときに、設定を読み替えなくて済む。設定の読み方（`parseOrigin` など）も、2 つの版で共有できる。

## 検討した代替案

- **Cloudflare 版だけにし、Workers Paid を前提にする：** CPU 時間の上限は広がるが、なくならない。重い機能ごとに上限に合わせた工夫を続けることになり、使う人みんなに月 5 ドルも求める。
- **Cloudflare 版をやめ、コンテナ版だけにする：** 作りは 1 つで済む。ただ、サーバーを持たない人が、無料で使えなくなる。
- **重い処理だけを、Cloudflare 版から別の場所に任せる（Cloudflare Containers、別のサーバー）：** Cloudflare Containers は Workers Paid が必要。別のサーバーを足すと、デプロイするものが 2 つになり、結局サーバーを持つことになる。
- **Cloudflare 版のまま、重い処理を Rust の Wasm で軽くする：**
  - `ctx.exports` で呼んだ仕事は同じ isolate で CPU を分け合うので、使える枠そのものは増えない（[仕事の流し方](jobs.md)の代替案）
  - どれだけ速くなるかも、測ってみないと分からない
- **コンテナ版も、各自が fork してビルドする：** コードを自分で変えたい人はそうすればよい。ただ、動かすだけなら要らない。
- **Postgres を支える：** 大勢で使うなら要るが、今は個人で使う規模を想定している。SQLite の方言で書いたスキーマ（FTS5 など）を、もう 1 組持つことになる。

## 見直す条件

- コンテナ版を、複数のプロセスや複数のサーバーで動かしたくなったとき。Postgres と、外のキューを考える。
- Cloudflare が無料プランの上限を変えたとき。どの機能をどちらの版に載せるかを見直す。
- 版を切って配るようになったとき。イメージのタグの付け方と、自動で更新するかどうかの勧め方を決め直す。
- どちらかの版を使う人がいなくなったとき。2 つの版を保つ手間が見合うかを考え直す。
