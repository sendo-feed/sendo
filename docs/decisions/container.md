# コンテナ版

- 状態：提案中
- 関連：[テックスタック](tech-stack.md)（緩衝層、Rust）、[仕事の流し方](jobs.md)（仕事の動かし方）、sendo-reader の[コンテナ版](https://github.com/sendo-feed/sendo-reader/blob/main/docs/decisions/container.md)（画面のコンテナと中継）

Sendo は、コンテナ（Node ＋ SQLite）だけで動かす（[テックスタック](tech-stack.md)の 2）。Cloudflare（Workers・D1・Queues）で動かす版は持たない。

## 決定

### 載せる機能

1. **Sendo は、コンテナだけで動かし、すべての機能を載せる。** 記事のページ本文の抽出と記事の言語判定も、ほかの機能と同じく常に動かす（[記事の本文](content.md)の 10、11、[記事の言語判定](article-language.md)の 1）。
2. **重い処理は Rust のネイティブのモジュールで動かし、起動するときに必ず読み込む。**
   - 読み込めなければ、起動を止める。機能を欠いたまま動かさない。イメージには必ず入っている
   - アプリは、重い処理を緩衝層（`Platform`）越しに使う。機能があるかどうかで分岐しない
3. **`GET /api/v1/features` は reader との互換のために残す。** 現行の Sendo で使える機能はすべて true を返す。段階的な更新の間は、[差分同期](sync.md)の 9 の `syncUpdates` で旧 Sendo を判別できる。reader が使わなくなったら API を消す。

### 動かし方

4. **Node で動かす。** 入口と緩衝層の実装は `src/platform/node/` に置き、HTTP は `@hono/node-server` で受ける。CPU を多く使う処理は Rust で書き、napi-rs のネイティブのモジュールとして同じプロセスに読み込む（[テックスタック](tech-stack.md)の 5）。
5. **DB は SQLite のファイルにし、ドライバは libsql を使う。**
   - マイグレーションは、コンテナを起動したあと、リクエストを受ける前に当てる
   - Postgres は、今は支えない
6. **仕事は SQLite のジョブの表に積み、同じプロセスの中で取り出して動かす。** 定期実行も、同じプロセスのタイマーで動かす（10 分おきと、日本時間 3:00 の片付け）。詳しくは[仕事の流し方](jobs.md)に書く。
7. **sendo は、1 つのコンテナ・1 つのプロセスで動かす。** データ（SQLite のファイルと記事の本文）は、1 つのボリューム（`/data`）にまとめる。記事の本文は、そのボリュームにファイルとして置く。
   - 既存のサーバー（関連検索の RustXNG など）を使う機能は、そのサーバーを別のコンテナとして `compose.yaml` に並べる（[テックスタック](tech-stack.md)の 6）。その機能を使わない人は、入れなくてよい
   - 画面（sendo-reader）も、別のコンテナ（`ghcr.io/sendo-feed/sendo-reader`）として `compose.yaml` に並べる。外に出すのは sendo-reader のコンテナだけにし、sendo のポートは出さない。sendo-reader が画面を返し、sendo のパスを中継するので、画面・API・認証は sendo-reader と同じオリジンで使う。`PUBLIC_URL` と `READER_URL` には、どちらもそのオリジンを入れる（sendo-reader の[コンテナ版](https://github.com/sendo-feed/sendo-reader/blob/main/docs/decisions/container.md)の 1〜4）
   - 画面を使わない人は、sendo-reader のコンテナを外し、sendo のポートを出してよい（`PUBLIC_URL` は sendo のオリジン、`READER_URL` は空。OAuth は使えない）
8. **外への取得では、接続する IP アドレスも確かめる。**
   - 名前解決の結果が内部用・予約済みの範囲なら、接続しない。リダイレクトの行き先にも同じ確認をかける
   - 接続先 IP の確認は、配布するイメージの条件とする
9. **コンテナは HTTP だけを受ける。** TLS は、デプロイする人が手前に置くリバースプロキシ（Caddy など）や Cloudflare Tunnel に任せる。

### 配り方

10. **上流のリポジトリの CI がイメージを作り、GHCR（`ghcr.io/sendo-feed/sendo`）に置く。使う人は fork しない。**
    - 標準構成では、手元に `compose.yaml` と `.env` を置き、配布済みイメージで動かす。上流の更新は `docker compose pull` で取り込み、コンテナを作り直す。新しいコンテナが起動するときにマイグレーションを当てる（5）
    - X の埋め込みを有効にする場合は、reader とホスト名が異なる HTTPS オリジンで隔離フレーム用の静的ページを配信する。配信元を指定した reader イメージをビルドして Compose で使い、reader の更新時もビルドし直す。Sendo は `docker compose pull sendo` で更新してから、Compose でコンテナを作り直す。[reader のコンテナ構成](https://github.com/sendo-feed/sendo-reader/blob/main/docs/decisions/container.md)
    - `main` に変更が入るたびに、`main` のタグを付けて出す。版を切るようになったら、版のタグ（`1.2.3`、`1.2`）と `latest` も付ける
    - amd64 と arm64 の両方で作る。Rust のネイティブのモジュールも、それぞれの CPU 向けにビルドしてイメージに入れる
    - イメージは公開する。使う人は `docker login` せずに取ってこられる
11. **設定は環境変数で渡す**（`PUBLIC_URL`、`READER_URL`、`ALLOWED_EMAILS`、`FETCH_INTERVAL_MINUTES`、`STORAGE_LIMIT_MIB` など）。秘密も、`.env` から環境変数として渡す。何も入れなければ、コードの既定値で動く。
12. **テストは Node で動かす。Rust の処理は cargo test で確かめ、Node から呼べることは Node のテストで確かめる。** CI ではすべてを通す。

## 理由

### なぜコンテナだけにするのか

Sendo がほかの RSS リーダーと違う価値を出すのは、CPU を多く使う処理（ページ本文の抽出、言語判定、これから作る LLM・埋め込み・クラスタリング）。Cloudflare の無料プランでは、それが載らなかった。

- 無料プランの CPU 時間は、ドキュメントでは 1 回 10ms。2026-11-15 の実測でも、キューの受け手は約 1.2 秒、`ctx.exports` で呼んだ仕事は同じ isolate で合わせて 1.5 秒ほどで止まった
- ページ本文の抽出は、JavaScript の検証で 1 ページの中央値が 15.8ms、最大が 306ms（[記事の本文](content.md)の「理由」）。画像の処理は 1 枚で数十〜数百 ms。埋め込みの計算やクラスタリングは、記事の数に比例して重くなる
- 1 回の実行のクエリは 50、外への取得は 50 回まで。D1 は容量 500MB、書き込み 1 日 10 万行まで。これらに収めるため、仕事を封筒に束ねる、クエリ数を数える、本文を R2 に分けるなどの工夫を重ねていたが、重い機能は結局コンテナ版にしか載せられなかった
- Workers Paid（月 5 ドル）にしても、CPU 時間の上限は 1 回 30 秒（最大 5 分）に広がるだけで、なくならない。ネイティブのライブラリも使えない
- その結果、Cloudflare 版は普通の RSS リーダーの範囲にとどまり、Sendo を選ぶ理由にならなかった。2 人で話し合い、コンテナだけにすると決めた
- コンテナには、CPU 時間、1 回の実行のクエリ数、外への取得の回数のどれにも上限がない。手元の PC、自宅のサーバー、VPS のどこでも動く

### 決定ごとの理由

- **ネイティブのモジュールを必ず読み込む：** 機能を欠いたまま動くと、ページの本文や言語判定が静かに止まり、気づきにくい。イメージには必ず入っているので、読み込めないのは壊れたときだけ。起動を止めて知らせるほうがよい。
- **`GET /api/v1/features` を当面残す：** sendo-reader はこの API を見て画面を出し分けている。先に消すと、sendo-reader が呼んで失敗する。現行の Sendo はすべて true を返す。追加した項目を reader が見れば、古い Sendo と組み合わせたときも同期を続けられる。古い版を支える必要がなくなった機能は、reader の判定を消せる。
- **Node を使う：**
  - LTS の期間が長く、開発の道具（`.node-version`）でもすでに使っている
  - undici の接続の処理を差し替えれば、外への取得で接続先の IP を確かめられる（8）
- **libsql を使う：**
  - アプリの `Database` は、SQLite の非同期のドライバに共通の型にしてある。libsql はファイルの SQLite を非同期で扱えるので、その型にそのまま合う
  - better-sqlite3 は同期のドライバなので、この型に合わない
  - FTS5 とトリガーも使える
- **ジョブの表とタイマーで動かす：** 外のキューやスケジューラ（Redis など）を足さずに、1 つのコンテナで完結する。仕事を表に積むので、再起動しても消えない。
- **sendo-reader を、外に出す唯一のコンテナにする：**
  - コンテナの sendo は、リクエストの URL のオリジンを `PUBLIC_URL` に置き換える。`PUBLIC_URL` を sendo-reader のオリジンにすれば、ログインの戻り先、セッションのクッキー、状態を変えるリクエストの確かめ、OAuth の発行者と MCP の宛先が、どれも 1 つのオリジンでそろう
  - `PUBLIC_URL` と `READER_URL` が同じオリジンでも、設定は受ける（2 つを比べない）
  - 画面と画面の守り（CSP など）は、sendo-reader が持ったままになる（[技術構成](../tech-deck.md)。sendo は API だけを持つ）
- **1 つのプロセスで動かす：** SQLite のファイルは、1 つのプロセスから書くのが安全。個人で使う規模なら、1 つで足りる。Rust の重い処理も同じプロセスのスレッドプールで動くので、プロセスを分けずに済む。既存のサーバーを別のコンテナにしても、それらは sendo の SQLite に触らない。
- **接続する IP も確かめる：**
  - 共通の `toFetchableUrl` は URL のホスト名を確認する
  - コンテナからは内部のネットワークやクラウドのメタデータ（`169.254.169.254`）に届く。ホスト名の確認だけでは、内部のアドレスに解決されるドメインや、DNS リバインディングで突破されてしまう
- **配布済みイメージを使う：**
  - 標準構成では上流が作ったイメージで動かせる。X の埋め込みを有効にする構成では、配信元をビルド時に reader の設定と CSP に入れるため、reader をビルドして使う（10）
  - 人ごとの設定は `.env` にあって git に載らないので、自分の URL が公開の fork に載る心配もない
- **起動するときにマイグレーションを当てる：** 1 つのプロセスなので、古い版と新しい版のコードが同じ DB で同時に動くことがない。マイグレーションを前の版のコードと両立させる必要がない。標準構成では更新を `docker compose pull` で取り込み、`docker compose up -d` でコンテナを作り直す。X の埋め込みを有効にした場合は、Sendo のイメージを取り込み、新しい reader イメージをビルドしてからコンテナを作り直す（10）。

## 検討した代替案

- **Cloudflare 版も残し、2 つの版を同じコードから作る：** サーバーを持たない人も無料で使える。ただ、Cloudflare 版に載るのは普通の RSS リーダーの範囲だけで、Sendo を選ぶ理由にならない。緩衝層の 2 つの実装、workerd と Node の 2 組のテスト、上限に合わせた作り、2 つのデプロイの手順を保つ手間が大きい。
- **重い処理だけを、Cloudflare から別の場所に任せる（Cloudflare Containers、別のサーバー）：** Cloudflare Containers は Workers Paid が必要。別のサーバーを足すと、デプロイするものが 2 つになり、結局サーバーを持つことになる。
- **ネイティブのモジュールがなくても、その機能なしで起動する：** 開発の手元で Rust を入れずに動かせる。ただ、本番で読み込みに失敗したときに、機能が黙って止まる。手元でも `pnpm build:native` で作れる。
- **`GET /api/v1/features` をすぐ消す：** API が小さくなるが、sendo-reader を同時に直さないと、画面が壊れる。
- **全員が fork してイメージをビルドする：** コードを変えるときは各自でビルドできる。標準構成では配布済みイメージを使い、X の埋め込みを有効にした構成では reader イメージをビルドする（10）。
- **Postgres を支える：** 大勢で使うなら要るが、今は個人で使う規模を想定している。SQLite の方言で書いたスキーマ（FTS5 など）を、もう 1 組持つことになる。

## 見直す条件

- コンテナを、複数のプロセスや複数のサーバーで動かしたくなったとき。Postgres と、外のキューを考える。
- 版を切って配るようになったとき。イメージのタグの付け方と、自動で更新するかどうかの勧め方を決め直す。
- sendo-reader が `GET /api/v1/features` を使わなくなったとき。API から消す（3）。
- サーバーを持たない人にも使ってもらう必要が出たとき。コンテナを動かせるホスティングを勧めるか、軽い版を作るかを考える。
