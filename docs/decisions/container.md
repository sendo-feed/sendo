# コンテナ版

- 状態：提案中
- 関連：[テックスタック](tech-stack.md)（緩衝層、Rust）、[仕事の流し方](jobs.md)（仕事の動かし方）、[Web Push](web-push.md)（3 の有無）、sendo-reader の[コンテナ版](https://github.com/sendo-feed/sendo-reader/blob/main/docs/decisions/container.md)（画面のコンテナと中継）

Sendo は、コンテナ（Node ＋ SQLite）だけで動かす（[テックスタック](tech-stack.md)の 2）。Cloudflare（Workers・D1・Queues）で動かす版は持たない。

## 決定

### 載せる機能

1. **Sendo は、コンテナだけで動かし、すべての機能を載せる。** 記事のページ本文の抽出と記事の言語判定は常に動かす（[記事の本文](content.md)の 10、11、[記事の言語判定](article-language.md)の 1）。
2. **重い処理は Rust のネイティブのモジュールで動かし、起動するときに必ず読み込む。**
   - 読み込めなければ、起動を止める。機能を欠いたまま動かさない。イメージには必ず入っている
   - アプリは、重い処理を緩衝層（`Platform`）越しに使う。機能があるかどうかで分岐しない
3. **設定によって使えるかどうかが決まる機能は、その機能の API で有無を伝える。** 機能の有無をまとめて返す API（`GET /api/v1/features` など）は持たない。
   - [記事の翻訳](translation.md)は、Claude API のキー（`ANTHROPIC_API_KEY`）があるときだけ翻訳の行を作り、外へ送る。クライアントは、差分同期で配る記事ごとの翻訳の状態があるときに、翻訳の表示と操作を出す。キーを外したあとも残る行への翻訳の求めは 503（`translation_unavailable`）で断る（同じく 15）
   - [Discord チャンネルの購読](discord.md)には、`DISCORD_CLIENT_ID`、`DISCORD_CLIENT_SECRET`、`DISCORD_BOT_TOKEN` と、コールバック先に使う `READER_URL` の設定が要る。使える設定がそろっているかは `GET /api/v1/integrations/discord` の `available` で伝える。設定がそろっていなければ、接続・コールバック・新規購読の入口は 501（`feature_unavailable`）を返す
   - ベルの[通知](notifications.md)を送る [Web Push](web-push.md) には、VAPID の `sub` に使う `VAPID_SUBJECT` と、通知から記事を開く URL に使う `READER_URL` の設定が要る。使える設定がそろっているかは `GET /api/v1/push` の `available` で伝える。設定がそろっていなければ、端末の登録（`PUT`）は 501（`feature_unavailable`）を返す（[Web Push](web-push.md)の 3）
   - 新しい機能に対応する前の Sendo と組み合わさる間は、その機能を呼んで失敗したら使わずに動き続ける形で扱う（例：[差分同期](sync.md)の 9 の通知）

### 動かし方

4. **Node で動かす。** 入口と緩衝層の実装は `src/platform/node/` に置き、HTTP は `@hono/node-server` で受ける。CPU を多く使う処理は Rust で書き、napi-rs のネイティブのモジュールとして同じプロセスに読み込む（[テックスタック](tech-stack.md)の 5）。
5. **DB は SQLite のファイルにし、ドライバは libsql を使う。**
   - マイグレーションは、コンテナを起動したあと、リクエストを受ける前に当てる
   - Postgres は、今は支えない
6. **仕事は SQLite のジョブの表に積み、同じプロセスの中で取り出して動かす。** 定期実行も、同じプロセスのタイマーで動かす（5 分おきと、日本時間 3:00 の片付け）。詳しくは[仕事の流し方](jobs.md)に書く。
7. **sendo は、1 つのコンテナ・1 つのプロセスで動かす。** データ（SQLite のファイルと記事の本文）は、1 つのボリューム（`/data`）にまとめる。記事の本文は、そのボリュームにファイルとして置く。
   - 既存のサーバー（関連検索の RustXNG など）を使う機能は、そのサーバーを別のコンテナとして `compose.yaml` に並べる（[テックスタック](tech-stack.md)の 6）。その機能を使わない人は、入れなくてよい
   - 画面（sendo-reader）も、別のコンテナ（`ghcr.io/sendo-feed/sendo-reader`）として `compose.yaml` に並べる。外に出すのは sendo-reader のコンテナだけにし、sendo のポートは出さない。sendo-reader が画面を返し、sendo のパスを中継するので、外からは sendo-reader のオリジン 1 つに見える。`PUBLIC_URL` と `READER_URL` には、どちらもそのオリジンを入れる（sendo-reader の[コンテナ版](https://github.com/sendo-feed/sendo-reader/blob/main/docs/decisions/container.md)の 1〜4）
   - 画面を使わない人は、sendo-reader のコンテナを外し、sendo のポートを出してよい（`PUBLIC_URL` は sendo のオリジン、`READER_URL` は空。OAuth は使えない）
8. **外への取得では、接続する IP アドレスも確かめる。**
   - 名前解決の結果が内部用・予約済みの範囲なら、接続しない。リダイレクトの行き先にも同じ確認をかける
   - 接続先 IP の確認は、配布するイメージの条件とする
9. **コンテナは HTTP だけを受ける。** TLS は、デプロイする人が手前に置くリバースプロキシ（Caddy など）や Cloudflare Tunnel に任せる。

### 配り方

10. **上流のリポジトリの CI がイメージを作り、GHCR（`ghcr.io/sendo-feed/sendo`）に置く。使う人は fork しない。**
    - 使う人は、手元に `compose.yaml` と `.env` だけを置き、イメージを取ってきて動かす。上流の更新は `docker compose pull` で取り込み、コンテナを作り直す。新しいコンテナが起動するときにマイグレーションを当てる（5）。自動で更新したい人には、更新のスクリプトの例を勧める（13）
    - `main` に変更が入るたびに、`main` のタグと、コミットごとの `sha-<コミット>` のタグを付けて出す。版を切るようになったら、版のタグ（`1.2.3`、`1.2`）と `latest` も付ける
    - amd64 と arm64 の両方で作る。Rust のネイティブのモジュールも、それぞれの CPU 向けにビルドしてイメージに入れる
    - イメージは公開する。使う人は `docker login` せずに取ってこられる
11. **設定は環境変数で渡す**（`PUBLIC_URL`、`READER_URL`、`ALLOWED_EMAILS`、`FETCH_INTERVAL_MINUTES`、`STORAGE_LIMIT_MIB`、`ANTHROPIC_API_KEY`、`TRANSLATION_MODEL`、`TRANSLATION_EFFORT`、`TRANSLATION_LONG_MODEL`、`TRANSLATION_LONG_EFFORT`、`TRANSLATION_LONG_THRESHOLD_CHARS`、`RETRANSLATION_MODEL`、`RETRANSLATION_EFFORT`、`VAPID_SUBJECT` など）。秘密も、`.env` から環境変数として渡す。何も入れなければ、コードの既定値で動く。
12. **テストは Node で動かす。Rust の処理は cargo test で確かめ、Node から呼べることは Node のテストで確かめる。** CI では、`main` への push と、Markdown 以外のファイルを変える PR で、すべてを通す。Markdown だけを変える PR では、決定の文書の検査だけを動かす。
13. **自動で更新したい人には、上流に置いた更新のスクリプトの例を勧める。** 基本の手順は、手で `docker compose pull` するまま（10）にし、自動の更新を既定にしない。
    - 例は sendo のリポジトリに置き、README の更新の手順から案内する。使う人が、`compose.yaml` を置いたマシンで cron などから動かす。コンテナの中には更新の仕組みを入れない（Docker のソケットをコンテナに渡さない）。対象は sendo と sendo-reader を並べた構成（7）だけにし、sendo-reader のない構成では使わない
    - 上げるのは、`compose.yaml` で `ghcr.io/sendo-feed/sendo` と `ghcr.io/sendo-feed/sendo-reader` のイメージを `main` のタグで指定したサービスだけ。`compose.yaml` に並べたほかのサービス（RustXNG など）には触らない。`sha-<コミット>` のタグかダイジェストで固定したサービスは上げない
    - 上げてよいのは、上げるイメージが上流の `main` の最新のコミットのもので、そのコミットの CI のワークフローが通っているときだけ。sendo-reader では、動いている sendo についても同じことを確かめる。片方を上げられないとき（固定した、CI が落ちた、戻して飛ばしている）は、もう片方も上げない。イメージを取ったあとで上げないと決めたら、手元の `main` のタグを動いているイメージに戻す
    - 始めるときに sendo か sendo-reader が動いていなければ、何も変えずに終わる。どちらにも上げる版がなければ、何も変えない。sendo に上げる版がなければ、sendo には触らず sendo-reader だけを上げる
    - sendo は、次の順に上げる
      - イメージの取得と、バックアップを置く場所の空きの確かめは、止める前に済ませる。空きが足りなければ、その回は上げない。置く場所は使う人が選べる
      - sendo-reader を止め、sendo を止めてから、データ（`/data` のボリューム）のバックアップを取り、新しいイメージで sendo を起動する
      - sendo が healthy になってから、sendo-reader を新しいイメージで起こす。healthy を待つ時間には上限を置き、使う人が変えられるようにする
    - sendo が healthy にならなければ、前のイメージと、上げる直前に取ったバックアップを組で戻してから、sendo-reader を起こす
      - 戻すときは、sendo を止めて消してから、ボリュームの中身をまるごとバックアップに置き換える（新しい版が残した WAL や本文のファイルを残さない）
      - 戻す前に sendo-reader が止まったままかを確かめる。起きていれば、戻さずに止めて知らせる
      - 戻した sendo も healthy にならなければ、sendo-reader を起こさず、止まったと知らせて終わる
    - sendo-reader が healthy にならなければ、前のイメージに戻す。sendo と sendo-reader のどちらも、戻した版は飛ばし、上流の `main` に次のコミットが入るまで上げ直さない
    - バックアップは、上げる直前の 1 組だけを残し、その回の戻しにだけ使う。sendo-reader を新しい sendo で起こしたあとは、バックアップで戻さない
    - 途中で失敗したときと、実行が落ちたときに備える
      - 新しい版で起動する前の段で失敗したら、前のイメージで起こし直して終わる
      - タグを動かす前と止める前に、前のイメージ、バックアップの場所、いまの段をホストに書き留める。次の実行は、書き留めが残っていれば、先にその続きから戻して終わらせる。戻すのには、取り終えた印のあるバックアップだけを使う
      - 例は 1 回ずつ動かす。前の実行が終わっていなければ、次の実行は何もせずに終わる。実行が落ちても、印が残って以後の実行を止めない形にする
      - 例を使うときは、手で `docker compose pull` しない。例が動いている間は、compose の操作をしない
    - 知らせ（上げた、戻した、止まった）は、使う人が送り先を設定したときだけ送る。設定がなければ、どこにも送らない

## 理由

### なぜコンテナだけにするのか

Sendo がほかの RSS リーダーと違う価値を出すのは、CPU を多く使う処理（ページ本文の抽出、言語判定、これから作る LLM・埋め込み・クラスタリング）。Cloudflare の無料プランでは、それが載らなかった。

- 無料プランの CPU 時間は、ドキュメントでは 1 回 10ms。2026-11-15 の実測でも、キューの受け手は約 1.2 秒、`ctx.exports` で呼んだ仕事は同じ isolate で合わせて 1.5 秒ほどで止まった
- ページ本文の抽出は、JavaScript の検証で 1 ページの中央値が 15.8ms、最大が 306ms（[記事の本文](content.md)の「理由」）。画像の処理は 1 枚で数十〜数百 ms。埋め込みの計算やクラスタリングは、記事の数に比例して重くなる
- 1 回の実行のクエリは 50、外への取得は 50 回まで。D1 は容量 500MB、書き込み 1 日 10 万行まで。これらに収めるため、仕事を封筒に束ねる、クエリ数を数える、本文を R2 に分けるなどの工夫を重ねていたが、重い機能は結局コンテナ版にしか載せられなかった
- Workers Paid（月 5 ドル）にしても、CPU 時間の上限は 1 回 30 秒（最大 5 分）に広がるだけで、なくならない。ネイティブのライブラリも使えない
- その結果、Cloudflare 版は普通の RSS リーダーの範囲にとどまり、Sendo を選ぶ理由にならなかった。2 人で話し合い、コンテナだけにすると決めた
- コンテナには、CPU 時間、1 回の実行のクエリ数、外への取得の回数のどれにも上限がない。手元の PC、自宅のサーバー、VPS のどこでも動く

### 決定ごとの理由

- **ネイティブのモジュールを必ず読み込む：** 機能を欠いたまま動くと、ページの本文や言語判定が静かに止まり、気づきにくい。イメージには必ず入っているので、読み込めないのは壊れたときだけ。起動を止めて知らせるほうがよい。
- **設定による機能の有無は、その機能の API で伝える。**
  - 配布するイメージは全機能を載せる。デプロイごとの設定で有無が分かれる翻訳、Discord、Web Push は、画面がその機能のために読む応答で判断できる。翻訳の表示は記事ごとの状態、Discord の接続と新規購読の操作は連携状態の `available`、通知の許可とベルの操作は Web Push の `available` で出すかどうかを決められる
  - Sendo と reader は compose で一緒に更新するので、新旧が混ざるのは更新の途中の短い間だけ。その間は、呼んで失敗したら使わない、で足りる。自動の更新の例で新しい reader を戻したときは、古い reader と新しい Sendo の組が上流が直すまで続くが、これも同じ扱いで足りる（13）
  - sendo-reader は、全文の取得を常に使える機能として扱う（sendo-reader の[コンテナ版](https://github.com/sendo-feed/sendo-reader/blob/main/docs/decisions/container.md)の 8）。古い版の画面（Service Worker に残った版）が `GET /api/v1/features` を呼んで 404 を受けても、全文の取得を出さないだけで動き続ける
- **Node を使う：**
  - LTS の期間が長く、開発の道具（`.node-version`）でもすでに使っている
  - undici の接続の処理を差し替えれば、外への取得で接続先の IP を確かめられる（8）
- **libsql を使う：**
  - アプリの `Database` は、SQLite の非同期のドライバに共通の型にしてある。libsql はファイルの SQLite を非同期で扱えるので、その型にそのまま合う
  - better-sqlite3 は同期のドライバなので、この型に合わない
  - FTS5 とトリガーも使える
- **ジョブの表とタイマーで動かす：** 外のキューやスケジューラ（Redis など）を足さずに、1 つのコンテナで完結する。仕事を表に積むので、再起動しても消えない。
- **sendo-reader を、外に出す唯一のコンテナにする：**
  - コンテナの sendo は、リクエストの URL のオリジンを `PUBLIC_URL` に置き換える。`PUBLIC_URL` を sendo-reader のオリジンにすれば、ログインの戻り先、セッションのクッキー、状態を変えるリクエストの確かめ、OAuth の発行者と MCP の宛先が、どれも 1 つのオリジンでそろう
  - `PUBLIC_URL` と `READER_URL` が同じオリジンでも、設定は受ける（2 つを比べない）
  - 画面と画面の守り（CSP など）は、sendo-reader が持ったままになる（[技術構成](../tech-deck.md)。sendo は API だけを持つ）
- **1 つのプロセスで動かす：** SQLite のファイルは、1 つのプロセスから書くのが安全。個人で使う規模なら、1 つで足りる。Rust の重い処理も同じプロセスのスレッドプールで動くので、プロセスを分けずに済む。既存のサーバーを別のコンテナにしても、それらは sendo の SQLite に触らない。
- **接続する IP も確かめる：**
  - 共通の `toFetchableUrl` は URL のホスト名を確認する
  - コンテナからは内部のネットワークやクラウドのメタデータ（`169.254.169.254`）に届く。ホスト名の確認だけでは、内部のアドレスに解決されるドメインや、DNS リバインディングで突破されてしまう
- **fork しない：**
  - 上流でイメージを作って配れば、使う人は自分のリポジトリを持たなくてよい
  - 人ごとの設定は `.env` にあって git に載らないので、自分の URL が公開の fork に載る心配もない
- **Markdown だけの PR では検査を絞る：** Markdown を読む検査は決定の文書の検査だけで、テスト、ビルド、Rust の検査は、コードが `main` と同じなら結果が変わらない。文書の直しのたびに Rust のビルドを含む重い検査を待たずに済む。`main` への push ではすべてを通すので、`main` の状態はいつも全部の検査を通っている。
- **起動するときにマイグレーションを当てる：** 1 つのプロセスなので、古い版と新しい版のコードが同じ DB で同時に動くことがない。マイグレーションを前の版のコードと両立させる必要がなく、更新の手順も `docker compose pull` だけで済む。
- **自動の更新は、上流に置いた例で勧める：**
  - Cloudflare 版では、sendo-updater が上流に自動で追いついていた。コンテナ版でも、その役目を選べるようにしたい。ただ、知らないうちに版が変わるのを望まない人もいるので、既定は手の更新のままにする
  - 汎用の自動更新の道具は、イメージが新しくなったらコンテナを作り直すだけで、Sendo に固有の手順（上げる前のバックアップ、sendo のあとに sendo-reader、healthy にならないときの戻し）を守れない。使う人がそれぞれに書くと、どこかが抜けやすいので、手順を守る例を上流に置く
  - イメージは CI と別に作るので、CI が落ちたコミットのイメージも `main` のタグで置かれうる。sendo-reader の `main` は sendo の `main` の API を前提にする。2 つに同じ確かめ方を当て、片方を上げられないときはもう片方も上げなければ、2 つは同じ回に進み、新旧が混ざるのは手の更新と同じく短い間で済む（3）。例外は、新しい sendo-reader が healthy にならずに戻したときで、上流が直すまで、古い sendo-reader と新しい sendo の組で動く。そのときは、3 のとおり、古い sendo-reader が呼んで失敗した機能を使わずに動く
  - マイグレーションは起動するときに当て、前の版のコードと両立させない（5）。healthy にならなかった sendo でも、マイグレーションは当たっていることがある。イメージだけを戻すと、古いコードが新しいスキーマの上で動くので、上げる直前のバックアップと組で戻す。止めてからバックアップを取るのは、書き込みの途中の SQLite のファイルを写さないため。中身をまるごと置き換えるのは、新しい版の WAL が古い DB に当たって壊すのと、新しい版が置いた本文のファイルが行のないまま残るのを防ぐため
  - 新しい sendo は、healthy の判定が出る前から要求を受ける。その間に変更番号が進み、クライアントがカーソルを進めてから戻すと、以後の変更は、クライアントが通り過ぎた番号で振られて届かない（[差分同期](sync.md)の 1）。sendo-reader を並べた構成では、外から要求が届くのは sendo-reader の中継を通してだけ（7）なので、sendo を上げるあいだは sendo-reader を止めておく。sendo 自身の仕事が進めた番号は、どのクライアントにも渡らないまま戻る。同じ理由で、sendo-reader を新しい sendo で起こしたあとは、バックアップで戻さない。sendo のポートを出す構成では入口を閉じられないので、例の対象にしない
  - 戻した版をすぐに上げ直すと、同じ失敗と戻しを繰り返す。上流が直すまで（次のコミットが入るまで）待つ
  - 取ったイメージで手元の `main` のタグが進んだままだと、次にコンテナを作り直したとき（再起動の設定の変更など）に、確かめていない版やバックアップを取っていない版が動く。手で `docker compose pull` しても同じことが起き、例が戻す先の「前のイメージ」も分からなくなる。2 つの実行が重なったり、途中で手の操作が入ったりすると、取ったバックアップと戻すイメージの組がずれる
  - `restart: unless-stopped` でも、止めたコンテナは再起動のあとも止まったままになる。手元のタグも進んでいるので、どこまで進んだかを書き留めておかないと、次の実行は戻す先が分からず、止まったまま残る。始めるときに止まっているサービスは、使う人が止めたものかもしれないので、起こさない
  - バックアップは記事の本文ごとで大きいので、1 組だけを残し、sendo の保存先の空きを食わないようにする。上流の `main` には文書だけの変更でも新しいイメージが出るので、そのたびに止めてバックアップを取ることになり、止まる時間はボリュームの大きさに比例する。止まるのを減らしたい人は、動かす間隔を広げればよい
  - 上げる対象を 2 つのイメージに限るのは、手順（バックアップ、順番、戻し）を決めたのがこの 2 つだけだから。ほかのサービスは、それぞれの手順で上げる
  - タグかダイジェストで固定するのは、使う人が更新を止める方法。片方だけが進むと、新旧の組が固定を外すまで続く
  - 知らせの送り先は、使う人ごとに違い、外へ送るものなので、使う人が決めたときだけにする

## 検討した代替案

- **Cloudflare 版も残し、2 つの版を同じコードから作る：** サーバーを持たない人も無料で使える。ただ、Cloudflare 版に載るのは普通の RSS リーダーの範囲だけで、Sendo を選ぶ理由にならない。緩衝層の 2 つの実装、workerd と Node の 2 組のテスト、上限に合わせた作り、2 つのデプロイの手順を保つ手間が大きい。
- **重い処理だけを、Cloudflare から別の場所に任せる（Cloudflare Containers、別のサーバー）：** Cloudflare Containers は Workers Paid が必要。別のサーバーを足すと、デプロイするものが 2 つになり、結局サーバーを持つことになる。
- **ネイティブのモジュールがなくても、その機能なしで起動する：** 開発の手元で Rust を入れずに動かせる。ただ、本番で読み込みに失敗したときに、機能が黙って止まる。手元でも `pnpm build:native` で作れる。
- **機能の有無と新しい機能への対応を `GET /api/v1/features` にまとめる。** 新旧の組み合わせを、機能を呼ぶ前に見分けられる。ただ、項目ごとにいつ消すかを決め続けることになる。翻訳、Discord、Web Push の設定の有無はそれぞれの API で伝えられ、新旧の組み合わせは呼んで失敗したときに扱える。
- **コンテナ版も、各自が fork してビルドする：** コードを自分で変えたい人はそうすればよい。ただ、動かすだけなら要らない。
- **Postgres を支える：** 大勢で使うなら要るが、今は個人で使う規模を想定している。SQLite の方言で書いたスキーマ（FTS5 など）を、もう 1 組持つことになる。
- **自動の更新に、汎用の道具（Watchtower など）を勧める：** 設定だけで済む。ただ、上げる前のバックアップ、sendo のあとに sendo-reader を上げる順番、バックアップと組の戻しを守れない。多くはコンテナとして動き、Docker のソケットを渡すことになる。
- **手の更新だけにする：** 勧めるものが 1 つで済む。ただ、上流に自動で追いつく役目を選べない。自動にしたい人がそれぞれに書くと、バックアップや戻しが抜けやすい。
- **コンテナの中で更新する（sendo 自身や、並べた更新のコンテナ）：** 使う人は cron を設定しなくてよい。ただ、Docker のソケットをコンテナに渡すと、ホストの root と同じことができてしまう。sendo 自身が更新すると、healthy にならないときに戻す役が動いていない。

## 見直す条件

- コンテナを、複数のプロセスや複数のサーバーで動かしたくなったとき。Postgres と、外のキューを考える。
- 版を切って配るようになったとき。イメージのタグの付け方と、更新のスクリプトの例が追うタグ（今は `main`）を決め直す（10、13）。
- データが増えて、更新のたびのバックアップが重くなったとき。更新の例のバックアップの取り方を決め直す（13）。
- マイグレーションが、更新の例の healthy を待つ上限より長くかかる版を出すとき。その版を壊れた版と見て飛ばし続けないよう、上限か待ち方を決め直す（13）。
- デプロイによって有無が分かれる機能を足すとき（別のコンテナの RustXNG を使う関連検索など）は、その機能の API で伝えられるかを確かめる。機能ごとの応答や「呼んで失敗したら使わない」では足りないとき（失敗が利用者に見える、呼ぶこと自体が重いなど）は、機能の有無をまとめて返す API を考え直す（3）。
- コードやテストが Markdown を読むようになったとき（文書から何かを生成するなど）。Markdown だけの PR で検査を絞るのをやめるか、絞る範囲を決め直す（12）。
- サーバーを持たない人にも使ってもらう必要が出たとき。コンテナを動かせるホスティングを勧めるか、軽い版を作るかを考える。
