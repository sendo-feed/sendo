# 通知

- 状態：提案中
- 関連：[差分同期](sync.md)、[ワークスペース](workspaces.md)（4 の REST API の形、5 の同期）、[あとで読むページ](saved.md)（4 の同期）、[クライアントの設定](settings.md)（3 の片付け）、[コンテナ版](container.md)（3 の機能の有無、8 の接続する IP）、[仕事の流し方](jobs.md)（1 の時刻を指定して積む、5 のやり直し）、[ユーザーと認証](accounts.md)（セッション）、[MCP サーバー](mcp.md)（11 のツール）、[記事のキーワード検索](article-search.md)、[画像の中継とサムネイル](images.md)（sendo が持つ秘密、時間切れ）

購読か言葉、またはその両方に「ベル」を付けると、当たる新しい記事を取り込んだときに、sendo が sendo-reader へ Web Push で知らせる。押すと reader でその記事を開く。通知には受信箱の未読の数も載せるので、reader を閉じている間は、ベルの通知が届いたときにアプリのバッジが変わる。通知の許可、Service Worker、バッジの出し方など reader の側の扱いは、sendo-reader の決定で決める。

## 決定

### ベル

1. **ベルは人ごとに持ち、購読と言葉の組で表す。** 種類は 3 つ。
   - 購読だけ：その購読に入った記事すべて
   - 言葉だけ：その人のどの購読に入った記事でも、言葉に当たるもの
   - 購読 AND 言葉：その購読に入った記事のうち、言葉に当たるもの

   3 つを 1 つの表（`bells`）に持つ。行は ID、ユーザー、購読の ID（なければ null）、言葉（`words`。なければ null）、照合用の言葉（`match_key`。6）、作った時刻、変更番号、消した印を持つ。購読も言葉もない行は作らない。種類は 2 つの列の有無で決まるので、種類の列は持たない。
2. **既定はオフ。** 購読しても、ベルは付かない。付けるのは利用者の操作（REST API と MCP）だけ。
3. **同じ人で、購読と言葉の組が同じ有効なベルは 1 つにする。**
   - 消した印のない行に、`(ユーザー, coalesce(購読の ID, ''), coalesce(match_key, ''))` の部分一意索引を張る。SQLite の一意索引は null どうしを別の値とみなすので、空文字にそろえる
   - 付ける文は `INSERT … ON CONFLICT DO NOTHING` にし、上限も同じ文の中で数える。有効なベルは 1 人 100 個まで。入らなければ、同じ組の有効なベルを読み直して返す（5）。読み直してもどの理由（同じ組のベル、上限、`id` の重なり）にも当たらなければ（間に同じ組のベルが外された）、付ける文をもう一度だけ流す。2 回目も入らず、どの理由にも当たらなければ 500 にする
   - 外すと、消した印と新しい変更番号を付ける。もう一度外しても失敗にしない。外したあとに付け直すと、新しい行を作る
   - 購読をやめると（購読に消した印が付くと）、表に付けたトリガーが、同じ文の中で、その購読の ID を持つベルに消した印と新しい変更番号を付ける。言葉だけのベルは残る
   - 消した印の行は、30 日たったら 1 日 1 回の片付けで消し、回収した番号を記録する（[クライアントの設定](settings.md)の 3 と同じ）
4. **差分同期で配る。** `includeBells=true` を指定したクライアントに、`bells` で有効なベル（5 の項目と `deleted: false`）と消した印（`id` と `deleted: true`）を返す。番号とページ送りはベルの表で独立させ、ベルの位置を持たないカーソルでは、ベルを番号 0 から送る（[ワークスペース](workspaces.md)の 5、[あとで読むページ](saved.md)の 4 と同じ形）。変わったら、ほかの書き込みと同じく WebSocket で知らせる（[差分同期](sync.md)の 9）。
5. **REST API で、一覧・付ける・外すを扱う。** 入口は `/api/v1` の下。ベルは `id`、`subscriptionId`、`feedId`、`words`、`createdAt` を返す。購読のないベルは `subscriptionId` と `feedId` が null、言葉のないベルは `words` が null。`words` は空白区切りの 1 つの文字列で受けて返す。

   | 操作 | リクエストと結果 |
   |---|---|
   | `GET /bells` | 有効なベルを作った順で `{ items }` に返す |
   | `POST /bells` | `{ id?, feedId?, words? }` で付ける。`feedId` と `words` の少なくとも一方が要る。`feedId` は、書く文の中で、本人の有効な購読に引き当てる。`id` を省くとサーバーが決め、オフラインで付けるクライアントは小文字の UUID を指定できる。新しく作ったら 201、同じ組の有効なベルがあれば、送った `id` によらずそのベルを 200 で返す（どちらも `{ bell }`）。クライアントは応答の `id` を正とする |
   | `DELETE /bells/{id}` | 外して 204 を返す。本人が外したベルの再送も 204 |

   - 言葉が 7 に合わないか、`feedId` も `words` もなければ 400（`invalid_request`）。`feedId` に本人の有効な購読がなければ（購読していない、やめた、ほかの人の購読）404
   - 有効なベルが 100 個あれば 409 `bell_limit_reached`。指定した `id` がほかの行（外したベル、ほかの組、ほかの人のベル）に使われていれば 409 `bell_id_taken`。DELETE で本人のベルが見つからなければ 404
   - MCP のツール（`list_bells`、`add_bell`、`remove_bell`）は [MCP サーバー](mcp.md)の 11 で決める

### 言葉の当て方

6. **空白で区切った言葉を、すべて含む記事に当てる（AND）。** 受けた文字列を NFKC で正規化してから、空白（`\s` に当たる文字。全角の空白、タブ、改行を含む）の並びで区切る。OR、NOT、正規表現、引用符で囲んだ句は持たない（引用符も言葉の文字として扱う）。
   - 比べるときは、言葉と記事の文字を NFKC で正規化し、小文字にする。大文字と小文字、全角と半角の英数字を区別しない
   - 英数字（ASCII の英字と数字）で始まる言葉は、すぐ前に英数字があると当てない。英数字で終わる言葉は、すぐあとに英数字があると当てない。「Go」は「Google」に当たらず、「Go 1.26」と「Go言語」に当たる。言葉の端が日本語や記号なら、その端では前後を見ない（「障害」は「大規模障害」に当たる）
   - 言葉ごとに、タイトル、要約、フィードの本文のどれかにあれば当たる。すべての言葉が同じ欄になくてよい
   - `words` は、区切った言葉を半角の空白 1 つでつなぐ。小文字にして同じになる言葉は、最初のものだけを残す。大文字と小文字は、利用者が入れたまま残す
   - `match_key` は、`words` の言葉を小文字にし、コードポイントの順に並べて、半角の空白 1 つでつないだもの。言葉の並びによらず同じになる
7. **言葉は 1〜8 個、全体で 64 文字まで。** 個数も文字数も、重なりを除いた保存する形（`words`。6）で数える。文字数は、区切りの空白を含むコードポイントの数。区切ったあとの言葉が空、上限を超える、制御文字か対になっていないサロゲートを含む、のどれかなら 400 で断る。上限ちょうどは受ける。

### 判定

8. **取得の仕事が受信箱に配ったあとに、その仕事が行を入れた記事を、その時点でその記事を受信箱に持つ人について判定する。** 行を入れた記事は、行を入れた文が返した記事（公開フィードは `insertArticles`、Discord は `insertDiscordArticles`。どちらも、入れた記事を返すように変える）。前の回が配る前に落ちて、この回にまとめて配った記事は判定しない。
   - 1 回の仕事で判定する記事は、公開日時の新しい順に 50 件まで。残りは判定しない
   - 欄は、タイトル、要約、フィードの本文（プレーンテキストにした先頭 20,000 文字。[記事のキーワード検索](article-search.md)の 2 と同じ切り方）。記事のページから抜いた本文と訳文は使わない
   - 次の記事には送らない
     - 取り込んだ時刻（記事の行を作った時刻）が、ベルを作った時刻より前の記事
     - 公開日時が、当たった時刻より 1 日以上前の記事。通知の記事の行（10）を作る文の中で比べ、行を作らない。公開日時の分からない記事（フィードに日付がなく、取得の時刻を公開日時に入れたもの）は、取り込んだ時刻を公開日時とみなし、この決まりでは止めない
     - 購読を作ってから、そのフィードの取得が 1 度も成功していないうちに入った記事。購読を作った時刻と、前の回までにフィードの取得に最後に成功した時刻で見分ける。後者は、この仕事が取得を始めるときにフィードの行から読んだ `last_successful_fetch_at`（成功した取得の仕事を始めた時刻が入る）。購読したばかりの初回の取得も、OPML の取り込みで作った購読の初回の取得も、これに入る。取得の途中で購読すると、その回に記録される成功の時刻も購読より前になるので、その回と次の回の 2 回分を知らせない
     - 購読したときに受信箱へ補う最近の記事（すでに取り込んであった記事で、取り込みではない）
   - Web Push が使えない設定（19）のときと、登録した端末のない人には、判定しない
   - 判定や、送る仕事とまとめの仕事を積むのに失敗しても、取得の仕事は失敗にしない。その回の通知は出ないことがある。定期実行で拾い直さない
9. **1 人 × 1 記事に送る通知は 1 つにする。** 1 件の記事が同じ人の複数のベルに当たったら、1 つのベルに数える。選ぶ順は、購読 AND 言葉、言葉だけ、購読だけ。同じ種類なら、作ったのが古いベル。

### 量の上限

10. **当たった記事とまとめを、通知の行に残す。** 行は窓と上限（11〜13）を数えるためだけに持ち、同期しない。1 日たった行は、1 日 1 回の片付けで消す。
    - 通知の行は 2 種類で、1 つの表に持つ。当たった記事ごとの「通知の記事の行」と、まとめた窓ごとの「通知のまとめの行」。この決定で単に「記事の行」と書くときは、記事の表（`articles`）の行を指す
    - 時刻は、どれも書く文の中の DB の時計（`src/db/clock.ts` の `DB_NOW_MS`）で決める。当たった時刻（通知の記事の行を作った時刻）、通知のまとめの行を作った時刻、窓と上限とまとめの条件で比べる「今」、ベルを作った時刻。記事を取り込んだ時刻（記事の行を作った時刻）も、同じ時計で決めている
    - 行は ID、ユーザー、ベルの ID、記事の ID（通知のまとめの行は null）、窓の始まり、作った時刻、状態を持つ
    - 通知の記事の行は、当たった記事ごとに 1 つ。ユーザーと記事で一意にする（9）。作った時刻が当たった時刻になる
    - 通知のまとめの行は、まとめた窓ごとに 1 つ。記事の ID が null の行に、`(ユーザー, ベル, 窓の始まり)` の部分一意索引を張る
    - 状態は `sent`（送る）、`limited`（上限で送らない）、`bundled`（まとめに入れる。通知の記事の行だけ）。通知のまとめの行がまだない窓の `bundled` が、まとめ待ち
11. **同じベルで 10 分のあいだに当たった記事は、3 件までは 1 件ずつ送り、4 件目からは 1 通にまとめる。**
    - 窓は `[始まり, 始まり + 10 分)`。当たった時刻を含む窓（始まり > 当たった時刻 − 10 分）が同じ人の同じベルにあれば、その窓に入れる。なければ、当たった時刻を始まりにして新しい窓を開く
    - 何件目かは、その窓の通知の記事の行の数で決める。上限で送らなかった行（`limited`）も数える。1〜3 件目は、12 の上限に当てて `sent` か `limited` にする。4 件目からは `bundled` にする
    - 窓が閉じたら、`bundled` の記事を 1 通にまとめて送る（13）。3 件ちょうどなら、まとめは作らない。1 つの窓のまとめは 1 通だけ。1〜3 件目で上限のため送らなかった記事は、まとめに入れない
12. **1 人に送る通知は、直近 1 時間で 20 通まで。** 同じ人の `sent` の行（通知の記事の行と通知のまとめの行）のうち、作った時刻 > 今 − 1 時間 のものを数え、20 通に達していたら `limited` にする。端末の数によらず、1 つの通知は 1 通。上限で送らなかった記事も受信箱に未読で入っているので、未読の数（14 の `app_badge`）と reader の一覧には入る。
13. **窓と上限は行を作る文の中で数え、行が入ったときだけ送る。**
    - 通知の記事の行は、記事 1 件ごとに、公開日時の古い順に、1 つずつ文を分けて作る（同じ文で入れた行どうしは、互いを数えられない）。窓、何件目か、上限を、その文の中で数えて状態を決め、ベルが有効（消した印がない）なことと、その人の受信箱にその記事が未読であること（8）も同じ文の中で確かめる。同時に動く取得の仕事が、同じ人の行を同時に作っても、上限を超えない
    - 窓の 4 件目（その窓の最初の `bundled`）の通知の記事の行が入ったら、まとめの仕事を 1 つ、窓が閉じる時刻（始まり + 10 分）を指定して積む（[仕事の流し方](jobs.md)の 1）。仕事は、ユーザー、ベルの ID、窓の始まりを持つ
    - まとめの仕事は、1 つの文で、上限を数えて通知のまとめの行を作る。その文の中で、窓が閉じてから 1 時間以内であること（始まり + 10 分 ≤ 今 < 始まり + 70 分）、その窓に、受信箱に未読である記事の `bundled` の通知の記事の行があること、ベルが有効なことを確かめる。まとめに入れるのは、そのときその人の受信箱に未読である記事だけ。まとめは、窓が閉じてから、仕事の表の混み具合の分だけ遅れて届く
    - どちらの行も `INSERT … ON CONFLICT DO NOTHING` で作り、入った行が `sent` のときだけ、送る仕事（21）を積む。やり直した仕事は、行がもうあるので積まず、同じ通知は 2 通にならない。同じ窓のまとめの仕事が 2 度流れても、通知のまとめの行は窓ごとに 1 つなので、1 通になる。行を作ってから送る仕事を積む前に落ちたら、その通知は出ない。4 件目の通知の記事の行を作ってからまとめの仕事を積む前に落ちたら、その窓のまとめは出ない

### 通知の中身

14. **Declarative Web Push の JSON で送る。**

    ```json
    {
      "web_push": 8030,
      "notification": {
        "title": "Azure 障害 · Hacker News",
        "body": "記事のタイトル",
        "navigate": "https://reader.example/?article=<記事の ID>",
        "tag": "bell:<ベルの ID>:<記事の ID>",
        "data": { "bellId": "<ベルの ID>", "articleId": "<記事の ID>", "count": 1 }
      },
      "app_badge": 12,
      "mutable": true
    }
    ```

    - `title`：言葉のあるベルは、ベルの言葉とフィード名。言葉のないベルは、フィード名。言葉だけのベルのまとめは、言葉だけ。フィード名は、購読の表示名、フィードの名前、フィードの URL のホストの順で使い、空にしない
    - `body`：記事のタイトル（なければ要約の先頭）。まとめは、新しい順に 3 件までのタイトルを 1 行ずつ並べ、残りを「ほか n 件」とする。まとめの中の新しさは、公開日時で決め、同じなら通知の記事の行（10）を作った順で決める
    - `navigate`：reader でその記事を開く絶対 URL。`READER_URL` のオリジンに、reader が記事を開く URL（今は `/?article=<記事の ID>`）を付ける。まとめは、いちばん新しい記事を開く
    - `tag`：`bell:<ベルの ID>:<記事の ID>`。まとめは、いちばん新しい記事の ID を入れる
    - `data`：ベルの ID、記事の ID、まとめた件数（受信箱に未読である記事の数。1 件ずつの通知は 1）
    - `app_badge`：送るときの、その人の受信箱の未読の合計（`GET /api/v1/unread-counts` の `total` と同じ数え方）。最上位に整数で置く
    - `mutable: true`：reader の Service Worker が通知を作り直せるようにする。作り直せなくても、宣言した通知が出る
15. **フィード名とタイトルは、信頼できないデータとして、文字のまま入れる。** 保存してある文字を JSON の文字列として入れ、HTML として組み立てない。手を加えるのは、16 の長さの切り詰めだけ。
16. **中身は Web Push の暗号化（RFC 8291、aes128gcm）で送り、暗号化した本体を 4096 バイトまでにする。** 暗号化の前の JSON を 3993 バイトまでにする（1 つのレコードの見出し 86 バイト、区切り 1 バイト、認証タグ 16 バイトを引いた残り）。
    - 先に、フィード名を 80、記事のタイトル（または要約の先頭）を 1 件 200 コードポイントで切り、切ったら「…」を付ける
    - それでも超えたら、まとめの本文に並べるタイトルを 1 件ずつ減らす（減らした分は「ほか n 件」に入れる）。まだ超えるなら、記事のタイトル、フィード名の順に、半分ずつ切り詰める

### Web Push

17. **VAPID の鍵は、sendo が初めて要るときに作り、DB に置く。** P-256 の鍵の組を Web Crypto で作り、秘密の JWK（公開鍵の `x`・`y` を含む）にして、sendo が自分で持つ秘密の表（`app_secrets`。[画像の中継とサムネイル](images.md)の 2 と同じ）の 1 行に置く。「なければ入れる」を 1 つの文で行い、入れたあとで読み直す。自動では作り直さない。
18. **VAPID の `sub` は、設定（`VAPID_SUBJECT`）で必須にする。** `mailto:` か `https:` の URL だけを受ける。
    - JWT（RFC 8292、ES256）は、送り先のオリジン（`aud`）ごとに作る。`exp` は作った時刻の 12 時間後にする（24 時間未満）
    - 同じ `aud` には、作ってから 6 時間は同じ JWT を使い回す（Apple に合わせて 1 時間以上）。JWT はプロセスのメモリに持つ。`aud` ごとに、作っている途中のものがあればそれを待って使い、同時に何個も作らない
    - プッシュサービスが 401 か 403 を返したら、その `aud` の JWT を、作ってから 1 時間以上たっていればメモリから捨てる。次に送る仕事が作り直す
19. **Web Push を使えるのは、`VAPID_SUBJECT` と `READER_URL` がそろっているときだけにし、有無は Web Push の API で伝える**（[コンテナ版](container.md)の 3）。
    - `GET /api/v1/push` が、`available` と VAPID の公開鍵（`publicKey`。非圧縮の点の base64url）を返す。使えない設定では `available: false`、`publicKey: null` を返し、登録の `PUT` は 501（`feature_unavailable`）を返す。`DELETE` は 501 にせず、20 のとおり成功させる
    - 形の正しくない値は、エラーをログに出して、使えない設定として扱う
    - ベルの保存と同期は、Web Push が使えなくても動く（鳴らないだけ）
20. **登録は端末ごとにし、セッションに結ぶ。** `PUT /api/v1/push/registration` で、ブラウザが返した登録（エンドポイントと `p256dh`・`auth` の鍵）を、そのリクエストのセッションと人に結んで置き、204 を返す。`DELETE` で、そのセッションの登録を外す（なくても 204）。
    - この入口は、ブラウザのセッションでだけ使える。アクセストークンでは 403（`session_required`。アクセストークンや OAuth の許可を扱う入口と同じ）。状態を変えるので、同じオリジンからだけ受ける
    - エンドポイントは 2,048 文字までで、22 の確かめを通るもの。`p256dh` は base64url で 65 バイトの非圧縮の P-256 の公開鍵（Web Crypto で読めるもの）、`auth` は base64url で 16 バイト。合わなければ 400
    - 1 つのセッションに登録は 1 つ、1 つのエンドポイントにも登録は 1 つ（どちらも一意の索引）。同じセッションに同じエンドポイントと鍵があれば、何も変えない。エンドポイントか鍵が違えば、新しい ID の行を入れ、同じ文の中で、同じセッションの行と同じエンドポイントの行（ほかの人の行も）を消す（SQLite の `INSERT OR REPLACE`）
    - セッションの行が消えると、同じ文の中で、そのセッションの登録も消える。ログアウトも、ユーザーの切り替え（ログインは、前のセッションのクッキーがあればその行を消してから作る）も、これで消える。クッキーのないログインで前の人のセッションが残っても、reader はユーザーが替わると端末の登録を解除する（sendo-reader の決定）ので、残った行は、送ったときの 404 ／ 410 で消える。同じエンドポイントの登録が送り直されたときは、その文で消える。期限の切れたセッションの登録には送らず、1 日 1 回の片付けで消す
    - reader は、通知の許可があれば、起動のたびとログインのたびに登録を送り直す（冪等）。`publicKey` が手元の登録の鍵と違えば、登録し直してから送る。細かい扱いは sendo-reader の決定で決める
    - エンドポイントと鍵は秘密として扱い、ログと応答に出さない
21. **ベルの通知は、その人の登録した端末すべてに送る。送るのは仕事の表に積んだ仕事で、取り込みと切り離す。** 通知の行 1 つと端末 1 つにつき 1 つの仕事にし、仕事は通知の行と登録の行の ID を持つ。中身（14）は送るときに組み立てる。登録の行がもうないとき、ベルが外されたとき、通知の記事の行の記事がもうその人の受信箱にないか既読のとき（購読をやめたとき、ほかの端末で読んだときなど）、まとめに入れる記事が受信箱に未読で 1 件も残っていないときは送らない。
    - 要求には `Content-Encoding: aes128gcm`、`TTL: 43200`（12 時間）、`Urgency: high`、VAPID の `Authorization`（18）を付ける。`Topic` は付けない
    - 時間切れは、応答を読み終えるまでで 15 秒（[画像の中継とサムネイル](images.md)の 3 と同じ）
    - 404 ／ 410：その登録を行の ID で消し、やり直さない
    - 429 と 503 で、`Retry-After` が 1 分より先を指すとき：やり直さずに諦める
    - そのほかの 429、5xx、つながらない、時間切れ：仕事をやり直す（[仕事の流し方](jobs.md)の 5）。やり直しが尽きたら諦める
    - 3xx とそのほかの 4xx：やり直さず、状態コードをログに出す。401 ／ 403 では、18 のとおり JWT を捨てる
    - 送るのに失敗しても、記事の取り込みは止めない
22. **送る先は、ブラウザが返したエンドポイントだけにする。**
    - 登録のときに、エンドポイントを `toFetchableUrl` で確かめ、`https:` だけを受ける。通らなければ 400
    - 送るときは緩衝層の `fetch` を使い、接続する IP も確かめる（[コンテナ版](container.md)の 8）。内部のアドレスに解決されたら、送らず、その登録を行の ID で消す
    - リダイレクトは追わず、応答の中の URL へも行かない

## 理由

- **1 つの表にする：** 3 つの種類は、購読と言葉の有無の組み合わせで、判定も同期も同じ形で扱える。表を分けると、変更番号、消した印、上限の数え方を 2 組持つ。
- **既定はオフ：** 量の多いフィードに付くと鳴りすぎる。OPML で何百も購読した人に、一斉に鳴らない。
- **同じ組は 1 つにし、照合用の列の一意索引で止める：** reader は操作を手元に反映してあとで送り、届かなければ送り直す（[差分同期](sync.md)の 5）。同じ操作が 2 回届いても 1 つにまとまる。先に読んでから書くと、同時に付けた 2 つの操作が 2 つの行を作るので、正規化した言葉を列に持ち、書く文の中で一意索引に止めさせる。null を空文字にそろえないと、購読だけのベルや言葉だけのベルが重なる。
- **ID をクライアントが決められ、応答の ID を正とする：** オフラインで付けて外す操作を続けて積むには、送る前から ID が要る（[ワークスペース](workspaces.md)の 4 と同じ形）。別の端末が同じ組を先に付けていたら、その行を返せば、重なりを作らずに手元をそろえられる。
- **`feedId` で付け、項目にも載せる：** reader はフィードの ID で購読を扱い、購読の ID は `includeWorkspaces` を指定したときにだけ受け取る（[ワークスペース](workspaces.md)の 5）。書く文の中で有効な購読を引けば、やめた購読には付かない。
- **購読をやめたらトリガーで消す：** 購読を消す処理がベルを消し忘れない。2 つの文に分けると、間で落ちたときに、消えた購読を指すベルが残って配られる。変更番号も振るので、消した印が差分で届く。
- **`includeBells`：** ベルに対応する前の reader のカーソルが、ベルの番号を飛ばしたまま進むと、対応したあとにそれより前のベルが届かない。保存やワークスペースと同じ形にすれば、reader は同じ作りで扱える。
- **ベル 100 個、判定は 50 件まで：** 1 回の取得の仕事の判定は、記事の数 × ベルのある人の数 × 1 人の言葉の数（100 個 × 8 語で 800 まで）回の文字列の検索（1 回 20,000 文字まで）になる。記事を 50 件までにすれば、数人で使う規模で、最悪でも十数万回に収まる。ふだんの取得の新着は数件で、50 件を超えるのは配信元が記事をまとめて出し直したときくらい。1 時間 20 通の上限があるので、それより多いベルは鳴らしきれない。
- **入力の形は Search とそろえ、当て方は変える：** reader の Search で探して、ベルを押すだけで作れるよう、入力は同じ空白区切りの 1 つの文字列にする。当て方は通知に合わせる。
  - Search は、タイトル・要約・著者を部分一致（SQLite の `LIKE`。大文字と小文字を同じに扱うのは ASCII だけで、NFKC はない）で探し、9 個目からの言葉を捨て、1 語を 100 文字で切る
  - ベルは、タイトル・要約・フィードの本文を、NFKC と小文字、英数字の端の区切りで当て、上限を超えたら断る。黙って切ると、利用者の見ていない条件で鳴る
  - 上限を超える検索でベルを出さない扱いは、sendo-reader の決定で決める。OR は、ベルを 2 つ作れば代えられる
- **NFKC と小文字、NFKC のあとで区切る：** 日本語の文章には全角の英数字と全角の空白が混ざる。「ＡＷＳ」と「AWS」を同じに扱い、全角の空白やタブも区切りにすれば、貼り付けた言葉を断らずに済む。
- **英数字の前後だけ区切りを見る：** 「Go」「AI」のような短い英語の言葉は、部分一致では「Google」「said」に当たりすぎる。日本語は分かち書きがないので、区切りで当てると「障害」が「大規模障害」に当たらない。英数字の前後だけを見れば、「Go言語」のように日本語と続く書き方にも当たる。
- **言葉 8 個、64 文字：** 言葉は通知のタイトルに出すので、通知で読める長さにする。64 文字なら、3993 バイト（16）のうち言葉に使う量が 256 バイトに収まる。AND で絞るには 8 個で足り、判定の量も抑えられる。
- **取り込んだ回の記事だけを判定する：** 新しい記事の知らせは、取り込んだ直後でないと意味が薄い。取り込んだ回の記事だけを見れば、古い記事を探し直さない。落ちた回を定期実行で拾い直すと、判定したかの印を記事ごとに持つことになり、遅れて出る通知は、もう読んだ記事や古い話を知らせる。欠けても、記事は受信箱にある。
- **タイトル、要約、フィードの本文で判定する：** 3 つは取り込んだときにそろっている。ページから抜く本文は取り込んだあとの仕事で抜き、訳文はバッチで最大 24 時間かかる。本文を 20,000 文字で切るのは、長い記事でも判定の量を抑えるため。
- **公開日時が 1 日以上前の記事に送らない：** guid は新しくても、話は古い記事がある。配信元が guid を作り直すと、載っている過去の記事が新しい行として入る。取得が長く失敗していたフィードが直ると、止まっていた間の記事がまとめて入る。Discord は、止まっていた間の投稿をさかのぼって取り込む。公開日時の分からない記事を古いとみなすと、日付を出さないフィードのベルが鳴らなくなるので、取り込んだ時刻で見る。そうした記事が一斉に入る初回の取得は、次の決まりで止める。
- **ベルより前の記事と、初回の取得の記事に送らない：** 初回の取得では、フィードに載っている過去の記事（数十件）がまとめて入る。OPML の取り込みでは、それがフィードの数だけ続き、言葉だけのベルが一斉に鳴る。購読を作った時刻と、フィードの取得に成功した時刻で見分ければ、新しい列を持たずに、OPML、購読し直し、誰も購読していない間に止めていたフィードの再開を、同じ決まりで扱える。成功の時刻を取得を始めるときに読むのは、判定は配ったあとなので、そのときにはもう今回の時刻に書き換わっているため。共有のフィードでは、購読した直後の 1 回分（取得の途中で購読したときは 2 回分）の新着を知らせない。止める側にずれるだけで送りすぎはせず、ベルは既定でオフなので、困るのは言葉だけのベルのその 1〜2 回だけ。
- **1 人 × 1 記事に 1 通、言葉のあるベルを先に：** 同じ記事で 2 回鳴らない。言葉のあるベルを先に選べば、通知に当たった言葉が出る。
- **10 分で 3 件、そのあとはまとめる：** 量の多いフィードや、同じ話題の記事が続くときに鳴り続けない。窓が閉じてからまとめると、窓の中の残りが何件でも 1 通で済む。最初に当たったときから窓を数えるので、間の空いた記事はすぐ届く。
- **上限で送らなかった記事も窓に数える：** 窓は、そのベルがどれだけ鳴っているかを数えるもの。送ったかで数えると、1 時間の上限が空いたときに、同じ窓の 4 件目からが 1 件ずつ鳴り出す。送らなかった記事をまとめに入れないのは、上限を超えた分をあとで送らないため。
- **まとめの仕事を、窓が閉じる時刻を指定して積む：** 仕事の表は、取り出してよい時刻（`run_at`）で仕事を並べている（[仕事の流し方](jobs.md)の 1）。4 件目が入ったときに閉じる時刻を指定して積めば、まとめは閉じてすぐに流れ、遅れは仕事の表の混み具合の分だけになる。まとめる窓のない間は、仕事を積まない。通知のまとめの行を窓ごとに 1 つにすれば、仕事をやり直しても 1 通になる。積む前に落ちたら、そのまとめは出ない。1 件ずつの通知も、行を作ってから積む前に落ちたら出ない（13）ので、まとめにだけ拾い直す役を持たせない。記事は受信箱にある。閉じてから 1 時間を過ぎた窓をまとめないのは、遅れたまとめが古い話になるため（プロセスが止まっていた間に時刻の来た仕事など）。
- **1 時間 20 通：** ベルが多くても、1 人が受ける量を抑える。同じ通知は端末ごとに届くだけなので、端末の数では数えない。上限は直近 1 時間の行を、まとめは始まりが 70 分前までの窓の行を読み、どれも 1 日より前の行を見ないので、通知の行は 1 日で消してよい。
- **同じ文で数える：** 取得の仕事は同時に 4 つまで動き（[仕事の流し方](jobs.md)の 2）、別のフィードの取得が同じ人の通知を作る。先に数えてから書くと、上限を超える。ベルの有効さと、まとめの条件も同じ文で確かめ直すのは、読んだあとにベルが外されたり、まとめが作られたりしても、外したベルを鳴らさず、1 つの窓に 2 通出さないため。受信箱を確かめるのは、言葉だけのベルが購読をやめても外れないので、もう読めない記事を知らせないため。未読であることも確かめるのは、まとめは窓が閉じてから届くので、その間にほかの端末で読んだ記事を知らせないため。同じ通知の `app_badge`（未読の数）に入らない記事を、通知に出さずに済む。
- **時刻を DB の時計で決める：** SQLite は書き込みを 1 つずつ流すので、通知のまとめの行を作る文より後に流れた、通知の記事の行を作る文の「今」は、まとめの文の「今」より後になり、閉じた窓には入らず新しい窓に入る。当たった時刻に取得の仕事を始めた時刻を使うと、まとめたあとの窓に通知の記事の行が入り、その記事は送られない。ベルを作った時刻と取り込んだ時刻も、同じ時計なら、プロセスの時計のずれに左右されずに比べられる（記事の取り込んだ時刻と同じ考え）。
- **行を作ってから積む：** 積んでから行を作ると、やり直したときに 2 通出る。先に行を作れば、落ちたときに 1 通欠けるだけで済み、記事は受信箱にある。
- **Declarative Web Push：** iOS は、push を受けた Service Worker が通知を出さないと「出さない push」に数え、3 回で購読を消す。宣言した通知なら、Service Worker が失敗しても OS が出し、数えられない（2026-11-27 に、iOS 27.2 の実機と WebKit のソースで確かめた）。`app_badge` と `mutable` を最上位に置く形も、WebKit のソースで確かめた。宣言の形に対応しないブラウザ（Chrome など）では、reader の Service Worker が同じ JSON から通知を出す（sendo-reader の側で決める）。
- **`tag` に記事の ID：** iOS で通知センターから取り直した通知（`getNotifications()`）は `data` が空で、`tag` は残る。reader が裏で動いているときに通知を押すと、`notificationclick` も `navigate` も来ないので、reader は消えた通知の `tag` から押された記事を見分けられる（試作で確かめた）。まとめも同じ形にすれば、reader は 1 つの読み方で済む。ベルの ID は、どのベルの通知かを見分けるために入れる。
- **`app_badge` に未読の合計：** iOS では、宣言した push の中で `navigator.setAppBadge` を呼ぶと promise が返らず、push が時間切れになって通知ごと出ない。`app_badge` で送れば、閉じている間もバッジが変わる。バッジはアプリに 1 つしかないので、受信箱の未読の合計にし、REST API の未読の数とそろえる。push を送るのはベルの記事のときだけなので、別の端末で読んでも、次の通知か reader を開くまでバッジは変わらない。
- **3993 バイトに収める：** プッシュサービスは、暗号化した本体の 4096 バイトまでを受ける（試作では、FCM が 4097 バイトで 400 を返した）。先に長さを切っておけば、ほとんどの通知はそのまま収まり、減らす手順は保険になる。まとめに並べる件数から減らすのは、いちばん新しい記事のタイトルを残すため。
- **文字のまま入れる：** フィード名とタイトルは配信元が決める。HTML として組み立てると、reader の画面に出したときに注入の経路になる。通知は文字として出るので、手を加える理由がない。中身を暗号化するので、プッシュサービスは記事のタイトルを読めない。
- **鍵を sendo が作り、DB の 1 行に置く：** ブラウザの登録は公開鍵に結び付くので、鍵を変えると登録がすべて使えなくなる。設定で渡すと、デプロイする人が鍵を作る手間が増え、入れ違えたときに登録が黙って壊れる。DB に置けば、登録と同じバックアップに入り、戻すときも組で戻る（[コンテナ版](container.md)の 13）。秘密の JWK には公開鍵も入るので、1 行に置けば片方だけが入れ替わらない。
- **`sub` を設定で必須にする：** `sub` は、プッシュサービスが送り手に連絡するための宛先。Apple のプッシュサービスは、`sub` が URL か `mailto:` でない JWT を断る（Apple の Web Push の文書）。デプロイする人ごとに違い、sendo が決められる値ではない。
- **`exp` は 12 時間、使い回しは 6 時間：** VAPID（RFC 8292）は `exp` を 24 時間以内に求め、Apple は 1 日より先の `exp` を断り、JWT を 1 時間に 1 回より多く作り直さないよう求める。12 時間と 6 時間にすれば、時計が数時間ずれても両方の内側に収まる。
- **401 ／ 403 で、1 時間以上使った JWT を捨てる：** 使い回している JWT が断られたまま持ち続けると、作り直すまでの最大 6 時間、同じ `aud` の端末すべてに届かない。捨てれば、次の送信で作り直す。作ってから 1 時間たっていない JWT を捨てないのは、断られるたびに作り直すと、Apple の求める作り直しの間隔（1 時間に 1 回まで）を超えるため。
- **ベルは Web Push がなくても保存できる：** あとで設定を足すと、付けておいたベルがそのまま鳴り始める。reader は `available` を見て、ベルの操作と通知の許可を出すかを決められる。設定を外したあとも、登録を外す `DELETE` は失敗させない。
- **セッションに結ぶ：** 同じブラウザで別の人がログインすると、前の人の記事のタイトルが届いてしまう。セッションに結べば、ログアウトとユーザーの切り替えで、同じ文の中で登録も消える。期限の切れたセッションの端末にも送らないので、使わなくなった端末に記事のタイトルが出続けない。アクセストークンは端末に結び付かないので、登録には使わない。
- **同じセッションと同じエンドポイントの行を消す：** ブラウザは reader の Service Worker ごとに登録を 1 つ持ち、登録し直すとエンドポイントが変わる。宛先を、そのエンドポイントを最後に送ったセッションの 1 つにすれば、クッキーのないログインのあとでも、前の人の記事のタイトルが届かない。
- **置き換えたら新しい ID、同じなら変えない：** 送る仕事は登録の行の ID を持つ。置き換えた登録に同じ ID を使うと、古いエンドポイントへの仕事が 410 を受けて、新しい登録を消してしまう。同じ登録の送り直しで行を変えないのは、起動のたびに送り直しても、送っている途中の仕事を空振りさせないため。
- **鍵の形を登録のときに確かめる：** 壊れた鍵は、送るときの暗号化で失敗し、通知のたびに仕事が無駄になる。受けるときに断れば、reader が誤りに気づける。
- **端末ごとの仕事：** 1 つの端末で 500 が返っても、届いた端末にもう一度送らない。やり直しで同じ通知が 2 回届いても、端末では同じ `tag` の通知が置き換わる。
- **`TTL` は 12 時間：** 遅れて届く通知は古い話になる（取り込んだ回の記事だけを判定するのと同じ考え）。夜のあいだ端末が切れていても、翌朝には届く長さにし、それより遅れたらプッシュサービスに捨てさせる。
- **`Urgency: high`：** ベルは、利用者が選んで付けた、すぐ知りたい知らせ。プッシュサービスは、`Urgency` が低いと、端末の省電力のあいだ届けるのを遅らせてよい（RFC 8030 の 5.3）。量は 12 の上限で抑えてある。
- **`Topic` を付けない：** `Topic` は、まだ届いていない同じ `Topic` の通知を置き換える。記事ごとの通知を置き換えたくない。
- **`Retry-After` が 1 分より先なら諦める：** 仕事のやり直しは 1 分おきなので、求められた時刻より前に送り直してしまう。その時刻を指定して積み直すこともできるが、遅れた通知は古い話になるので、待たずに諦める。
- **404 ／ 410 で消す：** プッシュサービスが、その登録はもうないと答えたとき（購読の解除、アプリの削除）。試作でも、購読を解除した端末に送ると 410 が返った。
- **SSRF の対策を、登録と送信の両方に当てる：** エンドポイントはブラウザから来るが、sendo には、利用者が手で送った URL と見分けられない。reader の XSS や、API を直接呼ぶ人が、内部のアドレスを登録できる。フィードの取得と同じ確かめを当てれば、内部への送信を防げる。内部に解決された登録は使えないので消す。プッシュサービスはリダイレクトさせないので、追わなくても困らず、追えば確かめていない先へ送る道になる。

## 検討した代替案

- **購読のベルと言葉のベルを別の表にする：** 列は単純になるが、購読 AND 言葉の置き場所が決まらず、同期、上限、片付けを 2 組持つ。
- **購読の行にベルの印を持たせる：** 購読だけのベルは列 1 つで済むが、言葉のベルには別の表が要る。
- **ベルの ID を購読と言葉から決める（[あとで読むページ](saved.md)の 2 と同じ形）：** 端末どうしで同じ ID になるが、外して付け直すと同じ行を生き返らせることになり、作った時刻（8）と変更番号の扱いが増える。
- **ベルを既定でオンにする：** 新しい記事のたびに鳴り、全部は読みきれない読み方では使えない。
- **言葉を部分一致だけで当てる ／ すべて単語の区切りで当てる：** 前者は短い英語の言葉が当たりすぎ、後者は日本語に当たらない。
- **全文検索の索引（FTS5 の trigram）で当てる：** 索引は 10 分おきに少しずつ作る派生データで、取り込んだときにはまだない。trigram は 3 文字未満の言葉を引けない。
- **初回の取得を、フィードの最初の取得だけで見分ける：** 購読し直したときや、誰も購読していない間に止めていたフィードを再開したときに、たまった記事が一斉に鳴る。
- **4 件目から、そのたびにまとめを出し直す（同じ `tag` で置き換える）：** 早く分かるが、置き換えるたびに push が 1 通増え、まとめた意味が薄れる。
- **閉じた窓を、定期実行（5 分おき）で拾ってまとめる：** まとめの仕事を積む前に落ちても、次の区切りで拾い直せる。しかし、まとめる窓がなくても 1 日 288 回、ほとんど空振りの仕事を積み、まとめが閉じてから最大 5 分遅れる。1 件ずつの通知は拾い直さないので、まとめだけが違う扱いになる。
- **人ごとの上限を超えた分を、あとでまとめて送る：** 取りこぼさないが、遅れて届き、上限で抑える意味が薄れる。
- **Service Worker が中身から通知を作る（宣言の形にしない）：** Chrome ではこれで足りるが、iOS では Service Worker が失敗すると購読が消える。
- **記事の ID を `data` だけに入れる：** iOS で通知センターから取り直すと消える。
- **reader の Service Worker が、push の中でバッジを書く：** iOS では、宣言した push の中で `setAppBadge` が返らず、通知が出ない。
- **大きすぎる通知は送らない：** 中身を減らせば送れるのに、通知が消える。
- **VAPID の鍵を設定（環境変数）で渡す：** 鍵を自分で管理できるが、作る手間が増え、入れ違えると登録が黙って使えなくなる。
- **`sub` に `PUBLIC_URL` を使い、設定を足さない：** 設定は減るが、連絡の取れる宛先になるとは限らない。
- **送り先を、知っているプッシュサービスのホスト（FCM、Apple、Mozilla、Microsoft）に絞る：** 送れる先は狭くなるが、ほかのブラウザや、別のプッシュサービスを使うブラウザで届かない。内部への送信は、接続する IP の確かめで防げる。
- **登録を人だけに結ぶ（セッションに結ばない）：** ログアウトしても届き続け、同じ端末でほかの人に切り替えると、前の人の記事のタイトルが届く。
- **Web Push の有無を `GET /api/v1/features` で伝える：** 機能の有無をまとめて返す API は持たないと決めた（[コンテナ版](container.md)の 3）。

## 見直す条件

- 鳴りすぎる、または取りこぼすと分かったとき。10 分で 3 件、1 時間 20 通、ベル 100 個、言葉 8 個・64 文字の数字を直す。
- 判定が重くなり、取得の仕事が遅れるようになったとき。1 回に判定する記事の数（50 件）を減らすか、判定を `crates/`（Rust）に移す。
- まとめの仕事を積む前に落ちて、まとめが出ないことが問題になったとき。閉じた窓を拾い直す役（定期実行など）を足す。
- 次のことを始めるとき：言葉の OR・NOT・正規表現、訳文や記事のページから抜いた全文での判定、定時のまとめ、翻訳ができたときやフィードが止まったときの通知、Webhook・ntfy・Slack の出口、Capacitor で包むときの APNs ／ FCM、ミュート・自動タグ・自動スターなど通知以外のフィルタとルール、関心で選ぶ通知、続報や話題が育ったときの通知。
- ワークスペースごとに鳴らし分けたくなったとき。
- iOS やほかのブラウザで、Declarative Web Push の扱い（`app_badge`、`data`、`tag`、`navigate`）が変わったとき。
- VAPID の鍵を入れ替える必要が出たとき（漏れたときなど）。端末に登録し直してもらう手順を決める。
- reader が記事を開く URL の形を変えるとき。`navigate` を合わせる。
