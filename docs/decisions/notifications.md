# 通知

- 状態：提案中
- 関連：[差分同期](sync.md)、[コンテナ版](container.md)（3 の機能の有無、8 の接続する IP）、[仕事の流し方](jobs.md)、[ユーザーと認証](accounts.md)（セッション）、[MCP サーバー](mcp.md)、[記事のキーワード検索](article-search.md)、[画像の中継とサムネイル](images.md)（sendo が持つ秘密）

購読か言葉、またはその両方に「ベル」を付けると、当たる新しい記事を取り込んだときに、sendo が sendo-reader へ Web Push で知らせる。押すと reader でその記事を開く。閉じている間も、アプリのバッジに未読の数を出す。通知の許可、Service Worker、バッジの出し方など reader の側の扱いは、sendo-reader の決定で決める。

## 決定

### ベル

1. **ベルは人ごとに持ち、購読と言葉の組で表す。** 種類は 3 つ。
   - 購読だけ：その購読に入った記事すべて
   - 言葉だけ：その人のどの購読に入った記事でも、言葉に当たるもの
   - 購読 AND 言葉：その購読に入った記事のうち、言葉に当たるもの

   3 つを 1 つの表（`bells`）に持つ。行は ID、ユーザー、購読の ID（なければ null）、言葉（なければ null）、作った時刻、変更番号、消した印を持つ。購読も言葉もない行は作らない。種類は 2 つの列の有無で決まるので、種類の列は持たない。
2. **既定はオフ。** 購読しても、ベルは付かない。付けるのは利用者の操作（REST API と MCP）だけ。
3. **同じ人で、購読と言葉の組が同じ有効なベルは 1 つにする。**
   - 付ける操作は冪等で、すでにあればそのベルを返す。外すと消した印と新しい変更番号を付け、もう一度外しても失敗にしない。外したあとに付け直すと、新しい行を作る
   - 購読をやめると（購読に消した印が付くと）、表に付けたトリガーが、同じ文の中で、その購読の ID を持つベルに消した印を付ける。言葉だけのベルは残る
   - 有効なベルは 1 人 100 個まで。数えるのは付ける文の中で行う
   - 消した印の行は、30 日たったら 1 日 1 回の片付けで消し、回収した番号を記録する（[クライアントの設定](settings.md)の 3 と同じ）
4. **差分同期で配る。** `includeBells=true` を指定したクライアントに、`bells` で有効なベルと消した印を返す。番号とページ送りはベルの表で独立させ、ベルの位置を持たないカーソルでは、ベルを番号 0 から送る（[ワークスペース](workspaces.md)の 5、[あとで読むページ](saved.md)の 4 と同じ形）。変わったら、ほかの書き込みと同じく WebSocket で知らせる（[差分同期](sync.md)の 9）。
5. **REST API と MCP で、一覧・付ける・外すを扱う。** ほかの人の購読には付けられない（404）。言葉は、reader の Search と同じ 1 つの文字列（空白区切り）で受けて返す。MCP のツールは `list_bells`（`read`）、`add_bell` と `remove_bell`（`write`）。書き込みのツールは、利用者に頼まれたときだけ使うと説明する。

### 言葉の当て方

6. **空白で区切った言葉を、すべて含む記事に当てる（AND）。** 区切りは半角と全角の空白。OR、NOT、正規表現、引用符で囲んだ句は持たない（引用符も言葉の文字として扱う）。
   - 比べる前に、言葉と記事の文字を NFKC で正規化し、小文字にする。大文字と小文字、全角と半角の英数字を区別しない
   - 英数字（ASCII の英字と数字）で始まる言葉は、すぐ前に英数字があると当てない。英数字で終わる言葉は、すぐあとに英数字があると当てない。「Go」は「Google」に当たらず、「Go 1.26」と「Go言語」に当たる。言葉の端が日本語や記号なら、その端では前後を見ない（「障害」は「大規模障害」に当たる）
   - 言葉ごとに、タイトル、要約、フィードの本文のどれかにあれば当たる。すべての言葉が同じ欄になくてよい
   - 保存する言葉は、区切りを半角の空白 1 つにそろえ、正規化して同じになる言葉を重ねない形にする。表示には利用者が入れた大文字と小文字を残す。同じベルかどうかは、正規化した言葉の集まり（並びによらない）で決める
7. **言葉は 1〜8 個、全体で 64 文字まで。** 保存する形（区切りの空白を含む）のコードポイントで数える。言葉を付けるときに、空、上限を超える、制御文字を含む、のどれかなら 400 で断る。上限ちょうどは受ける。

### 判定

8. **取得の仕事が新しい記事を受信箱に配ったあとに、その回に入った記事だけを判定する。** 公開フィードの取得も Discord の取得も同じ。
   - 欄は、タイトル、要約、フィードの本文（プレーンテキストにした先頭 20,000 文字。[記事のキーワード検索](article-search.md)の 2 と同じ長さ）。記事のページから抜いた本文と訳文は使わない
   - 次の記事には送らない
     - 取り込んだ時刻（記事の行を作った時刻）が、ベルを作った時刻より前の記事
     - 購読を作ってから、そのフィードの取得が 1 度も成功していないうちに入った記事。購読を作った時刻と、今回より前にフィードの取得に最後に成功した時刻で見分ける。購読したばかりの初回の取得も、OPML の取り込みで作った購読の初回の取得も、これに入る
     - 購読したときに受信箱へ補う最近の記事（すでに取り込んであった記事で、取り込みではない）
   - Web Push が使えない設定（19）のときと、登録した端末のない人には、判定しない
   - 判定や、送る仕事を積むのに失敗しても、取得の仕事は失敗にしない。その回の通知は出ないことがある。定期実行で拾い直さない
9. **1 人 × 1 記事に送る通知は 1 つにする。** 1 件の記事が同じ人の複数のベルに当たったら、1 つのベルに数える。選ぶ順は、購読 AND 言葉、言葉だけ、購読だけ。同じ種類なら、作ったのが古いベル。
10. **当たった記事ごとに通知の行を作る。** 行はユーザーと記事で 1 つにし、重なりは作る文の中で確かめる。行は窓と上限（11〜13）を数えるためだけに持ち、同期しない。1 日たった行は、1 日 1 回の片付けで消す。

### 量の上限

11. **同じベルで 10 分のあいだに当たった記事は、3 件までは 1 件ずつ送り、4 件目からは 1 通にまとめる。**
    - 窓は、そのベルで窓の外で最初に当たった時刻から 10 分
    - 窓の中の 1〜3 件目は、当たったときに 1 件ずつ送る。4 件目からは、窓が閉じたときに 1 通にまとめて送る。3 件ちょうどなら、まとめは作らない。1 つの窓のまとめは 1 通だけ
12. **1 人に送る通知は、直近 1 時間で 20 通まで。** 1 件ずつの通知も、まとめた通知も 1 通と数える。端末の数によらず、1 つの通知は 1 通。20 通に達していたら、その通知は送らない。記事は受信箱に未読で入っているので、未読の数（14 の `app_badge`）と reader の一覧には入る。
13. **窓と上限は、通知の行を書く文の中で数える。** 同時に動く取得の仕事が、同じ人の通知を同時に作っても、上限を超えない。

### 通知の中身

14. **Declarative Web Push の JSON で送る。**

    ```json
    {
      "web_push": 8030,
      "notification": {
        "title": "Azure 障害 · Hacker News",
        "body": "記事のタイトル",
        "navigate": "https://reader.example/?article=<記事の ID>",
        "tag": "bell:<ベルの ID>:<記事の ID>",
        "data": { "bellId": "<ベルの ID>", "articleId": "<記事の ID>", "count": 1 }
      },
      "app_badge": 12,
      "mutable": true
    }
    ```

    - `title`：言葉のあるベルは、当たった言葉とフィード名。言葉のないベルは、フィード名。言葉だけのベルのまとめは、言葉だけ。フィード名は、購読の表示名、フィードの名前、フィードの URL のホストの順で使い、空にしない
    - `body`：記事のタイトル（なければ要約の先頭）。まとめは、新しい順に 3 件までのタイトルを 1 行ずつ並べ、残りを「ほか n 件」とする
    - `navigate`：reader でその記事を開く絶対 URL。`READER_URL` のオリジンに、reader が記事を開く URL（今は `/?article=<記事の ID>`）を付ける。まとめは、いちばん新しい記事を開く
    - `tag`：`bell:<ベルの ID>:<記事の ID>`。まとめは、いちばん新しい記事の ID を入れる
    - `data`：ベルの ID、記事の ID、まとめた件数（1 件ずつの通知は 1）
    - `app_badge`：送るときの、その人の受信箱の未読の合計（`GET /api/v1/unread-counts` の `total` と同じ数え方）。最上位に整数で置く
    - `mutable: true`：reader の Service Worker が通知を作り直せるようにする。作り直せなくても、宣言した通知が出る
15. **フィード名とタイトルは、信頼できないデータとして、文字のまま入れる。** 保存してある文字を JSON の文字列として入れ、HTML として組み立てない。手を加えるのは、16 の長さの切り詰めだけ。
16. **中身は Web Push の暗号化（RFC 8291、aes128gcm）で送り、暗号化した本体を 4096 バイトまでにする。** 暗号化の前の JSON を 3993 バイトまでにする（1 つのレコードの見出し 86 バイト、区切り 1 バイト、認証タグ 16 バイトを引いた残り）。
    - 先に、フィード名を 80 文字、記事のタイトル（または要約の先頭）を 1 件 200 文字で切り、切ったら「…」を付ける。サロゲートの組の途中では切らない
    - それでも超えたら、まとめの本文に並べるタイトルを 1 件ずつ減らす（減らした分は「ほか n 件」に入れる）。まだ超えるなら、記事のタイトル、フィード名の順に、半分ずつ切り詰める

### Web Push

17. **VAPID の鍵は、sendo が初めて要るときに作り、DB に置く。** P-256 の鍵の組を Web Crypto で作り、sendo が自分で持つ秘密の表（`app_secrets`。[画像の中継とサムネイル](images.md)の 2 と同じ）に置く。「なければ入れる」を 1 つの文で行う。自動では作り直さない。
18. **VAPID の `sub` は、設定（`VAPID_SUBJECT`）で必須にする。** `mailto:` か `https:` の URL だけを受ける。
    - JWT（RFC 8292、ES256）は、送り先のオリジン（`aud`）ごとに作る。`exp` は作った時刻の 12 時間後にする（24 時間未満）
    - 同じ `aud` には、作ってから 6 時間は同じ JWT を使い回す（Apple に合わせて 1 時間以上）。JWT はプロセスのメモリに持つ
19. **Web Push を使えるのは、`VAPID_SUBJECT` と `READER_URL` がそろっているときだけにし、有無は Web Push の API で伝える**（[コンテナ版](container.md)の 3）。
    - `GET /api/v1/push` が、`available` と VAPID の公開鍵（`publicKey`）を返す。使えない設定では `available: false`、`publicKey: null` を返し、登録の入口は 501（`feature_unavailable`）を返す
    - 形の正しくない値は、エラーをログに出して、使えない設定として扱う
    - ベルの保存と同期は、Web Push が使えなくても動く（鳴らないだけ）
20. **登録は端末ごとにし、セッションに結ぶ。** `PUT /api/v1/push/registration` で、ブラウザが返した登録（エンドポイントと `p256dh`・`auth` の鍵）を、そのリクエストのセッションと人に結んで置く。`DELETE` で外す。
    - この入口は、ブラウザのセッションでだけ使える（アクセストークンでは使えない）。状態を変えるので、同じオリジンからだけ受ける
    - 1 つのセッションに登録は 1 つ、同じエンドポイントの登録も 1 つにする。同じ登録を 2 回送っても 1 つのまま。別のエンドポイントを送ると置き換える
    - セッションの行が消えると、同じ文の中で、そのセッションの登録も消える。ログアウトも、ユーザーの切り替え（ログインは前のセッションを消してから作る）も、これで消える。期限の切れたセッションの登録には送らず、1 日 1 回の片付けで消す
    - エンドポイントと鍵は秘密として扱い、ログと応答に出さない
21. **ベルの通知は、その人の登録した端末すべてに送る。送るのは仕事の表に積んだ仕事で、取り込みと切り離す。** 端末ごとに 1 つの仕事にする。
    - 404 ／ 410：その登録を行の ID で消し、やり直さない
    - 429、5xx、つながらない、時間切れ：仕事をやり直す（[仕事の流し方](jobs.md)の 5）。やり直しが尽きたら諦める
    - 3xx とそのほかの 4xx：やり直さず、状態コードをログに出す
    - 送るのに失敗しても、記事の取り込みは止めない
22. **送る先は、ブラウザが返したエンドポイントだけにする。**
    - 登録のときに、エンドポイントを `toFetchableUrl` で確かめ、`https:` だけを受ける。通らなければ 400
    - 送るときは緩衝層の `fetch` を使い、接続する IP も確かめる（[コンテナ版](container.md)の 8）。内部のアドレスに解決されたら、送らず、やり直さない
    - リダイレクトは追わず、応答の中の URL へも行かない

## 理由

- **1 つの表にする：** 3 つの種類は、購読と言葉の有無の組み合わせで、判定も同期も同じ形で扱える。表を分けると、変更番号、消した印、上限の数え方を 2 組持つ。
- **既定はオフ：** 量の多いフィードに付くと鳴りすぎる。OPML で何百も購読した人に、一斉に鳴らない。
- **同じ組は 1 つ、付けるのは冪等：** reader は操作を手元に反映してあとで送り、届かなければ送り直す（[差分同期](sync.md)の 5）。同じ操作が 2 回届いても 1 つにまとまる。
- **購読をやめたらトリガーで消す：** 購読を消す処理がベルを消し忘れない。2 つの文に分けると、間で落ちたときに、消えた購読を指すベルが残って配られる。
- **`includeBells`：** ベルに対応する前の reader のカーソルが、ベルの番号を飛ばしたまま進むと、対応したあとにそれより前のベルが届かない。保存やワークスペースと同じ形にすれば、reader は同じ作りで扱える。
- **ベル 100 個：** 1 記事の判定の量は、ベルの数 × 言葉の数 × 欄の長さで決まる。100 個 × 8 語でも、1 記事で 800 回の文字列の検索（20,000 文字まで）に収まる。1 時間 20 通の上限があるので、それより多いベルは鳴らしきれない。
- **言葉は Search と同じ形で、AND だけ：** reader の Search で探して、ベルを押すだけで作れる。OR は、ベルを 2 つ作れば代えられる。
- **NFKC と小文字：** 日本語の文章には全角の英数字が混ざる。「ＡＷＳ」と「AWS」を同じに扱いたい。
- **英数字の前後だけ区切りを見る：** 「Go」「AI」のような短い英語の言葉は、部分一致では「Google」「said」に当たりすぎる。日本語は分かち書きがないので、区切りで当てると「障害」が「大規模障害」に当たらない。英数字の前後だけを見れば、「Go言語」のように日本語と続く書き方にも当たる。
- **言葉 8 個、64 文字：** 言葉は通知のタイトルに出すので、通知で読める長さにする。64 文字なら、3993 バイト（16）のうち言葉に使う量が 256 バイトに収まる。AND で絞るには 8 個で足り、判定の量も抑えられる。
- **取り込んだ回の記事だけを判定する：** 新しい記事の知らせは、取り込んだ直後でないと意味が薄い。取り込んだ回の記事だけを見れば、古い記事を探し直さない。落ちた回を定期実行で拾い直すと、判定したかの印を記事ごとに持つことになり、遅れて出る通知は、もう読んだ記事や古い話を知らせる。欠けても、記事は受信箱にある。
- **タイトル、要約、フィードの本文で判定する：** 3 つは取り込んだときにそろっている。ページから抜く本文は取り込んだあとの仕事で抜き、訳文はバッチで最大 24 時間かかる。本文を 20,000 文字で切るのは、長い記事でも判定の量を抑えるため。
- **ベルより前の記事と、初回の取得の記事に送らない：** 初回の取得では、フィードに載っている過去の記事（数十件）がまとめて入る。OPML の取り込みでは、それがフィードの数だけ続き、言葉だけのベルが一斉に鳴る。購読を作った時刻と、フィードの取得に成功した時刻で見分ければ、新しい列を持たずに、OPML、購読し直し、誰も購読していない間に止めていたフィードの再開を、同じ決まりで扱える。共有のフィードでは、購読した直後の 1 回分の新着を知らせないが、ベルは既定でオフなので、困るのは言葉だけのベルのその 1 回だけ。
- **1 人 × 1 記事に 1 通、言葉のあるベルを先に：** 同じ記事で 2 回鳴らない。言葉のあるベルを先に選べば、通知に当たった言葉が出る。
- **10 分で 3 件、そのあとはまとめる：** 量の多いフィードや、同じ話題の記事が続くときに鳴り続けない。窓が閉じてからまとめると、窓の中の残りが何件でも 1 通で済む。最初に当たったときから窓を数えるので、間の空いた記事はすぐ届く。
- **1 時間 20 通：** ベルが多くても、1 人が受ける量を抑える。同じ通知は端末ごとに届くだけなので、端末の数では数えない。窓も上限も 1 時間より前を見ないので、通知の行は 1 日で消してよい。
- **同じ文で数える：** 取得の仕事は同時に 4 つまで動き（[仕事の流し方](jobs.md)の 2）、別のフィードの取得が同じ人の通知を作る。先に数えてから書くと、上限を超える。
- **Declarative Web Push：** iOS は、push を受けた Service Worker が通知を出さないと「出さない push」に数え、3 回で購読を消す。宣言した通知なら、Service Worker が失敗しても OS が出し、数えられない（2026-11-27 に、iOS 27.2 の実機と WebKit のソースで確かめた）。`app_badge` と `mutable` を最上位に置く形も、WebKit のソースで確かめた。宣言の形に対応しないブラウザ（Chrome など）では、reader の Service Worker が同じ JSON から通知を出す（sendo-reader の側で決める）。
- **`tag` に記事の ID：** iOS で通知センターから取り直した通知（`getNotifications()`）は `data` が空で、`tag` は残る。reader が裏で動いているときに通知を押すと、`notificationclick` も `navigate` も来ないので、reader は消えた通知の `tag` から押された記事を見分けられる（試作で確かめた）。まとめも同じ形にすれば、reader は 1 つの読み方で済む。ベルの ID は、どのベルの通知かを見分けるために入れる。
- **`app_badge` に未読の合計：** iOS では、宣言した push の中で `navigator.setAppBadge` を呼ぶと promise が返らず、push が時間切れになって通知ごと出ない。`app_badge` で送れば、閉じている間もバッジが変わる。バッジはアプリに 1 つしかないので、受信箱の未読の合計にし、REST API の未読の数とそろえる。push を送るのはベルの記事のときだけなので、別の端末で読んでも、次の通知か reader を開くまでバッジは変わらない。
- **3993 バイトに収める：** プッシュサービスは、暗号化した本体の 4096 バイトまでを受ける（試作では、FCM が 4097 バイトで 400 を返した）。先に長さを切っておけば、ほとんどの通知はそのまま収まり、減らす手順は保険になる。まとめに並べる件数から減らすのは、いちばん新しい記事のタイトルを残すため。
- **文字のまま入れる：** フィード名とタイトルは配信元が決める。HTML として組み立てると、reader の画面に出したときに注入の経路になる。通知は文字として出るので、手を加える理由がない。中身を暗号化するので、プッシュサービスは記事のタイトルを読めない。
- **鍵を sendo が作り、DB に置く：** ブラウザの登録は公開鍵に結び付くので、鍵を変えると登録がすべて使えなくなる。設定で渡すと、デプロイする人が鍵を作る手間が増え、入れ違えたときに登録が黙って壊れる。DB に置けば、登録と同じバックアップに入り、戻すときも組で戻る（[コンテナ版](container.md)の 13）。
- **`sub` を設定で必須にする：** `sub` は、プッシュサービスが送り手に連絡するための宛先。Apple のプッシュサービスは、`sub` が URL か `mailto:` でない JWT を断る（Apple の Web Push の文書）。デプロイする人ごとに違い、sendo が決められる値ではない。
- **`exp` は 12 時間、使い回しは 6 時間：** VAPID（RFC 8292）は `exp` を 24 時間以内に求め、Apple は 1 日より先の `exp` を断り、JWT を 1 時間に 1 回より多く作り直さないよう求める。12 時間と 6 時間にすれば、時計が数時間ずれても両方の内側に収まる。
- **`READER_URL` も要る：** `navigate` には、reader の記事の絶対 URL が要る。
- **ベルは Web Push がなくても保存できる：** あとで設定を足すと、付けておいたベルがそのまま鳴り始める。reader は `available` を見て、ベルの操作と通知の許可を出すかを決められる。
- **セッションに結ぶ：** 同じブラウザで別の人がログインすると、前の人の記事のタイトルが届いてしまう。ログインは前のセッションを消すので、セッションに結べば、ログアウトとユーザーの切り替えで、同じ文の中で登録も消える。期限の切れたセッションの端末にも送らないので、使わなくなった端末に記事のタイトルが出続けない。アクセストークンは端末に結び付かないので、登録には使わない。ブラウザは reader の Service Worker ごとに登録を 1 つ持ち、登録し直すとエンドポイントが変わるので、セッションごとに 1 つにして置き換える。
- **端末ごとの仕事：** 1 つの端末で 500 が返っても、届いた端末にもう一度送らない。
- **404 ／ 410 で消す：** プッシュサービスが、その登録はもうないと答えたとき（購読の解除、アプリの削除）。試作でも、購読を解除した端末に送ると 410 が返った。
- **SSRF の対策を、登録と送信の両方に当てる：** エンドポイントはブラウザから来るが、sendo には、利用者が手で送った URL と見分けられない。reader の XSS や、API を直接呼ぶ人が、内部のアドレスを登録できる。フィードの取得と同じ確かめを当てれば、内部への送信を防げる。プッシュサービスはリダイレクトさせないので、追わなくても困らず、追えば確かめていない先へ送る道になる。

## 検討した代替案

- **購読のベルと言葉のベルを別の表にする：** 列は単純になるが、購読 AND 言葉の置き場所が決まらず、同期、上限、片付けを 2 組持つ。
- **購読の行にベルの印を持たせる：** 購読だけのベルは列 1 つで済むが、言葉のベルには別の表が要る。
- **ベルを既定でオンにする：** 新しい記事のたびに鳴り、全部は読みきれない読み方では使えない。
- **言葉を部分一致だけで当てる ／ すべて単語の区切りで当てる：** 前者は短い英語の言葉が当たりすぎ、後者は日本語に当たらない。
- **全文検索の索引（FTS5 の trigram）で当てる：** 索引は 10 分おきに少しずつ作る派生データで、取り込んだときにはまだない。trigram は 3 文字未満の言葉を引けない。
- **初回の取得を、フィードの最初の取得だけで見分ける：** 購読し直したときや、誰も購読していない間に止めていたフィードを再開したときに、たまった記事が一斉に鳴る。
- **4 件目から、そのたびにまとめを出し直す（同じ `tag` で置き換える）：** 早く分かるが、置き換えるたびに push が 1 通増え、まとめた意味が薄れる。
- **人ごとの上限を超えた分を、あとでまとめて送る：** 取りこぼさないが、遅れて届き、上限で抑える意味が薄れる。
- **Service Worker が中身から通知を作る（宣言の形にしない）：** Chrome ではこれで足りるが、iOS では Service Worker が失敗すると購読が消える。
- **記事の ID を `data` だけに入れる：** iOS で通知センターから取り直すと消える。
- **reader の Service Worker が、push の中でバッジを書く：** iOS では、宣言した push の中で `setAppBadge` が返らず、通知が出ない。
- **大きすぎる通知は送らない：** 中身を減らせば送れるのに、通知が消える。
- **VAPID の鍵を設定（環境変数）で渡す：** 鍵を自分で管理できるが、作る手間が増え、入れ違えると登録が黙って使えなくなる。
- **`sub` に `PUBLIC_URL` を使い、設定を足さない：** 設定は減るが、連絡の取れる宛先になるとは限らない。
- **送り先を、知っているプッシュサービスのホスト（FCM、Apple、Mozilla、Microsoft）に絞る：** 送れる先は狭くなるが、ほかのブラウザや、別のプッシュサービスを使うブラウザで届かない。内部への送信は、接続する IP の確かめで防げる。
- **登録を人だけに結ぶ（セッションに結ばない）：** ログアウトしても届き続け、同じ端末でほかの人に切り替えると、前の人の記事のタイトルが届く。
- **Web Push の有無を `GET /api/v1/features` で伝える：** 機能の有無をまとめて返す API は持たないと決めた（[コンテナ版](container.md)の 3）。

## 見直す条件

- 鳴りすぎる、または取りこぼすと分かったとき。10 分で 3 件、1 時間 20 通、ベル 100 個、言葉 8 個・64 文字の数字を直す。
- 次のことを始めるとき：言葉の OR・NOT・正規表現、訳文や記事のページから抜いた全文での判定、定時のまとめ、翻訳ができたときやフィードが止まったときの通知、Webhook・ntfy・Slack の出口、Capacitor で包むときの APNs ／ FCM、ミュート・自動タグ・自動スターなど通知以外のフィルタとルール、関心で選ぶ通知、続報や話題が育ったときの通知。
- ワークスペースごとに鳴らし分けたくなったとき。
- iOS やほかのブラウザで、Declarative Web Push の扱い（`app_badge`、`data`、`tag`、`navigate`）が変わったとき。
- VAPID の鍵を入れ替える必要が出たとき（漏れたときなど）。端末に登録し直してもらう手順を決める。
- reader が記事を開く URL の形を変えるとき。`navigate` を合わせる。
