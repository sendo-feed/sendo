# クライアントの設定

- 状態：提案中
- 関連：[差分同期](sync.md)、[ユーザーと認証](accounts.md)、[テックスタック](tech-stack.md)、[古い記事の片付け](retention.md)

公式リーダー（sendo-reader）の設定（テーマ、文字の大きさ、一覧ごとの形や並び順、スワイプの割り当てなど）は、その端末のブラウザにしかなく、別の端末に引き継がれない。これを sendo が預かり、差分同期で配る。スマホと PC では合う設定が違うので、端末の種類ごとに分けて預かる。

## 決定

1. **ユーザー × 端末の種類ごとに、項目（名前）ごとの行で持つ。**
   - 端末の種類は `mobile` と `desktop` の 2 つに限る。どちらとして動くかはクライアントが決めて送り、sendo は端末を見分けない。DB の列は文字列にしておき、種類を足すときは API の検証を直すだけにする
   - 1 つの項目が 1 行。同じ種類の 2 台が別の項目を同時に変えても、どちらも残る。同じ項目を変えたら、sendo が後から受けたほうを採る（[差分同期](sync.md)の 5 と同じ）
2. **項目は、名前と JSON の値の組。sendo は中身を解釈しない。** 項目を足したり変えたりするのに、sendo の変更は要らない。
   - 名前は `<クライアント>.<残り>` の形にする。公式リーダーは `reader.` で始める。sendo が確かめるのは形だけで、クライアントの一覧は持たない
   - 値は JSON の値なら何でもよい（オブジェクト、配列、文字列、数、真偽、null）。sendo は、JSON であること、大きさ、入れ子の深さだけを確かめる
   - sendo は、設定の中身で動きを変えない。購読をやめても、そのフィードの名前を含む項目を sendo は消さない（名前を解釈しないので）。消すのはクライアントの仕事
3. **変更番号を振り、消すときは消した印を付ける。** フォルダや購読と同じ扱いにする。
   - 置くたびに、設定の表の変更番号を同じ文の中で振る（[差分同期](sync.md)の 1）
   - 消すと、行は残して、消した印と新しい番号を付け、値は捨てる。同じ名前でもう一度置くと、印が外れる
   - 今と同じ値を置いたとき、ない項目やもう消してある項目を消したときは、何も変えない（番号も振らない）。送り直しで、書き込みも同期の知らせも増えない
   - 消した印の行は、30 日たったら物理的に消す（受信箱の消した記録と同じ期間。1 日 1 回の片付けで行う）。回収した番号を人ごとに記録し、それより古いカーソルには、今と同じ `invalid_cursor` で最初から同期し直してもらう
4. **差分同期（`GET /api/v1/sync`）で配る。** 応答に `settings` の配列を足す。各項目は、端末の種類・名前・値・消した印を持つ。
   - **両方の種類を返す。** クライアントは、自分の種類の分だけを使えばよい。カーソルは種類によらない
   - 最初の同期（カーソルなし）では、消した印の付いていない項目をすべて返す。差分では、消した印の付いた項目も返す
   - 番号とページ送りは、ほかの表と同じく設定だけで独立している。カーソルの中身が増えるが、クライアントはそのまま送り返すだけ。設定の位置を持たない古いカーソルは、設定だけを最初から送る（全体の同期し直しはさせない）
5. **書く入口は 1 つで、まとめて受ける。** `PATCH /api/v1/settings/{deviceType}` に、置く項目（`put`：名前と値の組の配列）と、消す項目（`remove`：名前の配列）を送る。
   - 1 回のリクエストで、合わせて 100 項目まで。同じ名前を 2 度入れたリクエストは断る
   - 成功したら 204 を返す。結果は、次の同期で番号付きで戻ってくる
   - 何度送り直しても同じ結果になる。1 つの項目だけを変えるときも、同じ入口を使う
   - 上限を超えるリクエストは、項目を 1 つも置かずに断る。上限は、書き込みと同じ文の中で確かめる
   - 同期を使わないクライアントのために、`GET /api/v1/settings/{deviceType}` で、その種類の項目（消していないもの）をすべて返す
6. **上限**（端末の種類ごと。消した印の行は数えない）

   | 対象 | 上限 | 超えたとき |
   |---|---|---|
   | 名前 | 128 文字。`<クライアント>.<残り>`。クライアントは英小文字で始まる英小文字・数字・ハイフン（32 文字まで）、残りは空白を除く印字できる ASCII | 400 `invalid_request` |
   | 値 | JSON にして 8KB（UTF-8）、入れ子は 16 段まで | 400 `invalid_request` |
   | 1 回のリクエスト | 100 項目、本文 1MB | 400 `invalid_request` ／ 413 `too_large` |
   | 項目の数 | 1,000 | 409 `settings_full` |
   | 名前と値の合計 | 256KB | 409 `settings_full` |

7. **使えるのは REST API と差分同期だけ。** 認証はほかの REST API と同じ（セッションのクッキーか、アクセストークン）。Google Reader API と MCP には出さない。
8. **ユーザーを消すと、設定も消える**（外部キーで一緒に消す）。古い記事の片付けとは関係しない。

## 理由

- **項目ごとの行**：1 つの種類をまとめて 1 つの値にすると、2 台が別の項目を変えたときに、後から受けたほうが先のほうを丸ごと上書きして消す。防ぐには版の比較とやり直しがクライアントに要り、ローカルファーストの「送り直すだけ」と合わない。行ごとなら、「後から受けたほうを採る」が項目ごとに当たる。
- **種類を 2 つに限る**：上限は種類ごとなので、種類を自由な文字列にすると、1 人が預けられる量に上限がなくなる（種類の数の上限と、その検査が別に要る）。端末の ID を種類にして「端末ごとの設定」にする使い方もできてしまう。種類は、同期で配る範囲を決める、sendo にも見える区切りなので、中身（項目）と違って sendo が決めておく。足すのは API の検証の 1 行で済む。
- **名前と JSON の値**：設定の項目は reader の都合で増える。sendo が項目を知っていると、reader を変えるたびに sendo のスキーマと API を直すことになり、各自が fork してデプロイする sendo と reader の版がずれたときに壊れる。
- **名前の先頭にクライアント**：あとでほかのクライアントが同じ仕組みを使っても、名前がぶつからない。列を分けるほどの違い（クライアントごとの上限や権限）は、まだ要らない。
- **消した印（行を残す）**：既定に戻したこと、購読をやめたフィードの一覧の設定を捨てたことを、ほかの端末に伝える必要がある。数が少ないので、フォルダや購読と同じく行に印を付けるのがいちばん単純（受信箱のような、別の表の記録とトリガーは要らない）。同じ名前で置き直せば同じ行に戻るので、番号も行の ID で振れる。
- **消した印を 30 日で回収する**：一覧ごとの設定は、名前にフィードの ID が入るので、購読を入れ替えるたびに印の行が増え続ける。受信箱の消した記録と同じ 30 日にそろえれば、30 日より長く開かなかった端末は、もともと最初から同期し直すことになるので、クライアントに新しい決まりが増えない。
- **同じ値なら何も変えない**：操作キューの送り直しや、初めての端末のまとめ送りで、D1 の書き込み（1 日 10 万行）と、ほかの端末への知らせを増やさない。
- **両方の種類を返す**：種類で絞ると、カーソルが「どの種類で読んできたか」に依存する。途中で種類を変えた端末（絞り方を変えたクライアント）は、変える前の項目を取りこぼす。量は種類ごとに 256KB まで、ふつうは数十 KB なので、絞らないほうが安全で単純。もう一方の種類の設定を写す機能も、あとで reader だけで作れる。
- **入口を 1 つにして本文で名前を送る**：名前には一覧のパス（`/` を含む）が入りうるので、URL のパスに載せるとエスケープの扱いで壊れやすい。初めて同期する端末がまとめて送る用途と、1 つだけ変える用途を、同じ入口で受けられる。
- **上限の数字**：reader の見込み（一覧ごとの設定が 500 まで、ほかは十数個）の 2 倍を項目の数にした。値の 8KB は、畳んでいるフォルダの ID の配列（100 個で 4KB ほど）が 1 つの項目に入る大きさ。合計の 256KB は、同期の 1 回の応答に載せても軽い大きさ。
- **数と合計の超過は 409**：リクエストの形は正しく、今の状態とぶつかっているだけなので、項目を消せば通る。5xx にすると、クライアントの操作キューが送り直し続ける。

## 検討した代替案

- **種類ごとに 1 つの値（JSON）でまとめて持つ**：表も API も単純だが、別の項目の同時の変更が消える。
- **種類を自由な文字列にする**：タブレットなどを sendo の変更なしで足せるが、預かる量の上限が崩れる。
- **sendo が項目を知っている（列やスキーマで持つ）**：値を確かめられるが、項目を足すたびに sendo を直す。
- **物理的に消して、消した記録を別の表に残す（受信箱と同じ）**：行は増えないが、表とトリガーが増える。数が少ないので見合わない。
- **変わったら、その種類の設定をすべて送り直す（消した印を持たない）**：消したことを伝える仕組みが要らないが、1 つ変えるたびに全部を送り、行を消したことを番号で知らせる別の仕組み（種類ごとの版）が要る。
- **同期で、クライアントの種類の分だけを返す**：応答は少し小さくなるが、カーソルが種類に依存する。
- **項目ごとの入口（`PUT` ／ `DELETE /settings/{deviceType}/{name}`）**：REST らしいが、名前を URL に載せることになり、まとめて送れない。
- **「まだなければ置く」の指定を足す**：初めての端末が、ほかの端末の設定を上書きしないために使える。クライアントが、同期で受けた設定にない項目だけを送れば足りるので、足さない。

## 見直す条件

- 公式リーダーのほかのクライアントが、この仕組みを使い始めたとき（クライアントごとの上限、アクセストークンの範囲）。
- 3 つ目の種類（タブレットなど）や、端末ごとの設定が要ると分かったとき。
- sendo が設定の中身で動きを変える話が出たとき（その項目は、ここではなく、sendo が知っている形で持つ）。
- 上限（1,000 項目、256KB）が、使ってみて足りないと分かったとき。
