# 記事を開いた履歴

- 状態：提案中
- 関連：[ユーザーと認証](accounts.md)、[MCP サーバー](mcp.md)、[保存容量と古い記事の片付け](retention.md)

利用者が sendo-reader で開いた記事を、あとで日時から探せるようにする。

## 決定

1. **最初は記事の開封を記録する。** 利用者が sendo-reader で受信箱の記事を開いたとき、端末がイベント ID と開いた時刻を付ける。端末は `POST /api/v1/activity` に 50 件までまとめて送る。Sendo がイベントの種類を `article_opened`、操作元を `reader` として記録する。MCP による記事取得は開封に数えない。
2. **ユーザーとイベント ID の組を一意にする。** オフラインからの再送でも開封回数を増やさない。書き込みと同じ文で、そのユーザーの受信箱に記事があることを確かめる。記録には記事 ID と、そのときのタイトル・URL を持つ。後から受信箱や記事本体が片付いても、履歴には保存時のタイトルと URL が残る。
3. **90 日間残す。** 開封時刻が 90 日より前か、サーバーの時刻より 5 分を超えて先なら記録しない。履歴はユーザーごとに 20,000 件までとし、上限は登録と同じ文で確かめる。応答は今回新しく記録した件数を返す。期限を過ぎた行は日次の片付けで少しずつ消す。
4. **MCP からは `list_activity` で読む。** 認証したユーザーの履歴を開封時刻の新しい順に返す。期間・種類・操作元で絞り込め、続きを取得できる。履歴は差分同期に載せない。閲覧時間、リンクのクリック、評価、MCP による状態変更の履歴は、そのデータを記録する段階で追加する。

## 理由

- 既読には一括操作も含まれ、未読に戻すとその時刻を失う。開封の記録があれば実際に開いた時系列を取得できる。
- 利用者が開いたときの記録を元にするので、閲覧傾向を調べるときに Claude の記事取得が混ざらない。
- 端末でまとめて送れば、オフラインから再開でき、画面を開くたびに個別の書き込みを待たずに済む。保持期間と件数を抑え、日次の回収で容量を管理する。
