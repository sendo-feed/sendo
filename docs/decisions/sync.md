# 差分同期

- 状態：提案中
- 関連：[ユーザーと認証](accounts.md)、[テックスタック](tech-stack.md)、[技術構成](../tech-deck.md)（方針 03、未決事項 7）

sendo-reader はローカルファーストで作る（画面はネットワークを待たず、ブラウザの SQLite に同期する）。そのための、サーバー（sendo）とクライアントの間の同期の決まり。

## 決定

1. **変更番号で同期する。** 人ごとのデータ（フォルダ、購読、記事の受信箱＝既読・スター）の行に、変更番号（`seq`）を持たせる。行を作ったり変えたりするたびに、その表の中でいちばん大きい番号に 1 を足した番号を、同じ文の中で振る。
   - D1 は文を 1 つずつ順に処理するので、番号の順は書き込みの順と一致し、あとから小さい番号の変更が現れることはない（取りこぼさない）。同じ文で変えた行は同じ番号になってよい
   - **番号を二度と使わない。** 行を物理的に消すと表の最大が下がり、同期済みの番号がもう一度振られて取りこぼす。そこで、行が物理的に消えたら、その行の番号で、別の表の「下限」を引き上げる。これは表に付けたトリガーで行い、削除と下限の更新を同じ文の中で一緒に起こす（間にほかの書き込みが入らない）。番号は「表の最大と下限の大きいほう＋1」を、同じ文の中で振る
   - 番号は表ごとに増やし、クライアントは表ごとの番号をまとめた「カーソル」を持つ。カーソルの中身には意味を持たせず、クライアントはそのまま送り返すだけにする
   - 記事の公開日時や作成時刻は、同期の目印に使わない（公開日時の古い記事があとから入ると取りこぼす）
2. **1 回のリクエストで差分を取る。** `GET /api/v1/sync?cursor=…` で、カーソルより後に変わったフォルダ・購読・受信箱の行と、新しいカーソルを返す。受信箱の行には、記事の本体（タイトル、要約、URL など）を付ける。多すぎるときは途中で区切り、続きがあることを知らせる。
3. **消したものは「消した」という記録で伝える。**
   - フォルダと購読は、消すときに行を消さず、消した印と新しい変更番号を付ける
   - 受信箱の行は物理的に消す（購読をやめたフィードの記事は、スターを付けたものを除いて受信箱から消える）。行が消えたら、表に付けたトリガーが、削除と同じ文の中で、その記事の「消した記録」を別の表に残す。記録には受信箱の表の続きの番号を振り、下限もその番号まで引き上げる。同期では、受信箱の行と消した記録を番号の順に混ぜて返す
   - **クライアントは、ほかの表の変化から行を消さない。** 手元の記事を消すのは、その記事の消した記録が届いたときだけにする（購読をやめた知らせを見て、そのフィードの記事を消さない）
   - 消した印の行と消した記録は、一定の期間がたったら物理的に消してよい（下限はトリガーが記録する）。それより古いカーソルが来たら、最初から同期し直すよう伝える。そのために、回収した範囲の番号も記録しておく
4. **最初の同期は、手元に置く範囲だけ。** カーソルなしで来たら、未読の記事、スターを付けた記事、直近 30 日に受信箱に入った記事を返す。それより古い記事は、必要なときに通常の API で読む（手元には置かない）。
5. **クライアントの操作は、手元にすぐ反映して、あとで送る。** 既読・スター・購読の変更などは、ローカルの DB にすぐ反映し（楽観的更新）、操作キューに積んで通常の REST API で送る。サーバーは操作を冪等に受ける。ぶつかったら、サーバーが後から受けたほうを採る。送った操作の結果は、次の同期で番号付きで戻ってくる。
6. **まとめて既読の境界に、カーソルを使えるようにする。** 「すべて既読」は、クライアントが同期済みの範囲（カーソルまで）に入っていた記事だけを既読にできるようにする。手元に届いていない記事を、見ないまま既読にしない。
7. **記事の本体は、取り込んだあとは変えない。** 同期するのは受信箱の行（既読・スター）の変化だけで、記事のタイトルや要約の書き換えは追わない。

## 理由

- **変更番号**：時刻は、時計のずれや処理の始まりと書き込みの順のずれで、取りこぼしが起きる。D1 は文を 1 つずつ処理するので、同じ文の中で「最大＋1」を振れば、ロックも batch も要らずに、書き込み順の番号が作れる（[テックスタック](tech-stack.md)の「冪等な書き込み、batch に頼らない」に沿う）。
- **番号の下限をトリガーで記録する**：行を物理的に消さない（すべて消した印にする）方法もあるが、行が増え続ける。消す前にコードで下限を記録すると、記録と削除の間にほかの更新が入ったとき、記録した下限より大きい番号の行まで消えて、番号が重なる（#21 のレビューで実際に確かめられた）。トリガーなら、削除と下限の更新が同じ文の中で起き、消す側のコードが記録を忘れることもない。SQLite（D1）にも Postgres にもトリガーがあるので、移植の妨げにならない。
- **表ごとの番号をまとめたカーソル**：表をまたいで 1 つの番号を振るには、番号の表を別に持って 2 つの文で更新する必要があり、その間にほかの書き込みが入ると番号が重なる。表ごとなら 1 つの文で済む。クライアントには中身を見せないので、あとで作りを変えられる。
- **1 回のリクエスト**：iOS ではバックグラウンドで同期できないので、起動したときの 1 回の速さが体感を決める（[技術構成](../tech-deck.md)）。
- **消した印と消した記録**：行を消すだけでは、クライアントに「消えた」ことを伝えられない。フォルダと購読は数が少ないので、行に印を付けて残す。受信箱は行が多く、一覧や未読の数など読む処理も多いので、行は消し、消したことだけを別の表に残す。
- **ほかの表の変化から消さない**：番号もページ送りも表ごとに別なので、表をまたいだ順序は保証されない。購読をやめた知らせを見て記事を消す決まりだと、購読の変更が 1 ページに収まらないときに、購読し直して入れ直した記事が先に届き、あとから届いた「購読をやめた」で消してしまう（#25 で確かめた）。また、スターを外してから購読をやめると、行が消えてスターを外した変更も届かず、クライアントは古いスターを根拠に記事を残し続ける（#25 のレビュー）。記事ごとに消した記録を送れば、記事の表の流れだけで手元の状態が決まる。
- **消した記録をトリガーで残す**：下限と同じく、削除と同じ文の中で起き、消す側のコードが記録を忘れることもない。購読をやめる以外の理由で行が消えても（あとで作る、古い記事の回収など）、同じように伝わる。
- **手元に置く範囲を絞る**：何年分もの記事を手元に置くと、最初の同期が遅くなり、ブラウザの容量も使う。読むのは未読と最近の記事が中心。
- **後から受けたほうを採る**：ぶつかるのは既読・スター程度で、どちらを採っても困らない。複雑な仕組み（CRDT など）は要らない。

## 検討した代替案

- **時刻で同期する**：作りは簡単だが、時計のずれや書き込みの順のずれで取りこぼす（未決事項 7 で比べた）。
- **表をまたいで 1 つの番号を振る**：カーソルは単純になるが、番号の表の更新と行の更新を 1 つの文にできず、重なる。batch を使えばまとめられるが、緩衝層の DB に batch がない。
- **CRDT などで、ぶつかりを自動でまとめる**：既読・スターには大げさ。
- **記事をすべて手元に置く**：オフラインで何でも読めるが、最初の同期と容量が重い。
- **購読をやめたら、クライアントがそのフィードの記事をすべて消し、残すスター付きの記事はサーバーが送り直す**：変更は小さいが、表をまたいだ順序に頼るのは変わらず、送り直した記事が「購読をやめた」より先に届くと消してしまう。順序を保証するには、購読のページが残っている間は記事を送らないなど、表どうしを結び付ける仕組みが別に要る。
- **受信箱の行も消さずに、消した印を付ける**：記録の表は要らないが、一覧や未読の数など、受信箱を読むすべての処理で除外が要り、行も増え続ける。

## 見直す条件

- Postgres など、文が並行して動く DB に移すとき。「最大＋1」では番号が重なりうるので、番号の振り方を作り直す。
- 手元に置く範囲（30 日）が、使ってみて短すぎる ／ 長すぎると分かったとき。
