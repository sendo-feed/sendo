# 差分同期

- 状態：提案中
- 関連：[ユーザーと認証](accounts.md)、[テックスタック](tech-stack.md)、[古い記事の片付け](retention.md)、[クライアントの設定](settings.md)、[あとで読むページ](saved.md)、[技術構成](../tech-deck.md)（方針 03）

sendo-reader はローカルファーストで作る（画面はネットワークを待たず、ブラウザの SQLite に同期する）。そのための、サーバー（sendo）とクライアントの間の同期の決まり。

## 決定

1. **変更番号で同期する。** 人ごとのデータ（フォルダ、購読、記事の受信箱＝既読・スター、[クライアントの設定](settings.md)）の行に、変更番号（`seq`）を持たせる。行を作ったり変えたりするたびに、その表の中でいちばん大きい番号に 1 を足した番号を、同じ文の中で振る。
   - SQLite は書き込みを 1 つずつ順に処理するので、番号の順は書き込みの順と一致し、あとから小さい番号の変更が現れることはない（取りこぼさない）。同じ文で変えた行は同じ番号になってよい
   - **番号を二度と使わない。** 行を物理的に消すと表の最大が下がり、同期済みの番号がもう一度振られて取りこぼす。そこで、行が物理的に消えたら、その行の番号で、別の表の「下限」を引き上げる。これは表に付けたトリガーで行い、削除と下限の更新を同じ文の中で一緒に起こす（間にほかの書き込みが入らない）。番号は「表の最大と下限の大きいほう＋1」を、同じ文の中で振る
   - 番号は表ごとに増やし、クライアントは表ごとの番号をまとめた「カーソル」を持つ。カーソルの中身には意味を持たせず、クライアントはそのまま送り返すだけにする
   - 記事の公開日時や作成時刻は、同期の目印に使わない（公開日時の古い記事があとから入ると取りこぼす）
2. **1 回のリクエストで差分を取る。** `GET /api/v1/sync?cursor=…` で、カーソルより後に変わったフォルダ・購読・受信箱・クライアントの設定の行と、新しいカーソルを返す。受信箱の行には、記事の本体（タイトル、要約、URL など）を付ける。多すぎるときは途中で区切り、続きがあることを知らせる。
   - 購読の差分には、フィードの取得状態と直近の失敗理由のコード、確認できた移転先候補も載せる。[仕事の流し方](jobs.md)の 10 と[フィードの移転先候補](feed-relocation.md)
3. **消したものは「消した」という記録で伝える。**
   - フォルダと購読は、消すときに行を消さず、消した印と新しい変更番号を付ける
   - クライアントの設定の項目も、消した印を付ける。印の行は 30 日で回収する（[クライアントの設定](settings.md)の 3）
   - 受信箱の行は物理的に消す。公開フィードの購読をやめたときは、スターなしの記事が受信箱から消える。[Discord の購読](discord.md)の解除では、スター付きの記事も受信箱から消える。行が消えたら、表に付けたトリガーが、削除と同じ文の中で、その記事の「消した記録」を別の表に残す。記録には受信箱の表の続きの番号を振り、下限もその番号まで引き上げる。同期では、受信箱の行と消した記録を番号の順に混ぜて返す
   - **クライアントは、ほかの表の変化から行を消さない。** 手元の記事を消すのは、その記事の消した記録が届いたときだけにする（購読をやめた知らせを見て、そのフィードの記事を消さない）
   - 消した印の行と消した記録は、一定の期間がたったら物理的に消してよい（下限はトリガーが記録する）。それより古いカーソルが来たら、最初から同期し直すよう伝える。そのために、回収した範囲の番号も記録しておく
   - 受信箱の消した記録は 30 日で回収する。古い記事を消すと、受信箱の行が消えて記録が残る（[古い記事の片付け](retention.md)）
4. **最初の同期は、手元に置く範囲だけ。** カーソルなしで来たら、未読の記事、スターを付けた記事、直近 30 日に受信箱に入った記事を返す。それより古い記事は、必要なときに通常の API で読む（手元には置かない）。
5. **クライアントの操作は、手元にすぐ反映して、あとで送る。** 既読・スター・購読の変更などは、ローカルの DB にすぐ反映し（楽観的更新）、操作キューに積んで通常の REST API で送る。サーバーは操作を冪等に受ける。ぶつかったら、サーバーが後から受けたほうを採る。送った操作の結果は、次の同期で番号付きで戻ってくる。
6. **まとめて既読の境界に、カーソルを使えるようにする。** 「すべて既読」は、クライアントが同期済みの範囲（カーソルまで）に入っていた記事だけを既読にできるようにする。手元に届いていない記事を、見ないまま既読にしない。
7. **記事の本体は、取り込んだあとは変えない。** 同期するのは受信箱の行（既読・スター）の変化だけで、記事のタイトルや要約の書き換えは追わない。
8. **あとで読むページも変更番号で同期する。** `includeSaved=true` が指定されたときだけ、`savedPages` とその位置を返す。保存の位置がないカーソルでは、保存だけを最初から送る。解除の記録は 30 日で回収し、回収した範囲より古い保存カーソルには `invalid_cursor` を返す（[あとで読むページ](saved.md)）。

9. **人ごとの同期の対象が変わったら、WebSocket で知らせる。** 入口は `GET /api/v1/sync/updates`。
   - `101` を返す前に、有効なブラウザのセッションクッキーを必須とし、接続をそのセッションのユーザーにひも付ける。`Origin` が公開オリジンと厳密に一致することを確かめ、欠けていれば拒否する
   - reader が中継する構成では、`PUBLIC_URL` に有効な公開 HTTPS オリジンを設定する。Sendo に直接接続する構成で `PUBLIC_URL` がなければ、リクエスト URL のオリジンと照合する
   - ブラウザは reader 自身の `/api/v1/sync/updates` へ接続する。reader のコンテナは、このパスの WebSocket の Upgrade を書き換えずに中継し、`Origin`、`Cookie`、`Sec-WebSocket-*` をそのまま Sendo へ渡す。`101` のあとは、フレームを読まずに両方向へ流す（sendo-reader の[コンテナ版](https://github.com/sendo-feed/sendo-reader/blob/main/docs/decisions/container.md)の 4。Sendo の側の構成は[コンテナ版](container.md#動かし方)の 7）
   - 本番では reader の公開 URL と同じホストとポートの `wss:` に接続する。reader は CSP を変えずに（`connect-src 'self'` のまま）つなぐ。CSP の決まりは、sendo-reader の[ローカルファースト](https://github.com/sendo-feed/sendo-reader/blob/main/docs/decisions/local-first.md#ページの守り)の「ページの守り」が正
   - reader は、`/api/v1/sync/updates` につないでみて、つながれば通知を使う。つながらないとき（対応前の Sendo、中継に対応する前の reader、ネットワークの都合）は、間を空けてつなぎ直しながら、定期同期を続ける。Sendo が通知に対応しているかを、別の API で問い合わせない
   - 書き込みの後で、対象ユーザーの接続へ `{"type":"sync_required"}` を送る。reader は通知を受けたら手元のカーソルから差分を取る。知らせるのは次のとき
     - REST API と Google Reader API で、利用者の状態を変えるリクエスト（`GET` と `HEAD` 以外）が成功したとき（2xx）。認証のミドルウェアの後ろの 1 か所で、そのリクエストの利用者に知らせる。購読、フォルダ、設定、あとで読むページ、受信箱のどれを変えても届く
     - MCP の書き込みのツール（購読する ／ やめる、移す、名前を変える、既読、スター）が成功したとき
     - 取得のジョブが新しい記事を受信箱へ配ったときと、OPML の取り込みのジョブが購読を足したとき
     - 片付け（容量による削除など）で受信箱の行を消しただけのときは知らせず、定期同期で取り込む
   - 変更を送った端末にも届く。届いた端末は、差分が空でも困らない
   - 知らせは利用者ごとに 1 秒まとめ、その間に何度変わっても 1 回だけ送る
   - 取得ジョブと HTTP が動く同じ Node プロセスのメモリに接続を持つ。通知を送る前にセッションが有効か確かめ、失効していれば接続を閉じる。Sendo が停止するときも通知接続を閉じる
   - 通知の重複や欠落を許す。初回と再接続のどちらでも、接続が開いたら手元のカーソルから同期し、定期同期も続ける。通知が使えないときは従来の同期で動く
   - クライアントからはメッセージを送らない。Sendo は、次のコードで接続を閉じる。クライアントは、コードで次の動きを分ける
     - `1001`（`going away`）：Sendo が止まる、または入れ替わる。少し待って（数秒）つなぎ直す。止めるときは `1001` で閉じ、閉じきらない接続は少し待ってから切る
     - `1008`（`session ended`）：セッションが切れた。すぐにはつなぎ直さず、同期を 1 回して確かめる。401 ならログインし直す。同期が通れば、間を延ばしながらつなぎ直す。クライアントからメッセージが届いたとき（`client messages are not supported`）も `1008` で閉じる
     - `1013`（`try again later`）：接続数の上限に達した。長めに（1 分以上）間を空けてつなぎ直す
     - そのほか（`1006` など）：ネットワークの都合や、応答しない接続を Sendo が切ったとき。上限を置いて間を延ばしながらつなぎ直す
     - `101` を返す前に断ったとき（401、403、429、503）は、ブラウザの WebSocket からは状態コードが見えず、`1006` で閉じたようにしか見えない。クライアントは、ほかの `1006` と同じく、間を延ばしてつなぎ直すことで対処する。ログインが切れていれば、定期同期の 401 で気づく

## 理由

- **変更番号**：時刻は、時計のずれや処理の始まりと書き込みの順のずれで、取りこぼしが起きる。SQLite は書き込みを 1 つずつ処理するので、同じ文の中で「最大＋1」を振れば、ロックも batch も要らずに、書き込み順の番号が作れる（[テックスタック](tech-stack.md)の「守る規約」に沿う）。
- **番号の下限をトリガーで記録する**：行を物理的に消さない（すべて消した印にする）方法もあるが、行が増え続ける。消す前にコードで下限を記録すると、記録と削除の間にほかの更新が入ったとき、記録した下限より大きい番号の行まで消えて、番号が重なる（#21 のレビューで実際に確かめられた）。トリガーなら、削除と下限の更新が同じ文の中で起き、消す側のコードが記録を忘れることもない。SQLite にも Postgres にもトリガーがあるので、移植の妨げにならない。
- **表ごとの番号をまとめたカーソル**：表をまたいで 1 つの番号を振るには、番号の表を別に持って 2 つの文で更新する必要があり、その間にほかの書き込みが入ると番号が重なる。表ごとなら 1 つの文で済む。クライアントには中身を見せないので、あとで作りを変えられる。
- **1 回のリクエスト**：iOS ではバックグラウンドで同期できないので、起動したときの 1 回の速さが体感を決める（[技術構成](../tech-deck.md)）。
- **消した印と消した記録**：行を消すだけでは、クライアントに「消えた」ことを伝えられない。フォルダと購読は数が少ないので、行に印を付けて残す。受信箱は行が多く、一覧や未読の数など読む処理も多いので、行は消し、消したことだけを別の表に残す。
- **ほかの表の変化から消さない**：番号もページ送りも表ごとに別なので、表をまたいだ順序は保証されない。購読をやめた知らせを見て記事を消す決まりだと、購読の変更が 1 ページに収まらないときに、購読し直して入れ直した記事が先に届き、あとから届いた「購読をやめた」で消してしまう（#25 で確かめた）。また、スターを外してから購読をやめると、行が消えてスターを外した変更も届かず、クライアントは古いスターを根拠に記事を残し続ける（#25 のレビュー）。記事ごとに消した記録を送れば、記事の表の流れだけで手元の状態が決まる。
- **消した記録をトリガーで残す**：下限と同じく、削除と同じ文の中で起き、消す側のコードが記録を忘れることもない。購読の解除でも容量による片付けでも、受信箱の行が消えたことを同じように伝えられる。
- **手元に置く範囲を絞る**：何年分もの記事を手元に置くと、最初の同期が遅くなり、ブラウザの容量も使う。読むのは未読と最近の記事が中心。
- **後から受けたほうを採る**：ぶつかるのは既読・スター程度で、どちらを採っても困らない。複雑な仕組み（CRDT など）は要らない。
- **差分同期を始める時機を通知する。** 開いたままの reader に、取得のジョブや別の端末の変更をすぐ反映できる。カーソルで続きが取れるため、通知の再送を管理せずに済む。
- **状態を変えるリクエストの後に、入口の 1 か所で知らせる。** reader は、購読、フォルダ、設定、あとで読むページも同じカーソルで同期する。別の端末での変更を、開いたままの画面にすぐ届けられる。変更番号を振る書き込みは `db/` のあちこちにあり、そこで 1 つずつ知らせると、新しい書き込みを足したときに送り忘れる。入口の 1 か所なら、新しい API にも自動でかかる。変わらなかったリクエストでも知らせることになるが、届いた端末が空の差分を取るだけで済む。
- **利用者ごとに 1 秒まとめる。** 取得のジョブは、フィードごとに新着を配るたびに知らせるので、定期実行の直後に何度も続く。状態を変えるリクエストのたびに知らせるので、操作が続くときも重なる。まとめれば、送る回数と、送る前のセッションの確かめ（DB の読み取り）が減る。1 秒なら、読者が待つ長さは変わらない。
- **閉じるときのコードを決める。** クライアントは、閉じられた理由で次の動きを分けたい。セッションが切れたのにすぐつなぎ直すと、断られ続ける。上限に達したのにすぐつなぎ直すと、上限を押し続ける。Sendo が止まるときに接続を切るだけだと、ブラウザにはネットワークの失敗（`1006`）に見え、入れ替わりの数秒を待てない。
- **`1008` を 1 つの意味で使い分けない。** クライアントからはメッセージを送らないので、メッセージで閉じるのはクライアントのバグのときだけ。どちらでも、同期を 1 回して確かめれば、ログインし直すかどうかが分かる。コードを分けても、クライアントの動きは変わらない。
- **通知に対応しているかを、つないでみて決める。** Sendo と reader は compose で一緒に更新するので、新旧が混ざるのは更新の途中の短い間だけ。通知はもともと欠けてもよい作り（定期同期を続ける）なので、対応前の Sendo につないで失敗しても困らない。機能の有無を返す API を持たずに済む（[コンテナ版](container.md)の 3）。

## 検討した代替案

- **定期同期の間隔を短くする。** 更新がないときも SQLite に問い合わせる回数が増える。
- **受信箱、購読、フォルダ、設定などの書き込みごとに、`db/` の中で知らせる。** 変わった行があったときだけ知らせられるが、書き込みを足すたびに送り忘れが起きうる。入口で知らせれば、空の差分を取る端末が出るだけで済む。
- **Sendo の側でまとめず、reader だけでまとめる。** 作りは小さいが、送る回数とセッションの確かめは減らない。Google Reader API のアプリなど、ほかのクライアントが使うときにも、同じ負担がかかる。
- **閉じる理由を、メッセージ（`{"type":"session_ended"}` など）で送ってから閉じる。** 理由を細かく伝えられるが、閉じるコードで足りる。ブラウザの WebSocket は、閉じるコードと理由の文字列を `close` のイベントで受け取れる。
- **通知に対応しているかを、機能の有無を返す API（`syncUpdates`）で問い合わせる。** 対応前の Sendo につなぎにいく失敗を避けられるが、機能の有無を返す API を保ち続け、項目ごとにいつ消すかを決め続けることになる。新旧が混ざるのは短い間だけなので、つないで失敗したら定期同期を続ければ足りる。

- **時刻で同期する**：作りは簡単だが、時計のずれや書き込みの順のずれで取りこぼす。
- **表をまたいで 1 つの番号を振る**：カーソルは単純になるが、番号の表の更新と行の更新を 1 つの文にできず、重なる。batch を使えばまとめられるが、緩衝層の DB に batch がない。
- **CRDT などで、ぶつかりを自動でまとめる**：既読・スターには大げさ。
- **記事をすべて手元に置く**：オフラインで何でも読めるが、最初の同期と容量が重い。
- **購読をやめたら、クライアントがそのフィードの記事をすべて消し、残すスター付きの記事はサーバーが送り直す**：変更は小さいが、表をまたいだ順序に頼るのは変わらず、送り直した記事が「購読をやめた」より先に届くと消してしまう。順序を保証するには、購読のページが残っている間は記事を送らないなど、表どうしを結び付ける仕組みが別に要る。
- **受信箱の行も消さずに、消した印を付ける**：記録の表は要らないが、一覧や未読の数など、受信箱を読むすべての処理で除外が要り、行も増え続ける。

## 見直す条件

- Postgres など、文が並行して動く DB に移すとき。「最大＋1」では番号が重なりうるので、番号の振り方を作り直す。
- 手元に置く範囲（30 日）が、使ってみて短すぎる ／ 長すぎると分かったとき。
