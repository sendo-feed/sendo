# Web Push

- 状態：提案中
- 関連：[通知](notifications.md)（ベル、通知の行、通知の中身）、[コンテナ版](container.md)（3 の機能の有無、8 の接続する IP、13 のバックアップ）、[仕事の流し方](jobs.md)（5 のやり直し）、[ユーザーと認証](accounts.md)（セッション）、[画像の中継とサムネイル](images.md)（2 の sendo が持つ秘密、3 の時間切れ）

[通知](notifications.md)で決めたベルの通知を、sendo が Web Push で sendo-reader の端末に届ける。ここでは、VAPID の鍵と JWT、Web Push の有無、端末の登録、送る仕事と送り先を決める。通知の中身（Declarative Web Push の JSON と、その暗号化）は[通知](notifications.md)の 14〜16 で決める。通知の許可や Service Worker など reader の側の扱いは、sendo-reader の決定で決める。

## 決定

1. **VAPID の鍵は、sendo が初めて要るときに作り、DB に置く。** P-256 の鍵の組を Web Crypto で作り、秘密の JWK（公開鍵の `x`・`y` を含む）にして、sendo が自分で持つ秘密の表（`app_secrets`。[画像の中継とサムネイル](images.md)の 2 と同じ）の 1 行に置く。「なければ入れる」を 1 つの文で行い、入れたあとで読み直す。自動では作り直さない。
2. **VAPID の `sub` は、設定（`VAPID_SUBJECT`）で必須にする。** `mailto:` か `https:` の URL だけを受ける。
   - JWT（RFC 8292、ES256）は、送り先のオリジン（`aud`）ごとに作る。`exp` は作った時刻の 12 時間後にする（24 時間未満）
   - 同じ `aud` には、作ってから 6 時間は同じ JWT を使い回す（Apple に合わせて 1 時間以上）。JWT はプロセスのメモリに持つ。`aud` ごとに、作っている途中のものがあればそれを待って使い、同時に何個も作らない
   - プッシュサービスが 401 か 403 を返したら、その `aud` の JWT を、作ってから 1 時間以上たっていればメモリから捨てる。次に送る仕事が作り直す
3. **Web Push を使えるのは、`VAPID_SUBJECT` と `READER_URL` がそろっているときだけにし、有無は Web Push の API で伝える**（[コンテナ版](container.md)の 3）。
   - `GET /api/v1/push` が、`available` と VAPID の公開鍵（`publicKey`。非圧縮の点の base64url）を返す。使えない設定では `available: false`、`publicKey: null` を返し、登録の `PUT` は 501（`feature_unavailable`）を返す。`DELETE` は 501 にせず、4 のとおり成功させる
   - 形の正しくない値は、エラーをログに出して、使えない設定として扱う
   - ベルの保存と同期は、Web Push が使えなくても動く（鳴らないだけ）
4. **登録は端末ごとにし、セッションに結ぶ。** `PUT /api/v1/push/registration` で、ブラウザが返した登録（エンドポイントと `p256dh`・`auth` の鍵）を、そのリクエストのセッションと人に結んで置き、204 を返す。`DELETE` で、そのセッションの登録を外す（なくても 204）。
   - この入口は、ブラウザのセッションでだけ使える。アクセストークンでは 403（`session_required`。アクセストークンや OAuth の許可を扱う入口と同じ）。状態を変えるので、同じオリジンからだけ受ける
   - エンドポイントは 2,048 文字までで、6 の確かめを通るもの。`p256dh` は base64url で 65 バイトの非圧縮の P-256 の公開鍵（Web Crypto で読めるもの）、`auth` は base64url で 16 バイト。合わなければ 400
   - 1 つのセッションに登録は 1 つ、1 つのエンドポイントにも登録は 1 つ（どちらも一意の索引）。同じセッションに同じエンドポイントと鍵があれば、何も変えない。エンドポイントか鍵が違えば、新しい ID の行を入れ、同じ文の中で、同じセッションの行と同じエンドポイントの行（ほかの人の行も）を消す（SQLite の `INSERT OR REPLACE`）
   - セッションの行が消えると、同じ文の中で、そのセッションの登録も消える。ログアウトも、ユーザーの切り替え（ログインは、前のセッションのクッキーがあればその行を消してから作る）も、これで消える。クッキーのないログインで前の人のセッションが残っても、reader はユーザーが替わると端末の登録を解除する（sendo-reader の決定）ので、残った行は、送ったときの 404 ／ 410 で消える。同じエンドポイントの登録が送り直されたときは、その文で消える。期限の切れたセッションの登録には送らず、1 日 1 回の片付けで消す
   - reader は、通知の許可があれば、起動のたびとログインのたびに登録を送り直す（冪等）。`publicKey` が手元の登録の鍵と違えば、登録し直してから送る。細かい扱いは sendo-reader の決定で決める
   - エンドポイントと鍵は秘密として扱い、ログと応答に出さない
5. **ベルの通知は、その人の登録した端末すべてに送る。送るのは仕事の表に積んだ仕事で、取り込みと切り離す。** 通知の行（[通知](notifications.md)の 10）1 つと端末 1 つにつき 1 つの仕事にし、仕事は通知の行と登録の行の ID を持つ。中身（[通知](notifications.md)の 14）は送るときに組み立てる。登録の行がもうないとき、ベルが外されたとき、通知の記事の行の記事がもうその人の受信箱にないか既読のとき（購読をやめたとき、ほかの端末で読んだときなど）、まとめに入れる記事が受信箱に未読で 1 件も残っていないときは送らない。
   - 要求には `Content-Encoding: aes128gcm`、`TTL: 43200`（12 時間）、`Urgency: high`、VAPID の `Authorization`（2）を付ける。`Topic` は付けない
   - 時間切れは、応答を読み終えるまでで 15 秒（[画像の中継とサムネイル](images.md)の 3 と同じ）
   - 404 ／ 410：その登録を行の ID で消し、やり直さない
   - 429 と 503 で、`Retry-After` が 1 分より先を指すとき：やり直さずに諦める
   - そのほかの 429、5xx、つながらない、時間切れ：仕事をやり直す（[仕事の流し方](jobs.md)の 5）。やり直しが尽きたら諦める
   - 3xx とそのほかの 4xx：やり直さず、状態コードをログに出す。401 ／ 403 では、2 のとおり JWT を捨てる
   - 送るのに失敗しても、記事の取り込みは止めない
6. **送る先は、ブラウザが返したエンドポイントだけにする。**
   - 登録のときに、エンドポイントを `toFetchableUrl` で確かめ、`https:` だけを受ける。通らなければ 400
   - 送るときは緩衝層の `fetch` を使い、接続する IP も確かめる（[コンテナ版](container.md)の 8）。内部のアドレスに解決されたら、送らず、その登録を行の ID で消す
   - リダイレクトは追わず、応答の中の URL へも行かない

## 理由

- **鍵を sendo が作り、DB の 1 行に置く：** ブラウザの登録は公開鍵に結び付くので、鍵を変えると登録がすべて使えなくなる。設定で渡すと、デプロイする人が鍵を作る手間が増え、入れ違えたときに登録が黙って壊れる。DB に置けば、登録と同じバックアップに入り、戻すときも組で戻る（[コンテナ版](container.md)の 13）。秘密の JWK には公開鍵も入るので、1 行に置けば片方だけが入れ替わらない。
- **`sub` を設定で必須にする：** `sub` は、プッシュサービスが送り手に連絡するための宛先。Apple のプッシュサービスは、`sub` が URL か `mailto:` でない JWT を断る（Apple の Web Push の文書）。デプロイする人ごとに違い、sendo が決められる値ではない。
- **`exp` は 12 時間、使い回しは 6 時間：** VAPID（RFC 8292）は `exp` を 24 時間以内に求め、Apple は 1 日より先の `exp` を断り、JWT を 1 時間に 1 回より多く作り直さないよう求める。12 時間と 6 時間にすれば、時計が数時間ずれても両方の内側に収まる。
- **401 ／ 403 で、1 時間以上使った JWT を捨てる：** 使い回している JWT が断られたまま持ち続けると、作り直すまでの最大 6 時間、同じ `aud` の端末すべてに届かない。捨てれば、次の送信で作り直す。作ってから 1 時間たっていない JWT を捨てないのは、断られるたびに作り直すと、Apple の求める作り直しの間隔（1 時間に 1 回まで）を超えるため。
- **ベルは Web Push がなくても保存できる：** あとで設定を足すと、付けておいたベルがそのまま鳴り始める。reader は `available` を見て、ベルの操作と通知の許可を出すかを決められる。設定を外したあとも、登録を外す `DELETE` は失敗させない。
- **セッションに結ぶ：** 同じブラウザで別の人がログインすると、前の人の記事のタイトルが届いてしまう。セッションに結べば、ログアウトとユーザーの切り替えで、同じ文の中で登録も消える。期限の切れたセッションの端末にも送らないので、使わなくなった端末に記事のタイトルが出続けない。アクセストークンは端末に結び付かないので、登録には使わない。
- **同じセッションと同じエンドポイントの行を消す：** ブラウザは reader の Service Worker ごとに登録を 1 つ持ち、登録し直すとエンドポイントが変わる。宛先を、そのエンドポイントを最後に送ったセッションの 1 つにすれば、クッキーのないログインのあとでも、前の人の記事のタイトルが届かない。
- **置き換えたら新しい ID、同じなら変えない：** 送る仕事は登録の行の ID を持つ。置き換えた登録に同じ ID を使うと、古いエンドポイントへの仕事が 410 を受けて、新しい登録を消してしまう。同じ登録の送り直しで行を変えないのは、起動のたびに送り直しても、送っている途中の仕事を空振りさせないため。
- **鍵の形を登録のときに確かめる：** 壊れた鍵は、送るときの暗号化で失敗し、通知のたびに仕事が無駄になる。受けるときに断れば、reader が誤りに気づける。
- **端末ごとの仕事：** 1 つの端末で 500 が返っても、届いた端末にもう一度送らない。やり直しで同じ通知が 2 回届いても、端末では同じ `tag`（[通知](notifications.md)の 14）の通知が置き換わる。
- **`TTL` は 12 時間：** 遅れて届く通知は古い話になる（[通知](notifications.md)の 8 で、取り込んだ回の記事だけを判定するのと同じ考え）。夜のあいだ端末が切れていても、翌朝には届く長さにし、それより遅れたらプッシュサービスに捨てさせる。
- **`Urgency: high`：** ベルは、利用者が選んで付けた、すぐ知りたい知らせ。プッシュサービスは、`Urgency` が低いと、端末の省電力のあいだ届けるのを遅らせてよい（RFC 8030 の 5.3）。量は[通知](notifications.md)の 12 の上限で抑えてある。
- **`Topic` を付けない：** `Topic` は、まだ届いていない同じ `Topic` の通知を置き換える。記事ごとの通知を置き換えたくない。
- **`Retry-After` が 1 分より先なら諦める：** 仕事のやり直しは 1 分おきなので、求められた時刻より前に送り直してしまう。その時刻を指定して積み直すこともできるが、遅れた通知は古い話になるので、待たずに諦める。
- **404 ／ 410 で消す：** プッシュサービスが、その登録はもうないと答えたとき（購読の解除、アプリの削除）。試作でも、購読を解除した端末に送ると 410 が返った。
- **SSRF の対策を、登録と送信の両方に当てる：** エンドポイントはブラウザから来るが、sendo には、利用者が手で送った URL と見分けられない。reader の XSS や、API を直接呼ぶ人が、内部のアドレスを登録できる。フィードの取得と同じ確かめを当てれば、内部への送信を防げる。内部に解決された登録は使えないので消す。プッシュサービスはリダイレクトさせないので、追わなくても困らず、追えば確かめていない先へ送る道になる。

## 検討した代替案

- **VAPID の鍵を設定（環境変数）で渡す：** 鍵を自分で管理できるが、作る手間が増え、入れ違えると登録が黙って使えなくなる。
- **`sub` に `PUBLIC_URL` を使い、設定を足さない：** 設定は減るが、連絡の取れる宛先になるとは限らない。
- **送り先を、知っているプッシュサービスのホスト（FCM、Apple、Mozilla、Microsoft）に絞る：** 送れる先は狭くなるが、ほかのブラウザや、別のプッシュサービスを使うブラウザで届かない。内部への送信は、接続する IP の確かめで防げる。
- **登録を人だけに結ぶ（セッションに結ばない）：** ログアウトしても届き続け、同じ端末でほかの人に切り替えると、前の人の記事のタイトルが届く。
- **Web Push の有無を `GET /api/v1/features` で伝える：** 機能の有無をまとめて返す API は持たないと決めた（[コンテナ版](container.md)の 3）。

## 見直す条件

- VAPID の鍵を入れ替える必要が出たとき（漏れたときなど）。端末に登録し直してもらう手順を決める。
