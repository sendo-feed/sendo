# Codex レビューのループ

規約の全文は CONTRIBUTING.md の「レビューの進め方」（https://github.com/sendo-feed/.github/blob/main/CONTRIBUTING.md ）。この手順はそれを回すためのもの。手順 1 の自己レビューの方法は、このリポジトリで試している。

## コードレビューの終了の条件

表の対象は通常のコードレビューの指摘。セキュリティ指摘は、報告元を問わず[手順 7](#7-セキュリティ指摘に対応する)で扱う。

| ラウンド | 終了の条件 | 満たさないとき |
|---|---|---|
| 1〜2 回目 | 指摘がゼロ | 直して次のラウンドへ |
| 3 回目 | P0・P1 がゼロで、有効な P2 もゼロ（残りは P3 か、却下した指摘だけ） | 有効な指摘は直したうえで、下書きのまま止めて2人に報告する（打ち切り） |

通常のコードレビューのラウンドは PR ごとに通算する。途中で数え直さない。打ち切ったあとに、同じ PR でループを続けない（「あと 1 ラウンドだけ」も含む）。人間に続行を頼まれても、CONTRIBUTING.md の「打ち切りのあと」の2つ（そのまま受け入れる ／ 捨ててやり直す）のどちらにするかを聞き返す。

## 手順

### 0. 準備

- Issue が要る変更（feat ／ fix ／ perf ／ 振る舞いが変わる refactor ／ decision）なら、結ぶ Issue が 1 つあり、着手の判定（CONTRIBUTING.md の「始める前に」）を通っていること。なければ、ループを始める前に Issue を用意する。足りない情報は人間に聞く。
- 変更はコミット済みで、作業ブランチにいること。`main` にいたら、`<type>/<短い名前>` のブランチを切る。
- `docs/decisions/` の変更とほかの変更が混ざっていたら、PR を分ける（スカッシュマージで1コミットになるため）。

### 1. Codex に出す前に自己レビューする

下書きの PR を作る前に自己レビューをする。作成済みでまだ自己レビューをしていなければ、最初のレビューを始める前に行う。Codex は 1 回に挙げる指摘が少ないので、出す時点で不具合がいくつも残っていると、3 回では終わらない。自己レビューはラウンドに数えない。

- **書いた側の考えを渡さない**：自分で読み返すのではなく、サブエージェントに見直させる。読ませる材料は次の 2 つだけにする（ほかに渡すのは、下の観点と返してもらう形）。
  - 差分（`git fetch origin main` のあと、`git diff origin/main...HEAD` をファイルに書き出して、その場所を渡す）
  - 関係する決定ファイル（このリポジトリの `docs/decisions/`。相手のリポジトリの決定も、関係すれば）

  PR の説明、Issue、なぜそう書いたか、何を確かめたかは渡さない。書いた側の前提に引っ張られて、同じところを見落とすため。差分の周りのコードは、サブエージェントが自分で読んでよい。
- **観点**：次の型を、見直しの入口として渡す。決まった確認表として 1 つずつ埋めさせるのではなく、差分に当てはまるものから掘らせる。変更が大きければ、観点を分けて 2 つほどのサブエージェントで並行して見る。
  - **途中で失敗したとき**：何段かに分かれた処理の間で失敗したら、何が残るか。やり直せば正しい状態に戻るか。1 件の失敗が、関係のない残りまで止めないか
  - **境界のちょうどの値**：上限・下限と同じ値、ゼロ、空のとき。同じ境界を扱う箇所の間で、比べ方が食い違っていないか
  - **ほかの操作と重なったとき**：処理の途中で、利用者の操作、同期、別のリクエストやジョブが同じデータに触れたら
  - **本番の道と順**：テストが、本番の呼び出し元と同じ入口から、同じ順で呼んでいるか。前提の状態を、本番にない手順で作っていないか
  - **足した状態の後始末**：足した状態（表、印、設定、表示）が、いつ消えるか、いつ新しくなるか。失敗したときに元に戻るか
  - **データが増えたとき**：行や件数が実際の量まで増えても、速さが保てるか
- **返してもらう形**：指摘ごとに、優先度（P0〜P3。AGENTS.md の定義）、場所、起きる入力と結果。
- **見つけたものの扱い**：手順 5 と同じ基準で有効かどうかを判定し、有効な P0〜P2 を直してコミットしてから Codex に出す（P3 は直さなくてよい）。直しで新しい処理を足したときは、その部分だけを同じやり方でもう一度見直す。見直しのやり直しは 1 回までにし、そこで出たものを直したら Codex に出す。
  - 直すために受け入れ条件や範囲を変える必要が出たら、先に Issue を直して理由を添える。1 本の PR に収まらないと分かったら、出さずに止めて報告する（単位の分け方は AGENTS.md の「変更の進め方」）。
  - 決定を変える必要が出たら、直さずに止めて2人に相談する。
- 自己レビューで直したものと、直さなかったもの（理由と一緒に）は、PR の「確認したこと」に短く書く。返信する相手のコメントはないので、ここに残す。

### 2. 下書きの PR を用意する

```sh
gh pr view --json number,isDraft,url   # すでにあればそれを使う
```

なければ push して作る。タイトルはコミットメッセージの形式、本文は PR テンプレートの「何を変えたか」「なぜ変えたか」「確認したこと」を埋める。

Issue が要る変更では、「Issue」に `Closes #番号` を 1 つだけ書き、「受け入れ条件」を Issue から写す（正本は Issue。PR の側だけを書き換えない）。Issue の要らない PR では、どちらも見出しごと消す。

```sh
git push -u origin HEAD
gh pr create --draft --title "<type>(<scope>): <件名>" --body-file <本文のファイル>
```

### 3. コードレビューのラウンドを記録して始める

- 最初は、自己レビューを終えた下書きの PR を `gh pr ready <番号>` でレビュー待ちにする。次のラウンドは、レビュー待ちのまま修正コミットを push する。初回と、通常の指摘に対応する再レビューを数える。通常の修正とセキュリティ修正を同じ push に含めた場合も 1 回。セキュリティ対応だけの push は手順 7 に従う。ラウンドごとに一度起動し、結果を確かめてから次に進む。
- 要約は最新のレビューで上書きされるため、解除・push・手動依頼の前に、PR のコメントにラウンド番号、対象 SHA、起動する操作を 1 件記録する。本文の先頭に `<!-- review-loop-round -->` を付ける。たとえば「1 回目・`<SHA>`・下書き解除」と書く。
- 作業を引き継ぐときは、PR のコメントと要約を照合する。進行記録は、そのリポジトリへの書き込み権限が確認できた投稿者のものを使う。打ち切り記録を使うときも、通常の3回分の完了結果と PR の状態を照合する。最新の記録がセキュリティ対応なら手順 7、打ち切りなら手順 6 の残りから再開する。通常のラウンドの記録では、下書き解除なら PR の状態とタイムライン、push なら PR の HEAD、手動依頼なら記録の後に付いた依頼コメントを調べる。操作が済んでいれば手順 4 で結果を確認し、済んでいなければその回の操作から再開する。既存の手動依頼や自動レビューがある PR は、その履歴も確認し、回数を確定できないときは新しいレビューを始めず報告する。4 回目は始めない。

```sh
gh api "repos/{owner}/{repo}/issues/<番号>/comments" --paginate \
  --jq '.[] | select(.body | startswith("<!-- review-loop-round -->") or startswith("<!-- review-loop-stopped -->") or startswith("<!-- review-loop-security -->")) | {id, login: .user.login, created_at, body}'

gh api "repos/{owner}/{repo}/collaborators/<投稿者>/permission" --jq .permission
```

- 権限を照会した結果が `write` か `admin` の投稿者の記録を数える。記録だけでレビューの完了を判定せず、手順 4 のボットの結果と照合する。
- 同じ SHA で次のラウンドが必要なら、要約の `Code Review` 行を控え、`gh pr comment <番号> --body "@codex review"` で依頼する。依頼コメントの作成時刻を GitHub で確かめる。対象 SHA の自動レビューが進行中なら、その結果を待つ。

### 4. Codex のレビューを待つ

`chatgpt-codex-connector[bot]` が投稿する「Codex Review Summary」は、同じコメントに最新の状態を上書きする。PR の HEAD と要約を GitHub から読む。下書きを外した時刻は PR タイムラインの最新の `ready_for_review` で確認できる。

```sh
gh api "repos/{owner}/{repo}/pulls/<番号>" --jq .head.sha
gh api "repos/{owner}/{repo}/issues/<番号>/timeline" --paginate \
  --jq '.[] | select(.event == "ready_for_review") | .created_at'
gh api "repos/{owner}/{repo}/issues/<番号>/comments" --paginate \
  --jq '.[] | select(.user.login == "chatgpt-codex-connector[bot]") | .body | select(contains("<!-- codex-pull-request-review-summary -->"))'
```

- `<!-- codex-review-state:v1 {...} -->` の `code_review.status` が `completed` で、`code_review.commit_sha` が PR の最新 HEAD とラウンドに記録した SHA に一致したら、コードレビューは完了。待っている間に HEAD が変わったら、PR の最新 HEAD とラウンドの記録を確認し直す。完了を確認したラウンドの記録には、対象 SHA と要約の `Code Review` 行を追記する。
- 自動レビューでは、要約の `Code Review` 行の起動理由が、下書き解除なら `Draft marked ready`、push なら `New commits` であることを確かめる。行の `relative-time` の `datetime` がラウンドを記録した時刻よりあとであることを確かめる。下書き解除のレビューはタイムラインの解除時刻とも照合する。
- 同じ SHA を手動で再レビューする場合は、要約の `Code Review` 行が `Manual request` を示し、今回の依頼よりあとに完了したことを行の `relative-time` の `datetime` で確かめる。依頼前に控えた行が更新されるまで待つ。要約全体の更新時刻は、セキュリティレビューでも変わる。
- 指摘ゼロの判定は `code_review.has_any_findings == false`。指摘ゼロの個別コメントが出ないこともある。👀 や 👍 は反応の目安として使う。
- Security Review は、`security_review.status` と `security_review.commit_sha` を個別に確認する。要約全体が完了でも、両レビューが別々のコミットを指す場合がある。`has_any_findings` が `null` のときは、要約と個別の指摘を照合する。
- 待つときはバックグラウンドで 60 秒おきに確かめ、30 分たっても終わらなければ止めて報告する。

指摘があれば、次でレビューと行コメントを読む。今回のコードレビューは対象 SHA と投稿時刻で見分け、そのレビューの ID に結びついた行コメントを読む。コードレビューとセキュリティレビューが並行したときは、レビュー本体の表示で区別する。自動レビューの投稿時刻は今回の起動・完了時刻と照合する。要約に未解決の指摘が残っていれば、前のレビューのスレッドも確認する。

```sh
# レビュー本体
gh api "repos/{owner}/{repo}/pulls/<番号>/reviews" --paginate \
  --jq '.[] | select(.user.login == "chatgpt-codex-connector[bot]") | {id, commit_id, submitted_at, body}'
# 行ごとの指摘
gh api "repos/{owner}/{repo}/pulls/<番号>/comments" --paginate \
  --jq '.[] | select(.user.login == "chatgpt-codex-connector[bot]") | {id, pull_request_review_id, path, line, created_at, body}'
```

### 5. 指摘を判定する

指摘ごとに、優先度と有効かどうかを決める。コードレビュー・セキュリティレビューのどちらから来ても、セキュリティ指摘は手順 7 に回す。通常のラウンドは残りの指摘で判定する。

- **優先度**：本文の P0〜P3 の表示に従う。表示がなければ AGENTS.md の定義で自分で付ける。
- **受け入れ条件があるとき**：受け入れ条件の外の入力への指摘は、P0 でない限り P2 以下として扱う（Codex の表示が P1 でも下げ、返信に理由を書く）。「対象外」に書いたものへの指摘は、却下できる。
- 指摘に応えるために受け入れ条件や範囲を変える必要が出たら、PR の説明ではなく、先に Issue を直して理由を添える。1 本の PR に収まらなくなったら、直さずに止めて報告する。
- **有効かどうか**：Codex の指摘をそのまま信じない。コードと `docs/decisions/` を読んで確かめる。判断に迷う P0・P1 は有効として扱う。
- **有効なもの**：手順 6 の終了判定を先に行う。続けるか打ち切る場合は、修正をコミットする（Conventional Commits）。3 回目に P3 だけが残って終了できるときは、そのまま報告する。
- **却下するもの**：その指摘に理由を返信する。

```sh
gh api -X POST "repos/{owner}/{repo}/pulls/<番号>/comments/<コメントID>/replies" -f body="<却下の理由>"
```

- 指摘に応えるために `docs/decisions/` の決定を変える必要が出たら、直さずにそこで止め、2人に相談する。

### 6. コードレビューの終了を判定する

上の表で判定する。

- **続ける**：手順 3 に戻り、次のラウンドを記録してから修正を push する。同じ SHA なら手動で依頼する。
- **終了**：終了条件を満たした対象 SHA と、ラウンド数、直した指摘、却下した指摘と理由を PR に記録する。セキュリティ対応が残っていれば手順 7 に進む。手順 8 の確認結果を含めて 2 人に報告する。
- **3 回目で打ち切り**：打ち切りと、最後に push する修正の SHA（修正なしなら PR の HEAD）を、`<!-- review-loop-stopped -->` から始まる PR コメントに記録する。`gh pr view <番号> --json isDraft` で状態を確認し、レビュー待ちなら `gh pr ready <番号> --undo` で下書きに戻す。下書きに戻ったことを確かめ、記録した修正が最新 HEAD にまだ含まれていなければ push する。セキュリティ対応で進んだ HEAD がその SHA を含む場合は、現在の HEAD から続ける。下書きのまま、残った指摘と[打ち切りのあと](#打ち切りのあと)の選択肢を 2 人に報告し、セキュリティ対応は手順 7 で進める。
### 7. セキュリティ指摘に対応する

- 報告元を問わず、指摘を全件判定する。PR が持ち込むか悪化させる有効な問題は、優先度にかかわらずマージ前に解消する。重複は一方に判断を集約して相互に参照し、誤検知は根拠を残す。今回の変更と独立した既存の問題は別の課題で追う。未公開の脆弱性の詳細や追跡は[セキュリティポリシー](https://github.com/sendo-feed/.github/blob/main/SECURITY.md)に従い非公開の報告に残し、公開 PR には詳細を明かさず対応状況だけを記録する。差分やレビュー結果から未公開の脆弱性を特定できる場合は、公開できる状態になるまで修正とレビューを非公開で進める。決定や受け入れ条件を変える必要があれば、手順 5 に従う。
- セキュリティ対応だけの push の前に、`<!-- review-loop-security -->` から始まる PR コメントに起点の HEAD、push する SHA、対応状況を記録する。公開 PR では、未公開の指摘を特定できる説明や参照先は非公開の報告で扱う。同時に走る Code Review はラウンドに加えず、修正で生じた回帰や新しい脆弱性を確認する。その修正に起因する回帰はここで直す。別の有効な P0・P1 が出たら、2 人に報告し、扱いが決まるまでマージを保留する。
- セキュリティ修正の push を引き継ぐときは、記録の起点・対象 SHA と PR の状態を読む。push が済んでいれば対象 SHA のレビュー結果を確認する。未 push で HEAD が記録した起点と一致する場合は、記録した SHA の push から再開する。HEAD がさらに進んでいれば、その変更と記録を確認し直す。
- コードレビューを打ち切った PR は下書きのまま修正する。Security Review が対象で最新 HEAD の結果が古いか未起動なら、単独で手動依頼できる。自動起動が見込まれる操作の直後は、手順 4 の間隔で一度読み直す。最新 HEAD のレビューが進行中なら完了を待つ。
- 手動依頼は、対象 SHA と依頼予定を `<!-- review-loop-security -->` の記録に残し、その後に `gh pr comment <番号> --body "@codex security review"` で依頼する。再開するときに、その記録のあとで同じ SHA の依頼が投稿済みなら、結果を待つ。手動依頼の完了は対象 SHA と `Security Review` 行の `Manual request`、依頼コメントよりあとの完了時刻を照合する。
- 確認したセキュリティ指摘の対応状況は、未対応分も含めて記録する。未公開のものは非公開の報告に残し、公開 PR には詳細を明かさない対応状況だけを書く。通常の修正とまとめて push する場合も同じ。再開時とマージ前は過去の指摘と記録を読み、新しい結果に再掲されなかった指摘についても、修正と検証の結果を照合する。
- 通常のコードレビューがまだ必要なら、手順 3 で残りの回を確認する。終了済みか打ち切りなら手順 8 に進む。

### 8. マージ前に最新 HEAD を確認する

- 手順 4 のコマンドで最新 HEAD の Code Review の完了を確認する。同じ HEAD の対象 CI が成功し、セキュリティ指摘の判定が済んだことも確かめる。Security Review が対象の PR では、`security_review.status == completed` と最新 HEAD への SHA の一致まで別に確認する。古いか未起動なら手順 7 から確認し直す。必要な結果が揃わない、または有効なセキュリティ指摘が未解消ならマージを保留する。
- 通常の終了後に HEAD が変わったら、終了を記録した SHA 以降の差分が、記録されたセキュリティ対応だけであることを確かめる。それ以外の変更があれば、ラウンド上限内で通常の終了を判定し直すか、人間が判断するまでマージを保留する。
- コードレビューが打ち切りなら、残った指摘への人間の判断と、その対象 SHA を記録する。記録した SHA から進んだ差分にセキュリティ対応以外の変更があれば、人間の判断を改めて求める。受け入れの指示を受けて下書きを外した場合も、自動レビューを最新 HEAD の確認に使い、新しく見つかった有効な P0・P1 で判断が必要なら報告する。通常のループは再開しない。
- 対象 SHA と確認した両レビュー・CI の結果を PR に記録する。人間のマージ指示を受けたときだけ、確認済みの SHA を指定してスカッシュマージし、[マージ後の片付け](#マージ後の片付け)まで行う。

```sh
gh pr merge <番号> --squash --match-head-commit <確認済みのSHA> \
  --subject "<PR のタイトル> (#<番号>)" --body "<PR の説明>"
```

## マージ後の片付け

片付けるのは、この作業専用の worktree とローカルブランチ、この作業で作った一時ファイル。

1. PR がマージ済みであることを確かめる。`git fetch origin main` で更新した `origin/main` にマージコミットが含まれ、作業ブランチの先端が PR のマージ時の HEAD と一致することを確認する。
2. `git worktree list` で対象を調べ、残す worktree から作業する。専用 worktree を削除する直前に、ほかの作業で使われていないことと、未コミットの変更・未追跡ファイル・Git が無視するファイルを確認する。残すべきものがあるか、ほかの作業での利用が分からなければ、専用 worktree とブランチを残す。片付けられる専用 worktree は `git worktree remove` で削除する。
3. ブランチがどの worktree でも使われておらず、先端が手順 1 で確かめた SHA と一致することを削除の直前に確認する。`git branch -d` で削除し、スカッシュマージによる祖先関係などを理由に拒否された場合はそのブランチを残す。
4. この作業で作った一時ファイルを片付ける。`git worktree list` と `git branch --list` で削除を確かめる。途中で失敗したときは、残った対象を再確認してから続ける。残したものがあれば、場所と理由を報告する。

## 打ち切りのあと

- **そのまま受け入れる**：残った通常のコードレビュー指摘を人間が却下するか別の課題に回す。手順 7 でセキュリティ対応を済ませ、人間の指示で下書きを外し、手順 8 の確認を済ませてからマージする。
- **捨ててやり直す**：PR を閉じて Issue に戻り、下の準備をしてから、`main` から新しく作る。
  - コードは引き継がない。cherry-pick しない。前のブランチは消さずに残し、読むだけにする。
  - 実在の入力の fixture は使ってよい。指摘ごとに足した合成のテストは持ち込まない。

### やり直す前の準備

実装の前に、次をこの順に行う。

1. **捨てた理由を残す**：Issue にコメントで書く。
2. **Issue を見直して直す**：次の3つを、この順にすべて見直す。原因がどれか1つに見えても、3つとも通す（問題のない段は、確認だけで済む）。
   1. **やりたいこと**：何を・どこまで・やらないことを、1〜2 文ずつ書けているか。決定（`docs/decisions/`）が変わるなら、決定の変更をそれだけで 1 つのサブ Issue にし、先に出す。
   2. **受け入れ条件**：確かめる入力と期待する結果、対象外が書けているか。入力は実在のものを使う。
   3. **単位**：受け入れ条件のまとまりが、1 本の PR に収まるか。単位が変わるなら、サブ Issue に分けて順番を決める（もとの Issue は親 Issue にするか、閉じて作り直す）。
3. **着手の判定をやり直す**：直した Issue で着手の判定を通してから、`main` から新しく作る。

人間は、見直しに要る情報を出す。人間の了承は要らない（着手の判定と同じ）。
